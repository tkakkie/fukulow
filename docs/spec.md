## Model
- A channel's timeline shows messages that have no topic (topic = null).
- Reply: a message may reply to another message. Replies form a chain, shown together in a right-side panel.
- A reply chain can be moved to a topic under the channel. A topic can also be created first and posted to directly.
- Messages inside a topic are shown only in the topic. The main timeline shows one line when a topic is created/updated.
- No threads. No calls (use external OSS if ever needed).

## MVP
Sign in, organization, channels, topics, reply chains, DM, unread/mention, basic search.
Later: attachments, reactions, push notifications, bots/webhooks, multiple organizations UI, OIDC.

## Setup
- `FUKULOW_SETUP_TOKEN` is optional: unset preserves setup without a token; an explicitly empty value fails startup.
- Setup extracts the JSON body before checking `setup_token`. Malformed JSON, missing required fields or invalid field types return 400, oversized bodies return 413, and unsupported content types return 415 even if the token is missing or invalid.
- After successful extraction, a configured token must match before semantic input validation, password hashing or database access; missing or incorrect tokens return the same generic 401 before and after setup.

## Real-time sync contract
Behaviour contract for Message delivery. OpenAPI covers only types (REST shapes, `ClientMessage`/`ServerEvent`, close codes); Rust, the web client and a future Kotlin client satisfy this contract independently and need not share an algorithm. Design and review: #91.
Scope of every key and guarantee: one Organization and one session. The idempotency key is `(organization_id, sender, client_message_id)`. Delivery guarantees assume the supported single-process deployment (`docs/decisions.md`).

### Server guarantees (implemented and tested)
Tests are in `server/src/messages/tests.rs` (M) and `server/src/realtime/tests.rs` (R).
- S1. seq is per Channel, starts at 1 and is consecutive with no gaps (a rollback or an idempotent retry consumes no number); it is the Channel's confirmed-Message ordinal. No order is promised across Channels. Tests: M `concurrent_sends_allocate_unique_consecutive_channel_sequences`, M `failed_send_after_sequence_allocation_leaves_no_gap`, M `concurrent_duplicate_sends_create_one_message_and_consume_one_sequence`, M `concurrent_cross_channel_duplicate_conflicts_without_sequence_gap`.
- S2. For an **accepted** subscription while the Member stays authorized: after `subscribe(channel, after_seq=N)` every confirmed Message with seq > N' is delivered in ascending order with no omissions, where N' = min(N, the Channel's committed high-water seq) (a future cursor is clamped, intended for database restore). Duplicates are possible: at-least-once, not exactly-once. Tests: R `replay_pages_handoff_and_reconnect_keep_independent_channel_sequences_without_gaps`, R `concurrent_message_delivery_is_in_channel_sequence_order`, R `out_of_order_publication_fills_committed_gaps_without_duplicate_delivery`, R `malformed_controls_and_future_cursor_do_not_break_subscription_state` (clamp).
- S3. `subscribed(caught_up_seq=K)` is a replay/queued-prefix **handoff watermark**: replay is finished and live delivery follows. It is not "the newest seq now"; Messages committed after the handoff snapshot may still be on their way. Tests: R `replay_pages_handoff_and_reconnect_keep_independent_channel_sequences_without_gaps`, R `malformed_controls_and_future_cursor_do_not_break_subscription_state`.
- S4. Overflow and session end are never silent: 4008 (queue overflow, authorization-query failure, send timeout) and 4001 (session ended) close the socket; other internal failures may close with 1011. The server does **not** close the socket when a subscription is refused (`channel_not_found`, `subscription_limit` errors) or when a private-Channel Member loses membership after subscribing (delivery to them simply stops). Tests: R `overflow_closes_socket_and_reconnect_replays_every_committed_message`, R `sign_out_closes_idle_and_replaying_sockets_but_leaves_other_sessions_usable`, R `session_expiry_closes_idle_and_replaying_sockets`, R `session_check_database_timeout_at_connect_closes_with_internal_error`, R `live_delivery_rechecks_private_membership_after_subscription` (silence, socket stays open). No dedicated test: 4008 on authorization-query failure and on send timeout. Reconnect timing is client policy.
- S5. The same `(organization_id, sender, client_message_id)` returns the same confirmed Message (409 if body or Channel differ), subject to current authorization. `client_message_id` is unique per sender only. Tests: M `committed_send_retry_returns_canonical_message_without_sequence_allocation`, M `reused_client_id_conflicts_on_different_body_or_channel`, M `equal_ids_in_two_organizations_do_not_collide`.
- History pages: `latest` (no cursor) returns the newest Messages visible to its query snapshot (not a response-time watermark), ascending; default 50, max 200; `after_seq`/`before_seq` are exclusive; `has_more` means older Messages for latest/before pages and newer ones for after pages. Test: M `message_pages_are_bounded_exclusive_ascending_and_directional`.

Guarantee scope: for an accepted subscription while the Member stays authorized (single process), at-least-once, ascending within the Channel, no omissions. Convergence after reconnect is an end-to-end property of the server together with a client that satisfies C1-C9, not a server-only guarantee. Not guaranteed: order across Channels, exactly-once, immediacy while disconnected (filled after reconnect), delivery after the Member loses access (it stops without closing the socket), and convergence after a database restore whose history has already grown past the client's old cursor (see C8).

### Client rules
Implemented by the TypeScript client (`web/src/protocol.ts` pure protocol, `web/src/sync.ts` controller, Svelte adapters on top) and checked by the shared `contract/realtime` client fixtures, which run against the protocol and through the controller transports and timers, plus the tests listed in `docs/invariants.md`. Any other client (for example Kotlin later) must satisfy the same fixtures. Client-side scope: replacing the session clears and fences the previous session's client state, so its Messages and pending sends never appear in the new session.
- C1. Deduplicate Messages by (channel, seq).
- C2. Resume cursor = the highest seq confirmed gap-free from a trusted base.
  - Bootstrap while a Channel is uninitialized: fetch the `latest` page, take its highest seq as base B (0 only if that page is empty), then subscribe with `after_seq = B`; Messages committed in between are replayed. B is never a maximum chosen from concurrent ack/echo records (those are buffered and merged). Once initialized, a refreshed or stale `latest` page never moves the cursor over a gap or backwards; an intentional reset is C8.
  - Afterwards the cursor advances only through seq contiguous with it: a live event with seq = cursor + 1, a replay continuing from the cursor, or a history page requested with `after_seq = cursor` (if live traffic advanced the cursor meanwhile, merge the response's still-contiguous suffix).
  - A page that is internally consecutive but not adjacent to the cursor, and every `before_seq` page, extends the window only. Example: cursor 100, receive 102 then 101: the cursor stays 100 until 101 arrives, then becomes 102.
  - An HTTP ack alone never advances the cursor. A server-confirmed record buffered from an ack may count toward contiguity when a live event, replay or `after_seq = cursor` page advances the cursor (example: cursor 100, buffered ack 102, live 101: the cursor becomes 102). The cursor never passes a missing seq. The order of ack and live arrival may differ: an ack arriving after the live event it follows need not advance the cursor at once, which is safe, and reconnect replay (C4) converges to the same state.
- C3. Gap detection and gap filling are separate decisions. A held seq above cursor + 1 is a gap. Wait briefly for reordering (the grace period is a controller parameter, not part of the contract); fill (`after_seq = cursor`) only if the gap persists. A gap at or below `caught_up_seq` K of a completed `subscribed` is not explained by replay and is filled at once; a gap above K may still be in flight and follows the grace period. Never issue overlapping fills for the same range; coverage by a request in flight is cleared on success and on failure, and failed fills back off. A fill continues page by page until the gap is closed. The cursor never passes a gap.
- C4. On reconnect every watched Channel is resubscribed from its C2 cursor; races between history and live converge by C1 and C3. After 4008, reconnect first, with bounded retries on repeated overflow. Abnormal closes and 1011 are treated like other non-4001 closes (backoff). 4001 means Sign in.
- C5. A pending send is resolved when an ack, echo or **any fetched history page (including older pages)** holds a Message with the same Channel, sender (the signed-in Member) and `client_message_id`. A Message missing from one page is not evidence that the send failed; a pending Message outside the loaded window is resolved by the same-key resend (C6). The confirmed Message always comes from the server record; local optimistic content never replaces it, and later ack/echo/history copies merge by (channel, seq) with the server record winning.
- C6. While a send outcome is unknown (network error, timeout, lost ack) resend with the same `client_message_id`. Definite refusals (400/403/404/409/413/415) are not resent; 401 means Sign in. A late 401 from a request that a history-generation change (C8) invalidated (clamp C8, unwatch or unavailable C9) still means Sign in when it comes from the same session; a 401 from a replaced session is ignored. A late failure or timeout never resurrects a pending entry already settled by echo, ack or history.
- C7. Another sender's identical `client_message_id` is a different Message.
- C8. Cursor clamp recovery: compare `caught_up_seq` with the `after_seq` **sent for that subscription**. If K < sent after_seq, the server's history is older than the client's (database restore): invalidate that Channel's confirmed window and cursor, fence stale async results by generation, and re-bootstrap (C2). Release the old server subscription at once, including when the Channel is unwatched before re-bootstrap finishes. Send state survives: definite failures stay failed, unknown outcomes stay resendable with the same `client_message_id`, a send invalidated with the old generation becomes unknown and its late result (other than 401, see C6) changes nothing, and a send started in the new bootstrap generation stays active and follows C5/C6. Clamp never resends automatically. Lowering the cursor alone is not enough. **Scope limit:** only a restored Channel that is behind the cursor is detected. A restored history that has already grown past the old cursor cannot be detected with today's API; a history-generation identifier in history/subscription responses is deferred until needed, and the end-to-end "convergent after reconnect" property excludes that case.
- C9. A refused subscription (`channel_not_found`, `subscription_limit`) or a 403/404 on history is terminal for that Channel until the user acts (select again, Sign in again): it is not a sequence gap, is never retried in a loop, and the UI shows the Channel as unavailable.

### Observable vocabulary (used by `contract/realtime` fixtures)
Fixtures assert only what a client shows or emits to the outside; they do not name internal state, functions or timers. Any implementation (Rust, TypeScript, a future Kotlin client) with different internals satisfies the contract if these observations hold.
- **Channel state** (what the client shows for a watched Channel): `loading` = initial sync not finished: this covers having no base yet and also having a base (from the initial history page) while the subscription is not yet confirmed; `ready` = initial sync finished, i.e. a base is established and the server has confirmed the subscription (`subscribed`), so the cursor is trusted. Establishing a base alone does not make a Channel `ready`. How a Channel is shown during a reconnect is not fixed by this contract unless a fixture asserts it; `unavailable` = terminal for that Channel until the user acts (C9).
- **Session state**: `signed_in`, or `sign_in_required` after a 401 or a 4001 close (C6, S4).
- **Effect categories** (what a client emits outward, as classified by contract tests): HTTP requests, WebSocket connect/subscribe/unsubscribe, and `wait` effects classified as `reorder_grace` (C3 grace before filling a gap), `fill_backoff` (pause after a failed fill, C3) and `reconnect_backoff` (pause before reconnecting, C4). These are categories of observable behaviour only: how long a wait is, how it is scheduled, and whether the implementation has a timer at all are not part of the contract.

Capabilities (per-operation `{allowed, reason?}` on resources) are not part of this contract; they are added only when the UI must show whether an operation is possible in advance (see `docs/decisions.md`).
