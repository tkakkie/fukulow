## Model
- A channel's timeline shows messages that have no topic (topic = null).
- Reply: a message may reply to another message. Replies form a chain, shown together in a right-side panel.
- A reply chain can be moved to a topic under the channel. A topic is created by its first message (or by a Move to a new topic); empty topics do not exist.
- Messages inside a topic are shown only in the topic. The main timeline shows one summary line per topic, at the topic's latest activity (a derived display).
- No threads. No calls (use external OSS if ever needed).

## MVP
Sign in, organization, channels, topics, reply chains, DM, unread/mention, basic search.
Later: attachments, reactions, push notifications, bots/webhooks, multiple organizations UI, OIDC.

## Accounts and Memberships
- An Account owns globally unique lower-case email, password and Account Sessions. A Member owns the display name and Role in one Organization. One Account may have different Members and Roles in several Organizations; there is at most one Member per Account per Organization.
- Sign in uses email and password only. Web POST /api/v1/session returns only identity and expires_in, setting an HttpOnly Account Session cookie; native POST /api/v1/native/session returns identity, token and expires_in without cookies. Both share verification, issuance, throttling and DELETE /api/v1/session revocation.
- GET /api/v1/me returns the Account and its active Organizations; GET /api/v1/orgs/{org}/me returns its active Member. Every Channel, Message and WebSocket route is under /api/v1/orgs/{org}; only the authenticated Account and that Organization URL establish authority.
- A non-Member, unknown Organization and deactivated Member all return identical 404 ErrorBody with error `organization_unavailable`. Other denials have distinct error values (for example `origin_not_allowed`). Cookie WebSocket Origin validation precedes authentication and Organization resolution: a missing or disallowed Origin returns 403 `origin_not_allowed` even with invalid credentials or an unavailable Organization. Member rows and historical attribution are retained. Reactivation never automatically restores private Channel permissions.

## Members, Roles and Invites
- The server uses one deny-by-default `authorize(actor, action, resource)`. Owners invite any Role and change Roles; Admins invite Admin/Member/Guest. Member and Guest cannot invite or change Roles. All active Members may list active Members (id/name/Role only). Owner/Admin/Member may create Channels; Guest cannot.
- Channel access permits a current explicit grant, or a public Channel for Owner/Admin/Member. Guest always needs a current explicit grant, including public Channels. Role, active Membership, revision and grants are read afresh for history, writes, subscribe, replay and fan-out; Owner/Admin never bypass private grants.
- Organization Capabilities are `can_invite`, `can_manage_roles`, `can_create_channels`; Channel Capability is `can_add_members` (Owner/Admin with Channel access; management endpoints belong to #149). Each is `{allowed, reason?}`, computed by `authorize`; they are UI hints, never authority.
- An Invite binds one normalized email and Role, expires after seven days and is single use. A 256-bit random token is returned once; only its SHA-256 hash is stored. The web sends tokens in POST bodies, shares fragment-only links and removes incoming fragments from browser history immediately; no credentials in web storage.
- Existing Accounts must sign in and match the Invite email by their authenticated Account id. Anonymous acceptance creates an Account only when the email is unused; a uniqueness race refuses rather than attaching that Account. New Accounts sign in afterward. Used/expired/unknown/foreign Invite or wrong supplied email returns identical 404 `invite_unavailable`; mismatched signed-in Account returns 403 `invite_account_mismatch`.
- Invite emails are not verified: an Account accepting an Invite is bound by authentication, not proof of email ownership; email verification is out of scope.
- Acceptance, Member activation and token consumption commit atomically; expiry is checked at consumption. An active Member cannot accept an Invite to change Role. A deactivated Member reuses its id and revision, gets the invited Role/name and restores no old Channel grants. Under the same Organization lock, acceptance re-reads the issuer's active Membership and current Role, applying the same permission rule as Invite creation for the invited Role; otherwise it returns 403 `invite_issuer_unauthorized`. No email sending or Invite revocation endpoint in this Issue.
- The last active Owner cannot be demoted or deactivated, including concurrent/direct SQL changes. Role changes serialize per Organization and re-check the actor under a Member lock through COMMIT. Organization removal remains out of scope.

## Setup
- `FUKULOW_SETUP_TOKEN` is required in every mode (Compose, docker run, standalone binary). Unset, whitespace-only or the former published example (`setup-token-local-test-only`, also with surrounding whitespace) fails startup with a Result error, regardless of `FUKULOW_COOKIE_SECURE`. `.env.example` leaves it empty; generate a secret with `openssl rand -base64 32`. Development and tests explicitly supply their own test-only values. The server never generates or logs the token; accepted values retain their exact bytes.
- Setup extracts the JSON body before checking `setup_token`. Malformed JSON, missing required fields or invalid field types return 400, oversized bodies return 413, and unsupported content types return 415 even if the token is missing or invalid.
- After successful extraction, the token must match before semantic input validation, password hashing or database access; missing or incorrect tokens return the same generic 401 before and after setup.
- `GET /api/v1/setup` remains public and read-only: only `setup_required`, with `Cache-Control: no-store`, independent of the token.

## Proxy and sign-in limits
- Sign-in failure budgets are process-local: 20 per IPv4 or IPv6 /64 and 5 per normalized Account email in a 60-second window. IPv4-mapped IPv6 shares the IPv4 budget. Web and native sign-in share budgets; in-flight attempts reserve capacity, and successful attempts release it.
- Standalone proxy configuration requires both `FUKULOW_TRUSTED_PROXIES` (comma-separated exact IPs or CIDRs, IPv4/IPv6) and `FUKULOW_CLIENT_IP_HEADER`. Invalid/partial configuration fails startup. CIDR prefix lengths use decimal digits without a sign or leading zeros (except `/0`). CIDRs may contain host bits; membership uses the prefix. IPv4-mapped IPv6 peers are canonicalized to IPv4. IPv4 peers match IPv4 ranges or IPv4-mapped IPv6 ranges wholly inside `::ffff:0:0/96` (mapped address and prefix >= 96); other IPv6 ranges never trust IPv4 peers.
- Only a trusted socket peer can supply the client IP. One header field uses its rightmost comma-separated IP, which the immediate proxy must append or overwrite. Missing headers, repeated header fields, a non-text value or an invalid rightmost IP fall back to the socket peer. Earlier comma-separated values are ignored, even if invalid. An untrusted peer's entire header is ignored.
- Compose runs exactly one of `--profile caddy` (HTTPS) or `--profile nginx` (HTTP). Only proxy + app join `edge`; only app + DB join `backend`. The app has no published port by default. `FUKULOW_EDGE_PREFIX` (default `172.30.94`) derives the edge subnet `<prefix>.0/29`, gateway `<prefix>.1`, fixed proxy IP `<prefix>.2`, app IP `<prefix>.3` and dynamic allocation range `<prefix>.4/30`; change this one value to move them together. Dynamic containers cannot take the proxy or app IP. Compose trusts exactly `<prefix>.2`, never the gateway or subnet, and sets `x-forwarded-for` itself.
- For opt-in local debugging, add a temporary Compose override with `services: {app: {ports: ["127.0.0.1:8080:8080"]}}` and pass it with `-f compose.yml -f /path/to/debug.yml`. The published-port peer is untrusted; forwarded headers cannot select a budget. Remove the override afterward. Health checks normally use the selected proxy.
- Upgrade existing deployments: set a random `FUKULOW_SETUP_TOKEN` before `docker compose up`; missing/empty fails interpolation before container recreation and leaves the running stack and volume intact. Existing Accounts and sign-in are unaffected; the token only gates setup, but remains required after setup. The default `127.0.0.1:8080` publication is gone; move host health probes to the proxy or use the debug override above. Existing `.env` values for `FUKULOW_TRUSTED_PROXIES` and `FUKULOW_CLIENT_IP_HEADER` are ignored by Compose. If Docker reports a subnet overlap, set `FUKULOW_EDGE_PREFIX` to three octets of a free private IPv4 subnet (for example `172.29.193` for `172.29.193.0/29`) and recreate the stack; never widen trusted proxies to resolve it.
- `node --test scripts/compose-security.test.ts` checks both configurations; `node scripts/check-compose-security.ts` builds an isolated stack for each profile, testing token setup, sign-in, spoofing over proxy, untrusted backend and published debug-port paths, restart and retained setup. It ignores deployment `.env`, uses disposable values/ports/volumes, and cleans up its own resources. Both it and `check-compose-restart.ts` choose random per-run private edge prefixes in separate ranges; `CHECK_EDGE_PREFIX` can select a known free test subnet. `CHECK_COMPOSE_IMAGE` can reuse a locally built image for the security check.

## Database deployment and upgrade (#194 B)
- Keep `fukulow` as the migration owner. The one-shot Compose `migrate` service uses the same image with `fukulow-server migrate`; only it and DB receive owner credentials. App depends on `service_completed_successfully` and receives only the `fukulow_app` URL. Standalone/dev must run the matching migration command separately with an owner URL; migration commands do not serve HTTP or require setup/proxy settings.
- App startup only reads `public._sqlx_migrations`. Missing history, missing/extra/different versions, checksum differences or any failed row stop startup before listening; it never repairs or migrates. Migration lock waits remain bounded to 5 seconds, including SQLx's advisory lock; failure requires an operator retry of the one-shot service.
- Before applying migrations, the migration command requires `fukulow_app` to exist; otherwise it exits with instructions to run `migrate roles`, leaving the schema untouched.
- `fukulow_app` is LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, NOREPLICATION, NOBYPASSRLS, with no ownership or role memberships in either direction (no role may be a member of `fukulow_app` either). It gets CONNECT, public-schema USAGE, table SELECT/INSERT/UPDATE/DELETE, sequence USAGE and only SELECT on migration history. In the application database it has no CREATE, TEMP, TRUNCATE or trigger-change rights; other databases retain their own PUBLIC privileges. Default privileges apply the same DML/sequence grants to future objects created by the migration owner; the migration command reapplies the history exception afterward.
- `POSTGRES_APP_PASSWORD` is required by Compose; unset/empty fails closed, never selecting the owner URL. Use a separate URL-safe random value (for example `openssl rand -hex 32`). The role step requires a superuser, as does initdb's Compose owner: before sending the password it transaction-locally suppresses statement/parameter/error-context logging and nested pg_stat_statements tracking, failing closed if settings cannot be changed. It binds/quotes the value as data; PostgreSQL literal-quotes the password utility statement, and role-update diagnostics are suppressed. No password lives in SQL files.
- New volumes run `deploy/init-db-roles.sh` and the shared roles/grants SQL via initdb. Existing volumes do not rerun initdb. Upgrade: take and drill a #198 backup first; set the required setup token (PR A) and new app password in the private deployment environment; build the matching image; stop app/writers; run `docker compose run --rm migrate roles`, then `docker compose --profile caddy up -d` (or nginx). The roles step is idempotent, preserves rows, updates an existing role's password/grants, and rejects ownership/membership instead of reassigning or deleting anything. Keep the same app password on subsequent runs; rotation also requires app recreation. Never remove the volume to resolve an upgrade failure.
- `node scripts/check-db-upgrade.ts` builds the current origin/main image in an isolated temporary directory, populates a disposable volume with Owner, Message and Session, then upgrades it and compares Organizations/Accounts/Members/Messages/Sessions exactly. It tests old-Session access, sign-in, history, restart, privilege denials, #198 backup/drill and restored grants. It never loads deployment `.env`; `CHECK_COMPOSE_IMAGE` may reuse a locally built candidate image. CI runs it after the candidate build.
- #198 restores use `--no-owner --no-acl`, so role GRANTs do not require role creation in the isolated drill. For recovery, run the roles step against the restored database after the deliberate database-name switch, before starting app; this restores ACLs/default privileges without changing data. Follow `docs/workflow.md` §14, including ending restored Sessions and reconciling permissions.

## HTTP availability
- During graceful shutdown, new HTTP API requests return 503 with JSON `ErrorBody` (`error: "shutting_down"`), a jittered `Retry-After` of 1–5 seconds and `Cache-Control: no-store`. This instance is stopping; the outer middleware rejects requests before authentication, extraction or operation admission, including health checks and WebSocket handshakes.
- Clients retry after `Retry-After`, preserving the same `client_message_id` for sends to retain idempotency (C6). Send-admission 503 (`send admission unavailable`) instead rejects one operation because its queue is full or its 30-second admission wait expired; persistence has not started. Projection-admission 503 (`projection admission unavailable`) is also an operation capacity rejection. Both admission responses use the same retry range and no-store policy.

## Real-time sync contract
Behaviour contract for Message delivery. OpenAPI covers only types (REST shapes, `ClientMessage`/`ServerEvent`, close codes); Rust, the web client and a future Kotlin client satisfy this contract independently and need not share an algorithm. Design and review: #91.
Scope of every key and guarantee: one Organization and one Account Session. The idempotency key is `(organization_id, sender, client_message_id)`. Delivery guarantees assume the supported single-process deployment (`docs/decisions.md`).

### Server guarantees (implemented and tested)
Tests are in `server/src/messages/tests.rs` (M), `server/src/realtime/tests.rs` (R) and `web/src/protocol.test.ts` (W).
- For all sends, including non-Replies, Account Session authentication precedes input validation (400/413/415), which precedes organization_unavailable (404) and Channel authorization. Topic, timeline and history GET projection routes keep organization_unavailable (404) before query validation (400); the Reply chain GET validates first.
- S1. seq is the Channel log position: per Channel, starts at 1 and is consecutive with no gaps (a rollback or an idempotent retry consumes no number). Today every seq is a confirmed Message, but the contract does not promise that every seq is a Message creation (later changes may take a position, #160). No order is promised across Channels. Tests: M `concurrent_sends_allocate_unique_consecutive_channel_sequences`, M `failed_send_after_sequence_allocation_leaves_no_gap`, M `concurrent_duplicate_sends_create_one_message_and_consume_one_sequence`, M `concurrent_cross_channel_duplicate_conflicts_without_sequence_gap`.
- S2. For an **accepted** subscription while the Member stays authorized: after `subscribe(channel, after_seq=N)` every confirmed Message with seq > N' is delivered in ascending order with no omissions, where N' = min(N, the Channel's committed high-water seq) (a future cursor is clamped, intended for database restore). Duplicates are possible: at-least-once, not exactly-once. S2 is a correctness guarantee that depends on no single notification: nothing is omitted while the database is reachable and the client stays connected or reconnects. Recovery latency is a measured target (#159), not a contractual bound (database waits, scheduling, replay limits and slow subscribers would break one). Tests: R `replay_pages_handoff_and_reconnect_keep_independent_channel_sequences_without_gaps`, R `concurrent_message_delivery_is_in_channel_sequence_order`, R `out_of_order_publication_fills_committed_gaps_without_duplicate_delivery`, R `malformed_controls_and_future_cursor_do_not_break_subscription_state` (clamp).
- S3. `subscribed(caught_up_seq=K)` is a replay/queued-prefix **handoff watermark**: replay is finished and live delivery follows. It is not "the newest seq now"; Messages committed after the handoff snapshot may still be on their way. Tests: R `replay_pages_handoff_and_reconnect_keep_independent_channel_sequences_without_gaps`, R `malformed_controls_and_future_cursor_do_not_break_subscription_state`.
- S4. Overflow and session end are never silent: 4008 (queue overflow, authorization-query failure, send timeout), 4001 (Account Session ended: Sign in) and 4003 (Organization Membership lost: Organization unavailable) close the socket; the server closes with 1001 (going away) sockets during server shutdown, when they stop answering Pings, or when their write fails because the peer is already gone (timings are in `docs/decisions.md`, #57 item 5); other internal failures may close with 1011. The server does **not** close the socket when a subscription is refused (`channel_not_found`, `subscription_limit` errors) or when a private-Channel Member loses membership after subscribing (delivery to them simply stops). Tests: R `overflow_closes_socket_and_reconnect_replays_every_committed_message`, R `sign_out_closes_idle_and_replaying_sockets_but_leaves_other_sessions_usable`, R `session_expiry_closes_idle_and_replaying_sockets`, R `session_check_database_timeout_at_connect_closes_with_internal_error`, R `live_delivery_rechecks_private_membership_after_subscription` (silence, socket stays open), R `missing_pong_disconnects_idle_websocket` (1001), W `reconnects with backoff after a 1001 idle-timeout close`. No dedicated test: 4008 on authorization-query failure and on send timeout. 4003 closes only that Organization's sockets and is terminal: no reconnect, resubscribe or send retry. Session end and Membership loss have independent scoped signals and one fallback pass every 30 seconds with a 5-second absolute deadline; failed checks close with 1011. No new protected frame starts after the monitor observes loss; a frame already handed to the socket, or whose check raced the commit, may still arrive. Reconnect timing is client policy.
- S5. The same `(organization_id, sender, client_message_id)` returns the same confirmed Message (409 if body or Channel differ), subject to current authorization; an identical retry always succeeds canonically. Topic and reply target join the comparison with P7. `client_message_id` is unique per sender only. Tests: M `committed_send_retry_returns_canonical_message_without_sequence_allocation`, M `reused_client_id_conflicts_on_different_body_or_channel`, M `equal_ids_in_two_organizations_do_not_collide`.
- History pages: `latest` (no cursor) returns the newest Messages visible to its query snapshot (not a response-time watermark), ascending; default 50, max 200; `after_seq`/`before_seq` are exclusive; `has_more` means older Messages for latest/before pages and newer ones for after pages. Test: M `message_pages_are_bounded_exclusive_ascending_and_directional`.

Guarantee scope: for an accepted subscription while the Member stays authorized (single process), at-least-once, ascending within the Channel, no omissions. Convergence after reconnect is an end-to-end property of the server together with a client that satisfies C1-C10, not a server-only guarantee. Not guaranteed: order across Channels, exactly-once, immediacy while disconnected (filled after reconnect), delivery after the Member loses access (private Channel loss stops delivery; Organization Membership loss closes with 4003), and convergence after a database restore whose history has already grown past the client's old cursor (see C8).

### Client rules
Implemented by the TypeScript client (`web/src/protocol.ts` pure protocol, `web/src/sync.ts` controller, Svelte adapters on top) and checked by the shared `contract/realtime` client fixtures, which run against the protocol and through the controller transports and timers, plus the tests listed in `docs/invariants.md`. Any other client (for example Kotlin later) must satisfy the same fixtures. Client-side scope: replacing the session clears and fences the previous session's client state, so its Messages and pending sends never appear in the new session.
- C1. Deduplicate Messages by (channel, seq).
- C2. Resume cursor = the highest seq confirmed gap-free from a trusted base.
  - Bootstrap while a Channel is uninitialized: fetch the `latest` page, take its highest seq as base B (0 only if that page is empty), then subscribe with `after_seq = B`; Messages committed in between are replayed. B is never a maximum chosen from concurrent ack/echo records (those are buffered and merged). Once initialized, a refreshed or stale `latest` page never moves the cursor over a gap or backwards; an intentional reset is C8.
  - The cursor advances only through unfiltered streams (live, replay, unfiltered pages); a projection page (P1) never moves it. Afterwards the cursor advances only through seq contiguous with it: a live event with seq = cursor + 1, a replay continuing from the cursor, or a history page requested with `after_seq = cursor` (if live traffic advanced the cursor meanwhile, merge the response's still-contiguous suffix).
  - A page that is internally consecutive but not adjacent to the cursor, and every `before_seq` page, extends the window only. Example: cursor 100, receive 102 then 101: the cursor stays 100 until 101 arrives, then becomes 102.
  - An HTTP ack alone never advances the cursor. A server-confirmed record buffered from an ack may count toward contiguity when a live event, replay or `after_seq = cursor` page advances the cursor (example: cursor 100, buffered ack 102, live 101: the cursor becomes 102). The cursor never passes a missing seq. The order of ack and live arrival may differ: an ack arriving after the live event it follows need not advance the cursor at once, which is safe, and reconnect replay (C4) converges to the same state.
- C3. Gap detection and gap filling are separate decisions. A held seq above cursor + 1 is a gap. Wait briefly for reordering (the grace period is a controller parameter, not part of the contract); fill (`after_seq = cursor`) only if the gap persists. A gap at or below `caught_up_seq` K of a completed `subscribed` is not explained by replay and is filled at once; a gap above K may still be in flight and follows the grace period. Never issue overlapping fills for the same range; coverage by a request in flight is cleared on success and on failure, and failed fills back off. A fill continues page by page until the gap is closed. The cursor never passes a gap.
- C4. On reconnect every watched Channel is resubscribed from its C2 cursor; races between history and live converge by C1 and C3. 4001 means Sign in for the Account; 4003 means Organization unavailable (C10). Neither reconnects. 1001 (Ping timeout, write failure or server shutdown), 1011 and abnormal closes reconnect with backoff. After 4008, reconnect with backoff before any history fill, with bounded retries on repeated overflow. A pre-connect handshake failure never implies 4003: use the REST check in C10. No other close code may reuse these meanings.
- C5. A pending send is resolved when an ack, echo or **any fetched history page (including older pages)** holds a Message with the same Channel, sender (the signed-in Member) and `client_message_id`. A Message missing from one page is not evidence that the send failed; a pending Message outside the loaded window is resolved by the same-key resend (C6). The confirmed Message always comes from the server record; local optimistic content never replaces it, and later ack/echo/history copies merge by (channel, seq) with the server record winning.
- C6. While a send outcome is unknown (network error, timeout, lost ack) resend with the same `client_message_id`. Definite refusals (400/403/404/409/413/415) are not resent; 401 means Sign in. A late 401 from a request that a history-generation change (C8) invalidated (clamp C8, unwatch or unavailable C9) still means Sign in when it comes from the same session; a 401 from a replaced Account Session is ignored. This includes an Organization switch or C10 terminal state: a late 401 from the same Account Session still means Sign in for the whole Account. A late failure or timeout never resurrects a pending entry already settled by echo, ack or history.
- C7. Another sender's identical `client_message_id` is a different Message.
- C8. Cursor clamp recovery: compare `caught_up_seq` with the `after_seq` **sent for that subscription**. If K < sent after_seq, the server's history is older than the client's (database restore): invalidate that Channel's confirmed window and cursor, fence stale async results by generation, and re-bootstrap (C2). Release the old server subscription at once, including when the Channel is unwatched before re-bootstrap finishes. Send state survives: definite failures stay failed, unknown outcomes stay resendable with the same `client_message_id`, a send invalidated with the old generation becomes unknown and its late result (other than 401, see C6) changes nothing, and a send started in the new bootstrap generation stays active and follows C5/C6. Clamp never resends automatically. Lowering the cursor alone is not enough. **Scope limit:** only a restored Channel that is behind the cursor is detected. A restored history that has already grown past the old cursor cannot be detected with today's API; a history-generation identifier in history/subscription responses is deferred until needed, and the end-to-end "convergent after reconnect" property excludes that case.
- C9. A refused subscription (`channel_not_found`, `subscription_limit`) or an ordinary 403/404 on history (other than organization_unavailable, C10) is terminal for that Channel until the user acts (select again, Sign in again): it is not a sequence gap, is never retried in a loop, and the UI shows the Channel as unavailable. A Channel access-loss event is owned by #149 (S4, C9, OpenAPI, fixtures).

- C10. Organization Membership loss is terminal for that Organization until explicit user re-selection. Re-selection (including after Invite acceptance) calls GET /api/v1/orgs/{org}/me with the current Account Session before opening any socket or loading Channels. Success starts fresh Organization sync state; organization_unavailable remains terminal, and network/5xx shows a retry action without automatic re-check. Re-selection never revives old pending sends or stale work. An open socket closing with 4003, or a REST 404 with `organization_unavailable`, marks it unavailable, fails its pending sends, and stops automatic reconnect, resubscribe and send retry. Other Organizations' sockets, subscriptions, Messages and pending sends remain unaffected; the user can switch Organizations. A browser cannot inspect a refused WebSocket handshake: after a handshake failure call GET /api/v1/orgs/{org}/me. Only `organization_unavailable` establishes Membership loss; 401 ends the Account Session everywhere, and network errors/5xx reconnect with backoff. Origin rejection has a different code and is never Membership loss. Switching Organizations closes the old socket and fences its Messages, ACKs, send completions, REST responses and timers. A late 401 from the same Account Session still means Sign in everywhere; a 401 from a replaced Account Session is ignored. An old Organization's unavailable response affects only that Organization.

### Topic, Reply and Unread projections (owners #137 Topics server, #138 Topics web, #139 Replies server, #140 Replies web, #142 Unread)
Topic server projections (#137) and opt-in web projection controllers/selectors (#138) are implemented and tested; Topic UI integration remains pending. The four client Topic projection fixtures run at the controller layer. Reply server behavior (#139) runs in delivery fixtures and Rust tests. Opt-in Reply chain controllers/adapters (#140 logic) and nine client controller fixtures are implemented; Reply panel UI remains pending after #222. Unread server behavior (#142) is implemented and tested; Unread client runtime work remains planned. The three Unread fixtures stay `proposed`, validated and skipped by production client runners, and also execute against a test-only reference merge. S1-S5 and C1-C10 keep holding; Topic and Reply Messages are ordinary Channel log positions.
- P1. Topic and Reply Messages travel in the same Channel stream with `topic_id` and reply target. Topic-filtered, main-timeline and Reply-chain pages are projection pages: they extend a projection window only, never move the cursor and never count toward contiguity (C2). Gap fill is always unfiltered, so Messages a view hides are never a gap (C3).
- P2. Main-timeline page. A Message without Topic is at its `seq`; a Topic line is at `position_W(T)` = max `seq` of T's Messages with `seq` <= W. The first page returns `as_of_seq` = W read under the #135 barrier, taken before the query snapshot is fixed so the read sees every `seq` <= W. Later pages pass W and return the state as of W; order and the exclusive continuation boundary apply after `position_W`, never to a position moved by later activity. Messages are immutable, so the state is derived from Messages with `seq` <= W: no server snapshot, no retention period for W.
- P3. W is a page anchor. It bootstraps the cursor (C2) only when the Channel has no sync state yet, and only from an initial response of the current history generation (C8); an established cursor is never moved to W. Page/stream overlap is removed by C1 and one line per Topic at its newest position. A C8 clamp discards W and all projection state; a stale page never revives an unavailable Channel (C9); C6's same-session late 401 is unchanged.
- P4. Summary merge. A page's summary fields (position, latest Message, `message_count`) are as of W. Per Topic the client keeps the as-of-W baseline and its live Messages with `seq` > W (deduped by C1): count = `count_W` + those Messages, position = max(baseline position, newest live `seq`). A Message with `seq` <= W never changes a baseline. A Topic seen only live has no count until a summary fetch gives it a baseline. Of two baselines the larger W wins and the rule is re-applied.
- P5. Whatever is posted while paging, no Topic with a Message <= W is missing from the pages and none is shown twice; activity after W arrives through the stream and moves its line. Cost is not claimed here: #137 measures a page with many Topics moved after W against a latency target and, on a miss, asks the maintainer (e.g. `snapshot_expired` with refetch); no limit is added silently. `snapshot_expired` is required anyway once Messages can change (#160).
- P6. Reply chain = the root and all its descendants, in the root's Channel; a Reply takes its parent's Topic (the client cannot choose it). Fetch is paged and bounded (exclusive continuation, `has_more`); Reply-chain pages are projection pages (P1). A bounded response is no claim of bounded traversal cost (#139).
- P7. A send names its Topic by `topic_name`, never `topic_id`. Retry (S5) also compares the normalized Topic `name_key` (#137) and the reply target: the same send intent returns the canonical Message; a different Topic or reply target returns 409. Responses and events carry `topic_id`.
- P8. Unread. The Channel read position covers Messages without Topic; each Topic has its own read position for its Messages. Main-timeline Unread = other senders' Messages without Topic with `seq` > the Channel position; Topic Unread = other senders' Messages of that Topic with `seq` > its position; the Channel badge = main-timeline Unread + the sum of its Topic Unread. Viewing the main timeline moves only the Channel position, viewing a Topic only that Topic's position. Positions are monotonic (`max`) and clamped to the Channel's latest committed `seq`. Own Messages never count; sending moves no position. Initial position: the latest committed `seq` when the Member gains access to the Channel (existing Members: the latest `seq` when Unread is introduced; a re-grant restarts at the new grant's latest `seq`). A current-revision Channel read position exists if and only if the active Member can see that Channel in the same Organization, for every Role. Role, grant, visibility and activation changes delete positions only when access is lost; continuous access preserves Channel and Topic positions. Guest public access requires a current explicit grant. Other devices converge by refetch on reconnect. Examples: hidden Topic Messages stay unread after viewing the main timeline; a Member's own sends never become Unread; a stale update from another device cannot move a position back; after reconnect the refetched positions replace local ones only by `max`. The client keeps each scope's REST count baseline and adds only other senders' Message events with `seq` > `as_of_seq` and > that scope's position, deduplicated by (channel, seq) (C1), regardless of arrival before or after the REST response. Events at or below `as_of_seq` are already covered. Within the same access generation, Channel and Topic positions only advance, so counts at equal `as_of_seq` are non-increasing with read progress. Of two Channel baselines the larger `as_of_seq` wins; at equal `as_of_seq`, the larger Channel `read_seq` wins; at equal `as_of_seq` and `read_seq`, the smaller `unread_count` and `main_unread_count` win. A stale response never raises these counts. Losing access drops the entry; a regrant starts a new access generation with a baseline at the latest committed `seq`. This follows from existing server behavior and requires no server change. Reapply the live suffix to the winning baseline.

Unread REST (#142): `PUT /api/v1/orgs/{org}/channels/{id}/read` and `.../topics/{topic_id}/read` accept `{read_seq}` (nonnegative) and return the persisted `{read_seq}`. Fetching history alone changes no position; clients explicitly mark the viewed scope. Channel lists return per-Channel `as_of_seq`, `read_seq`, `main_unread_count` and `unread_count` (the badge). `as_of_seq` is the latest committed Channel `seq` visible in the same read-only REPEATABLE READ snapshot as the positions and counts (0 if no Message); both counts include exactly the eligible Messages with `seq` <= `as_of_seq`. It is independent of `read_seq` and includes own and already-read Messages. Topic summaries, including timeline Topic lines, return the current Member's `read_seq` and `unread_count` bounded by their enclosing `as_of_seq`; summary positions/counts remain W-relative (P2/P4). All responses are `no-store`; refetch Channel/Topic lists after reconnect. A Topic created after a grant inherits that grant's initial position, so its first Message can be unread.

If a visible Channel's position is missing through data corruption or an administrative write, list reads suppress only that Channel's Unread: return the snapshot's committed Channel `seq` (0 if empty) and zero counts. Topic projections use their enclosing `as_of_seq` and zero Unread. This read-only fallback never marks history unread or creates a position; Channel lists log the inconsistency for repair. Mark-read returns 404 until the position is repaired.

Reply API (#139, implemented): POST `/api/v1/orgs/{org}/channels/{id}/messages` accepts optional UUID `reply_to` (omitted/null = non-Reply). The parent must already be committed in that Organization/Channel; #140 waits for a confirmed Message id. Replies inherit the parent's Topic and root. Every canonical Message (ACK, history, Topic/timeline projections, live, replay) carries nullable `reply_to` and `reply_root_id`; non-Replies have both null. A Reply with non-null `topic_name` gives 400 `reply_topic_not_allowed`. Account Session authentication precedes validation; validation precedes Organization/Channel authorization, then canonical retry comparison (409 for changed body/Channel/Topic intent/parent), then parent lookup (uniform 404 `reply_parent_not_found` for unknown, foreign or not-yet-committed parents). Refusals consume no seq or Topic count and publish nothing.

GET `/api/v1/orgs/{org}/channels/{id}/messages/{message_id}/chain?after_seq&limit` accepts the root or any descendant and returns `{ root_id, messages, has_more }`: root plus all descendants including siblings, ascending seq, no depth cap. `after_seq` defaults to 0 and is exclusive; limit defaults to 50, range 1..=200. Malformed/negative after_seq or invalid limits give 400 ErrorBody before Channel authorization. Unknown/foreign-Channel/foreign-Organization anchors give identical 404 `reply_chain_not_found`; authorization retains `channel not found` / `organization_unavailable`. `has_more` means further matching chain Messages after the page; continue from its last seq. Each page waits out unresolved COMMIT via watermark admission/barrier, releases both, then snapshots authorization and data together. It includes only that committed prefix, without a persistent W across pages; later appends appear on subsequent requests. Admission refusal gives 503 with Retry-After. Chain pages never move the sync cursor.

Reply web logic (#140): `createReplySync` owns one open chain per watched Channel, optionally composed over `createTopicSync` so a confirmed Message from a Topic uses the same stream. Open with a confirmed Message; the adapter exposes anchor, root, inherited Topic, sorted canonical Messages, pending sends, loading/error/hasMore and unavailable state. Continue exclusively after the last page record, independently of live appends. Merge pages and Channel ACK/echo/replay records by Message id; `reply_root_id` identifies membership even without the parent. Pages only settle matching own sends (C5), never cursor/gap evidence. Sends target a confirmed chain Message through sync with a new client id and no Topic intent; retry preserves the id/body/parent (C6). Session replacement and close are ordered before sync teardown; clamp/unwatch/C9/C10 discard the chain and fence stale reads. Only a current read's ordinary 403/404 causes C9; reply_chain_not_found fails only the chain; same-session late 401 and organization_unavailable retain C6/C10 meaning after timeout. Components, composer UI and panel integration follow separately.

### Observable vocabulary (used by `contract/realtime` fixtures)
Fixtures assert only what a client shows or emits to the outside; they do not name internal state, functions or timers. Any implementation (Rust, TypeScript, a future Kotlin client) with different internals satisfies the contract if these observations hold.
- **Channel state** (the contract's synchronisation state of a watched Channel, asserted by fixtures as `observe.channels[*].state`; it is not a UI display state): `loading` = initial sync not finished: this covers having no base yet and also having a base (from the initial history page) while the subscription is not yet confirmed; `ready` = initial sync finished, i.e. a base is established and the server has confirmed the subscription (`subscribed`), so the cursor is trusted. Establishing a base alone does not make a Channel `ready`. How a Channel is shown during a reconnect is not fixed by this contract unless a fixture asserts it; `unavailable` = terminal for that Channel until the user acts (C9). Not to be confused with the web client's `TimelineState.status`, a UI-facing, implementation-specific state: `TimelineState.status === 'ready'` means only that a base (cursor) is established and Messages can be shown; it does not require the `subscribed` confirmation. So a Channel can be `TimelineState.status === 'ready'` while its Channel state is still `loading` (for example after a reconnect, before the new subscription is confirmed), and the two need not agree at any moment. Fixtures verify the Channel state only and never equate it with `TimelineState.status`.
- **Organization state**: available, or terminal `unavailable` after 4003 or REST-confirmed `organization_unavailable` (C10).
- **Session state**: `signed_in`, or `sign_in_required` after a 401 or a 4001 close (C6, S4).
- **Effect categories** (what a client emits outward, as classified by contract tests): HTTP requests, WebSocket connect/subscribe/unsubscribe, and `wait` effects classified as `reorder_grace` (C3 grace before filling a gap), `fill_backoff` (pause after a failed fill, C3) and `reconnect_backoff` (pause before reconnecting, C4). These are categories of observable behaviour only: how long a wait is, how it is scheduled, and whether the implementation has a timer at all are not part of the contract. A `membership_check` effect is the C10 REST check after a handshake failure; a fixture marked `layer: controller` observes it and runs only against a whole client (TypeScript: the controller), not a pure protocol layer.
- **Unread vocabulary** (P8, production client proposed for #143): `load_unread` requests a Channel baseline (`fetch_unread`); `unread_result` delivers its `as_of_seq`, position and counts; `observe.channels[*].unread` asserts the selected baseline and merged counts. All three client Unread scenarios execute against a test-only reference merge, with broken-rule checks, including Topic-only mark-read responses in both orders: equal `as_of_seq`/Channel `read_seq` keeps smaller counts within one access generation (loss drops the entry; regrant starts at committed `seq`); they remain `proposed` for production client runners until #143. Server delivery `unread` steps assert the REST baseline and counts and run today.
- **Reply projection vocabulary** (P1, P6-P7, controller-layer fixtures): open a chain from a confirmed Message, fetch forward chain pages with root id and exclusive after_seq, observe root/Topic/visible Messages/has_more, and send with reply_to.
- **Topic projection vocabulary** (P1-P5, implemented in controller-layer fixtures): a Message's Topic label, Topic-filtered and main-timeline pages (`as_of_seq` = W), the main-timeline lines a client shows (one per Message without Topic, one per Topic with its merged position and count) and a Topic view's Messages.

Capabilities (per-operation `{allowed, reason?}` on resources) are not part of this contract; they are added only when the UI must show whether an operation is possible in advance (see `docs/decisions.md`).
