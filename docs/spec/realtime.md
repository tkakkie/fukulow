## Real-time sync contract

Each client implements this observable contract independently (#91). Keys and delivery are scoped to one Organization and Account Session unless explicitly Account-wide or Member-wide. Delivery assumes the supported single process ([deployment decision](../decisions/process.md)).

### Web display retention (#308)

| Store | Bound |
|---|---|
| Main projection, active Topic, single Reply panel | 400, 300, 200 records respectively. Main/Topic caps are shared across Channels. Release inactive Topic history. |
| Sync bodies | 400 per watched Channel, five inactive LRU slots of 50 each, 600 total. With projection bodies, at most 1,500 records. Pending intent, including Reply root, has its own lifetime. |
| Evidence | 400 Topic ranges per projection window, 400 Reply availability ranges, 400 disjoint cursor ranges, 400 retired-identity fence ranges, 1,100 Unread records/presented sequences per Channel/visit and 400 Unread Topic identities per Channel. Mutation version evidence holds 1,500 identities per watched Channel and the inactive body-slot limit otherwise. |

- Page older main history exclusively at fixed-W positions. If trimming moves the entire window beyond W, refresh W with a first page before continuing below the retained anchor, which that page must preserve. Latest navigation replaces the window. Topic history continues exclusively with `before_seq` or refreshes latest. Topic-list baselines cannot establish main continuation.
- Requested Reply history has priority over cached recent bodies. Newer availability is separate. Continue from returned page creation positions only, and restart from the chain start for older history. Selecting a cached same-chain Message, current anchor or root keeps window, continuation, live evidence and pending sends without a read. Open an uncached descendant from `max(0, anchor.created_seq - 25)`, even on first open, preserving older navigation to the omitted prefix. Explicit latest drains forward pages. Projection reads leave the cursor alone. Eviction fences superseded reads under C6/C8–C10.
- Checkpointing evidence makes summaries/counts unresolved where W or read-position coverage is insufficient. A fresh authoritative baseline is required. Stale responses and duplicate replay cannot restore authority. Forgotten cursor ranges retain a scalar recovery target and require unfiltered refetch. Keep one proven first-Unread identity per visit when evicting Unread evidence. Mark an evicted prefix only with retained projection/body coverage, and refetch counts after a successful mark if subtraction evidence is missing.
- Each version-evidence retirement creates a distinct fence for older reads. Exact creation ranges fence only covered, unheld identities in stream/ACK state and coalesce exactly. A fresh authorized snapshot can admit them. Exceeding 400 ranges invalidates the confirmed window and requests an authoritative first page while preserving the cursor. A scalar boundary then requires a fresh snapshot for unheld stream/ACK records at or below it. Each rejection fences pre-existing history requests and starts fresh latest. Latest clears the scalar boundary only over the covered range, retaining it below the first Message if older history exists. A complete page clears it. Exact fences still apply to unheld records, and held identities accept higher versions. Reclaiming metadata never advances a position.
- Mount viewport rows plus overscan and measure attached rows only. Paging preserves the visible anchor. A full unpinned window holds its bodies and offers arrivals through latest navigation. Keyboard navigation uses retained Message IDs and mounts before focus, with Composer fallback for a removed focus target. First-Unread entry may page past the body cap and restores the visit marker when its retained row mounts.

### Server guarantees (implemented and tested)

**Error order.** All sends authenticate before input validation (400/413/415), then Organization availability (404 `organization_unavailable`) and Channel authorization, then send limiting (429) and admission (503). Topic, timeline and history GETs check Organization availability before query validation (400). Reply-chain GET validates after Session authentication, before Organization and Channel denials.

- S1. Channel log `seq` starts at 1 and is gapless within the Channel. A rollback or canonical retry consumes nothing. Create carries current Message state. Move takes one position for the whole Reply chain. Cross-Channel order is unspecified.
- S2. For an accepted subscription while authorized, deliver every event after `min(after_seq, committed high-water seq)` in ascending order. Clamp future cursors for restore recovery. Duplicates are possible. No single notification is required to recover all events while the database is reachable and the client stays connected or reconnects. Disconnected clients recover on reconnect. End-to-end convergence requires C1–C10. Recovery latency is a measured target with no contractual deadline (#159). Restore requires C8's rotation.
- S3. Register live before replay, replay through the committed watermark and hand off the queued prefix before `subscribed.caught_up_seq`. That value acknowledges completion of that handoff. Later commits may still be in flight.
- S4. Close with 4008 for queue overflow, authorization-query failure or send timeout, 4001 for Account Session end, 4003 for Membership loss in that Organization only, and 1001 for shutdown, missed Pings or peer write error. Other internal failures can close with 1011. Refused subscriptions (`channel_not_found`, `subscription_limit`) leave the connection open. C4/C6/C10 govern reconnect and Sign in.
  - Session and Membership signals are independently scoped. One fallback every 30 s has an absolute 5 s deadline and fails closed with 1011 on failed/overdue checks. After observed loss, no new protected frame starts. A handed-off frame may finish, and a check racing commit may authorize a frame until observation.
  - Effective Channel loss (private grant, Guest public grant, or demotion to Guest without grant) sends `channel_access_lost` with only `channel_id`, discards queued/fetched frames and retires only that subscription. It leaves the socket open. Fallback compares durable grant lifetimes, including remove/re-grant, and detects a missed signal within 30 s + 5 s, with the same fail-closed behavior. Loss observation serializes with first frame handoff. Write failure uses ordinary reconnect and fresh subscribe authorization.
  - Per-Account (all Organizations/Sessions) or global socket cap, or an empty Account control budget, refuses the upgrade with 503 `socket_limit` and Retry-After 1–5 s. Charge every client text/binary frame, including malformed controls, to both budgets before database access. Exceeding either closes 4029. Reconnect preserves the Account budget. [Admission bounds and timings](../decisions/realtime.md#admission-and-timeouts).
  - Duplicate subscribe never replays or changes cursor, regardless of `after_seq`. Unsubscribe first to replay. Without `history_generation` the charged no-op does no queries. With it, check current access and epoch first. Stale epoch retires that subscription and returns `history_generation_changed`. Inaccessible Channels keep their ordinary denial.
- S5. After current authorization, a committed retry keyed by `(organization_id, sender, client_message_id)` returns the same Message identity and current state. A changed byte-exact body, Channel, normalized Topic intent or reply target conflicts with 409 (P7). Another sender's key is independent.
- S6. One token bucket per (Organization, Member) spans Channels and Sessions (default burst/initial balance 10, refill 1/s, tunable in [deployment](deployment.md)). A new send pays one token, normally without refund. Exhaustion returns 429 `send_rate_limited` with whole-second Retry-After until the next token (at least 1 s), with no queue, seq or publication. Pre-limiter refusals, 429s and committed canonical retries cost nothing. Canonical retry rechecks access and resolves before limiting and admission.
  - Identical in-flight requests wait and inherit the leader's canonical result or failure, including paid admission refusal, without executing or paying. A differing intent on that key waits too, then runs/pays independently and never inherits that failure. A confirmed failure's retry pays.
  - One same-intent retry within 120 s of a charged unknown COMMIT is free. Database failures without definite rollback remain unknown. A retry ending before persistence retains the credit. A free retry earns none.
  - Parent lookup is inside persistence. An empty bucket gives 429 before lookup. With a token, a missing parent gives 404 `reply_parent_not_found` and spends the token.
  - At most 16 waiters per key, 10,000 tracked keys and 100,000 buckets. Reclaim only full buckets. At any cap, return uncharged 503 with Retry-After 1 s and no admission slot.
- **Event pages.** Continue exclusively from the last event envelope `seq`, ascending (50 default, 200 maximum). Each page takes the #135 committed watermark, reads positions only from `channel_log` and hydrates current state as replay does. Missing/unhydratable positions or unsupported kinds fail closed. Access and log/state share a fresh snapshot and history GET error precedence.
- **Message history.** Latest is ascending over the newest Messages visible in the query snapshot, with 50 default and 200 maximum. Creation continuations are exclusive. `has_more` means older for latest/before and newer for after. See #160 for fixed-W expiry.

### Client rules

Session replacement clears and fences all old Messages and sends. The [shared fixtures](../../contract/realtime) check the same behaviour for every client, including controller-layer effects. Web boundary rules and delta ownership are in [AGENTS.md](../../AGENTS.md#boundaries).

- C1. Deduplicate events by (Channel, seq) and Message state by (message_id, version). Higher complete versions replace, equal versions are idempotent and lower versions are ignored across ACKs, replay and all history/projections. M1 still governs Mention name freshness. Tombstones discard bodies, excerpts and Mentions permanently.
- C2. Resume from the highest gap-free event position. An uninitialized Channel trusts the latest snapshot's explicit `(history_generation, as_of_seq)` as its base, even with no visible Messages. Subscribe with that generation and base so intervening commits replay. Concurrent ACK/echo records are buffered and merged, and never choose the base.
  - Extend coverage through contiguous live/replay events or an unfiltered event page requested at the cursor. If live advanced meanwhile, merge the still-contiguous suffix. A nonadjacent event page or creation-ordered history/projection page extends only its window. A refreshed/stale latest never moves an established cursor back or across a gap.
  - An ACK alone never advances the cursor or proves coverage through its version. Its immutable Create position may contribute to the buffered contiguous suffix when live/replay or the event page advances the cursor. An ACK arriving after predecessor delivery need not move it immediately. Reconnect converges.
- C3. Held evidence above cursor + 1 detects a gap. Allow a brief controller-configured reorder grace unless the gap is at/below a completed `subscribed.caught_up_seq` (fill immediately). Fill persistent gaps with unfiltered event pages from the cursor until closed. Never overlap fills for the same range. Release request coverage on success/failure and back off after failure. Never pass a gap.
- C4. Reconnect resubscribes each watched Channel from C2, with C1/C3 merging concurrent history/live. 4001 and 4003 are terminal under C6/C10. 1001, 4029, 1011 and abnormal close reconnect with backoff, reset only by `subscribed`. 4008 reconnects with backoff before any fill, with bounded retries on repeated overflow. Handshake failures, including 503 `socket_limit`, use the C10 check before backoff. Other codes cannot reuse these meanings.
- C5. ACK, echo or any history page, including older pages, settles a pending send only by matching Channel, signed-in sender and `client_message_id`. Page absence proves nothing. For an off-window unsettled send use C6. Confirmed state comes from the server and merges by C1, never local optimistic content.
- C6. Unknown outcomes (network, timeout or lost ACK) resend with the same key. A 429 retries the entire original request with that key after Retry-After (whole seconds >=1, default 1 s for absent/invalid), re-arming on each 429. Settlement, discard, access loss, Organization switch and Session replacement cancel waits. Definite 400/403/404/409/413/415 refusals never retry. A current-Session 401 always means Sign in across the Account, even after clamp, generation change, unwatch, C9, Organization switch or C10. Ignore replaced-Session 401s. No late failure/timeout resurrects a settled send.
- C7. An identical key from another sender identifies a different Message.
- C8. If `caught_up_seq` is below the `after_seq` sent on that subscription, release it immediately (even if unwatch interrupts recovery), discard that Channel's confirmed/projection state and cursor, fence old work and bootstrap again. A changed Organization `history_generation` applies the reset to every held Channel regardless of cursor magnitude. Release all subscriptions, discard windows, cursors, anchors, mutation/version floors and counts, fence async work and start a fresh socket first. For either reset, definite failures stay failed, unknowns keep their keys, sending/throttled attempts become unknown and their timers stop. Ignore old completions except C6's 401. New sends follow C5/C6. Clamp never auto-resends. Rotate before restore/cutover traffic using the #160 owner command. Startup never rotates.
- C9. Refused subscribe (`channel_not_found`, `subscription_limit`), ordinary history 403/404 (except `organization_unavailable`), or current `channel_access_lost` makes only that Channel unavailable until explicit user action. Show it as unavailable and stop retries and automatic reads, including gap recovery. Keep pending text as failed with only discard. Late completions cannot revive it, with C6's same-Session 401 intact. Reconnect with backoff if a pending/retired subscription makes loss attribution ambiguous while watched (#120). Ignore unwatched loss, and use A9's Organization-level revoke for list/badge removal.
- C10. 4003 or REST 404 `organization_unavailable` stops reconnect/resubscribe/send retry for that Organization and fails its pending sends. Other Organizations remain usable and unaffected. On any browser handshake failure, check GET `/api/v1/orgs/{org}/me` with the current Session. Only `organization_unavailable` establishes Membership loss. 401 ends the Account Session, and network errors/5xx reconnect with backoff. Origin rejection is distinct. Explicit re-selection (including after Invite acceptance) checks `/me` before sockets or Channel loads. Success starts fresh state without old sends/work. Continued unavailability stays terminal and network/5xx offers user retry without auto-check. Switching closes the old socket and fences Messages, ACKs, REST, sends and timers. An old Organization's unavailable result affects only it. Late 401 follows C6.
  - After Organization switch, a late definite refusal restores submitted text to that Organization's draft only if it remains unedited and unsettled. ACKs and unknown outcomes never restore drafts. Ending/replacing the Account Session clears all drafts and fences old controllers' writes.

### Topic, Reply and Unread projections (owners #137 Topics server, #138 Topics web, #139 Replies server, #140 Replies web, #142 Unread)

S/C rules apply unchanged. Topic and Reply sync logic is implemented. Topic UI and Reply panel integration remain pending. See [fixture vocabulary](#observable-vocabulary-used-by-contractrealtime-fixtures) for Unread fixture status and web request serialization.

- P1. Topic and Reply Messages share the Channel stream with their Topic and reply target. Topic-filtered, main and Reply pages extend only their projection window. They supply neither cursor advance nor contiguity evidence. Fill gaps with unfiltered event pages (C2–C3).
- P2. Main lines for Messages without Topic use `created_seq`. A Topic line's position at W is the maximum creation position at or below W of that Topic's nondeleted Messages. First-page W (`as_of_seq`) is captured under #135 before fixing the read snapshot. Continue at fixed W with exclusive W-relative positions, regardless of later Creates. Derive state from Messages created by W while W is at least mutation floor M. Otherwise return `snapshot_expired` for the entire page (#160). No server paging snapshot is retained.
- P3. Only an initial current-generation response can bootstrap an uninitialized Channel at W (C2). Deduplicate overlap and show one line per Topic at its newest position. C8 clamp discards W and projections. C9 cannot be undone by a stale page. Same-Session 401 retains C6.
- P4. A Topic summary's latest Message, position and count are as of W. Take the larger-W baseline and add only unique live Messages created after it. Position is the maximum of baseline and live positions. A live-only Topic needs a summary before its count is known.
- P5. Concurrent Creates cannot omit or duplicate a Topic with a Message at/below W during paging. The stream moves its line for later activity. Mutation can expire the window. #137 owns cost.
- P6. A Reply chain comprises the root and all descendants in the root's Channel. A Reply inherits its parent's Topic and root. The client cannot choose a Topic. Chain responses page exclusively with `has_more` (P1). Bounded responses do not bound traversal cost (#139).
- P7. Send names its Topic only via `topic_name`. Canonical intent compares normalized `name_key` and parent (S5). Changed Topic or parent returns 409. Responses/events carry `topic_id`.
- P8. Other senders' nondeleted Messages count when their creation position exceeds the read position of their scope: Channel position for no Topic, own Topic position otherwise. The Channel badge sums main and Topic counts. Explicitly mark the viewed scope. A mark advances only that scope's position, which is monotonic and clamped to the latest committed event seq. Sending or fetching alone moves nothing. Positions start at access-time committed seq (at feature introduction for existing access), including on re-grant. Later Topics inherit the grant's initial baseline.
  - Every active Member has a current-revision Channel position exactly where they have effective access in that Organization, for every Role. Guest public access requires a current grant. Grant, Role, visibility and activation changes preserve Channel and Topic positions through continuous access and delete them on loss.
  - Channel list `as_of_seq` is the latest committed event in the same read-only REPEATABLE READ snapshot as access, positions and counts (0 when empty). Count eligible creations through this watermark, which is independent of `read_seq` and includes own/already-read Messages. Topic counts and positions use their enclosing W, with W-relative summary fields. Replies use inherited scope. Mark-read returns the persisted position. Read/count responses are no-store.
  - Merge each authoritative REST baseline with the unique other-sender suffix above both its W and its read position, regardless of arrival order. Within a single access lifetime, compare Channel tuples by larger W then larger Channel position, then keep the smaller main and aggregate counts at an equal pair. Reapply the suffix. At equal W counts cannot rise through read progress. Refetch Channel/Topic baselines on reconnect, merging positions by max, and on cross-device read notices (A9). After confirmed Topic mark, refetch the Channel aggregate. Loss drops the entry. Re-grant starts a fresh generation.
  - A missing position on a visible Channel (corruption/admin write) suppresses only that Channel's Unread. Channel lists log the inconsistency and use the committed snapshot seq. Topic projections use enclosing W. Both return zero counts without creating a position or marking history unread. Mark-read returns 404 until repaired.

**Reply send and history (#139/#140).** Use a confirmed parent id. Canonical ACK/history/projection/live/replay carry `reply_to` and `reply_root_id`. Both are null for non-Replies. Non-null Topic intent on a Reply returns 400 `reply_topic_not_allowed`. Preserve send error precedence, resolve canonical retries before lookup, and uniformly return 404 `reply_parent_not_found` for absent, foreign or uncommitted parents (S6 governs the token charge). Refusals consume no seq or Topic count and publish nothing.

A root or descendant anchor returns the entire chain (including siblings), ascending by creation position, no depth cap, with the full `chain_version` (highest member version through W, including tombstones). Malformed cursors/limits get 400 `ErrorBody` before Channel authorization. Unknown, foreign-Channel and foreign-Organization anchors get the same 404 `reply_chain_not_found`. Ordinary `channel not found` and `organization_unavailable` denials remain. Each page waits under watermark admission/barrier, releases both before the fresh authorization/data snapshot, and returns generation and W. Admission refusal is 503 with Retry-After. Omitted W starts a fresh prefix. Continue from the last returned creation position, retaining W until a fresh first page or latest navigation. Live appends do not change continuation.

Web opens one chain per watched Channel from a confirmed Message, using the same stream even from Topic view. Expose anchor/root/inherited Topic, ordered canonical and pending Messages, loading/errors, availability and continuation. Merge pages and ACK/echo/replay by Message id. Root id determines membership even when the parent is unloaded. Page settlement obeys C5 without cursor evidence. New sends use fresh ids, confirmed targets and no Topic intent. Retry keeps id/body/parent. Close Reply state before closing sync, and reset Reply state before replacing the sync Session. Clamp, unwatch and C9/C10 discard the chain and fence old reads. Only a current ordinary 403/404 triggers C9. `reply_chain_not_found` fails just the panel. Same-Session late 401 and `organization_unavailable` retain C6/C10 after timeout.

**Reply counts (#409).** Batch 1–100 ids before deduplication, returning rows sorted by requested id. Visible roots or descendants share a full live descendant total (excluding root), even if the root body is absent. Omit unknown, foreign-Channel and foreign-Organization ids identically. Apply history's public/private/DM/Guest access rules (including no Owner/Admin private or DM bypass). Session auth precedes 400 input errors, then 404 Organization/Channel denials, then watermark admission (503 with Retry-After). Responses are no-store and change no state, positions or cursor.

Check access before admission and again in the fresh read-only snapshot after the #135 barrier captures W. Both anchors and aggregate Replies are bounded by W. Aggregate once per distinct root using the chain index, independent of pages/Topic/root body. A root tombstone keeps its identity/root metadata and live Reply count. Whole-chain Move preserves root and total. #287 owns Delete and its client reconciliation. Formal p95 verification remains open.

- Track a root while any chain body is loaded or its panel is open. Paging does not alter counts. Take the larger W baseline plus unique live creation ids above it, including fill and arrivals during the read. An unmodified root Create or accepted ACK above the established cursor seeds exact `(created_seq, 0)`. Newer baselines win. Mutations require a baseline covering their version. The client consumes Move invalidation. Delete follows in #287.
- At 400 evidence records per Channel, make oldest roots unresolved, clear evidence, retain their highest forgotten seq as floor, advance the root generation and refetch after the batch. Reject baselines below the floor and replay at/below it. Untracking discards baseline/evidence/floor and fences old work. Gap, reconnect and C8 recovery do the same before refetching tracked roots. C9/C10, unwatch and Session teardown clear/cancel without refetch. Scope each request by Session, Organization, Channel, watch lifetime, recovery and root generations. Late success cannot restore authority. Same-Session 401 follows C6.
- Requests carry the current Organization generation and wait for a cursor and confirmed subscription. Generation mismatch invokes C8 instead of installing counts. `snapshot_expired` clears affected baseline/evidence/floor and retries each root once. Other successes cannot renew its budget. Repeated expiry leaves that root unresolved. Omitted/mismatched roots also retry once and then await untracking or sync recovery. Count reads/expiry never move the cursor.
- Recoverable resets preserve Retry-After and accumulated backoff. Individual root invalidation/eviction fences just its ticket. Only whole-Channel recovery or timeout cancels the batch. Batch order is open panel first, then loaded main, Topic and Reply members in encounter order.

### Message changes (#160, partly implemented)

#515 implements the log, versioned Message/receipt, coordinated wire migration, explicit bootstrap, Organization generation and fixed-W expiry. #141 stage 1 adds the Move writer and body-free event, advances the mutation floor and serves current Topic, Reply and count projections. Clients advance the cursor and refetch stale projections. The panel action follows in #141 stage 2. Edit/Delete writers remain with #287. Proposed behaviour below keeps the S/C/P guarantees. [Design rationale](../decisions/messages.md#channels-and-messages)

#### Positions, state and convergence

- Messages owns `channel_log`, keyed by `(organization_id, channel_id, event_seq)`, with operation identity and stable Message/chain-root identity. Only the log supplies event positions. Current Message rows retain immutable creation position, version and deletion marker. History continues exclusively by creation position, which becomes sparse. Edits and moves never renumber. Missing or unhydratable replay state closes 1011 on subscribe or latches gap-recovery failure.
- All kinds use the transactional Channel counter and separate #135 exclusive-writer/shared-reader barrier. State, log, receipt, Mentions and Topic projections commit atomically. Rollback, duplicate or successful no-op allocates no position and publishes nothing. Preserve authorization locks through COMMIT, detached completion, ambiguous-COMMIT recovery and bounded admission. New tables require `organization_id NOT NULL`, scoped keys/FKs, tenant RLS and runtime grants. State deletion cannot cascade away log positions or receipts.
- Replay/live/fill use `(history_generation, channel_id, event_seq)` within the Organization. S2–S4 apply, including register-before-replay, queued handoff before ack, fresh page/delivery authorization, post-COMMIT publication and bounds measured in events.
- **Adopted current-state reconciliation.** Operation e supplies coverage. Authorized hydration supplies current state at version v, which may exceed e or W. Return both, or send invalidation and hydrate via bounded current-state pages. Never claim state as of e/W or omit positions for changed/deleted Messages. As-it-was replay would require retaining past bodies and Topics and was rejected.
- Compare versions only within the same Channel/history generation. C1 gates complete body/Topic/deletion state. A mutation establishes a minimum version: withhold affected stale state and refetch until complete state meets the floor. A partial patch cannot discard an older event needed for complete state. Mention names retain M1 freshness even at equal version. C2 separates coverage from versions and bootstraps explicitly, including positive W with no visible Messages. Retain C6–C10 fences and #308 evidence bounds, including fencing earlier reads on evidence retirement and requiring a fresh authorized snapshot for readmission.

#### Event, Message and operation identity

- S1/C2, `subscribed.caught_up_seq`, gap fill and replay use envelope `seq`. History continuations, P2 lines and Unread/Mention eligibility use immutable `created_seq`. Fixed-W, bootstrap and expiry compare committed event W. Message version is the last event affecting it. Create sends current state (live creation version equals creation seq. Replay may hydrate a later version or tombstone).
- Move uses the Message event envelope with kind `move`: root, source and destination Topics, operation identity and mutation version, without bodies. Create replay still carries current state, including a newer Topic/version or a body-free tombstone. Edit/Delete events remain with #287 (proposed: body-free, Delete carries a terminal tombstone). Hydrate current state as above.
- Edit/Move/Delete carry client-generated UUID `operation_id` and `expected_version`. Receipt key `(organization_id, actor_member_id, operation_id)` binds kind, target, intent digest and outcome (version or tombstone), committing with the mutation. Reauthorize and resolve it before stale-precondition checks. Same intent returns outcome plus current version/tombstone and allocates/publishes nothing. Changed kind/target/intent returns 409. A new key evaluates the version under serialization. An identical intent under a new key conflicts or, if it matches current state, succeeds as a no-op and allocates nothing. Proposed distinct Edits against one version yield one success and one conflict.
- Operation receipts are authoritative for 7 days, longer than client retry windows (#515). Bounded background batches reclaim expired rows. Expired retry is a new request. Its stale `expected_version` must lead to conflict or no-op without silently reapplying work. Move retains a same-Topic receipt for canonical retries. #287 owns Edit/Delete no-op and error policy.
- Original sends have a durable SHA-256 intent verifier for S5's key, kept as long as the Message and fixed at insert. Compare byte-exact body, Channel, normalized Topic intent and reply target independently of mutable state, without revalidating original Mention acceptance. After reauthorization, resolve matching retries before limiter/admission to the original id/creation position and current state or tombstone. Different intent returns 409. Retention policy below governs verifier representation/erasure, without requiring plaintext.

#### Delete, history generations and request identity

- Delete is terminal for that id. Preserve a body-free tombstone with scoped identity, creation position, deletion version and reference metadata (parent/root/Topic). Edit, Move and original-send retry cannot undelete. Root deletion preserves descendants and the visible chain. Proposed deleted-root placeholder is excluded from Message/Topic counts. Reply-first survives. Delete-first Reply acceptance is open (#287).
- Fresh history/snapshots/replay/search suppress deleted body, excerpt and Mentions, including historical Create/Edit positions, while replay covers each position with body-free state or invalidation. Version search indexing, remove deleted content and check current deletion/access before serving stale hits. Remove Unread/Mention contributions and repair projections atomically. After observing Delete, clients discard content and fence older events/pages/ACKs. Frames/reads already in flight may arrive before observation.
- One random UUID `history_generation` per Organization, initialized by migration for old Organizations and DB default for new ones. Runtime grants exclude INSERT/UPDATE of that column. After restore or destructive/incompatible replacement, run `fukulow-server rotate-history-generation <Organization UUID | --all>` over the owner connection **before traffic**, even if counters have surpassed old cursors. Startup never rotates. Local request/access epochs remain separate. C8 governs the reset.
- Discover the epoch on initial history/projection, count or Channel/DM-list response, including empty history. Create supplies it through canonical Message state and `subscribed` carries it. Once known, send it with cursor/W or other generation-aware requests. An old generation returns 409 `history_generation_changed`. Subscribe sends an `error` with that code and Channel id, keeping the socket open. The client restarts the socket under C8. Message/Reply history and main/Topic-list pages accept fixed event W. Preserve Session/input/Organization precedence. Check generation after current Channel authorization, before expiry or page data, in one fresh snapshot. Denied Channels disclose neither floor nor generation.
- `snapshot_expired` uses the messages-owned `channel_message_sequences.mutation_seq` floor M (initially 0, advanced only by Edit/Move/Delete). Client-fixed W<M returns 409 `ErrorBody` `snapshot_expired` with no partial page. Refresh only that window once. Repeated fresh expiry surfaces an error. Preserve other windows, send state, cursor and epoch. After #135, server-selected W, auth, generation/floor and data share one fresh snapshot, so initial pages cannot expire. Mutations supersede affected history/Topic anchors (initially a Channel-wide floor is allowed). Fenced older in-flight responses cannot revive them. Creates preserve fixed-W paging. Indexed current summaries cannot substitute for an older W. Expiry is separate from a gap or generation reset.

#### Move, Edit and projections (#141 / #287)

- **Move server implemented (#141 decision 4).** A root or descendant anchor selects its whole chain within one Organization/Channel, including tombstones. Preserve IDs, creation positions, parent links, root identity (root's `reply_root_id` remains null. Each Reply uses the parent's root or the parent) and deletion markers. One event position becomes every member's version. `expected_version` covers the full chain. A stale version returns 409 `version_conflict`. Chains over 1,000 Messages including tombstones return 409 `chain_too_large`. The destination is exactly one of an existing `topic_id` or a `topic_name` joining or creating that normalized name. Moving to the current Topic is a successful no-op that allocates no position and stores only its canonical receipt.
- Reply creation, Move and Delete share Channel writer serialization after Member/grant, #142 and #135 locks. Check committed parent existence before the barrier without waiting for uncommitted parents, then reread Topic/root/deletion state under serialization.
