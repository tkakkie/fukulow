## Real-time sync contract
Behaviour contract for Message delivery. OpenAPI covers only types (REST shapes, `ClientMessage`/`ServerEvent`, close codes); Rust, the web client and a future Kotlin client satisfy this contract independently and need not share an algorithm. Design and review: #91.
Scope of every key and guarantee: one Organization and one Account Session. The idempotency key is `(organization_id, sender, client_message_id)`. Delivery guarantees assume the supported single-process deployment (`docs/decisions/process.md`).

### Web display retention (#308)
Display bodies have separate lifetimes from cursor, gap, Topic-count and Unread evidence. Named limits are 400 main projection records, 300 active Topic Messages and 200 Reply Messages. Inactive Topic history is released. Sync retains at most 400 Messages per watched Channel and 50 per inactive Channel in five LRU slots, with a shared 600-record sync budget. Main and Topic budgets are shared across Channels; together with the single panel, display stores retain at most 1,500 records. Pending sends retain their intent independently of body limits, including the Reply root. Per-message bookkeeping is bounded separately: 400 Topic range objects per projection window, 400 Reply availability ranges, 400 disjoint cursor ranges, and 1,100 Unread records/presented sequences per Channel/active visit. Unread scope identities retain at most 400 Topics per Channel.

Older main pages continue exclusively at retained W-relative positions with fixed W. If live trimming leaves the entire window beyond W, a fresh first page establishes a new W before continuing below the retained anchor; its records do not replace that anchor. Latest navigation replaces the window with a fresh first page. Topic history uses before_seq or a fresh latest page. Topic-list-only baselines never establish main continuation. Cached recent Replies cannot displace a requested history page; newer availability is separate. Reply continuation uses only returned page seqs, never live appends; older Reply history restarts at the chain start. Selecting a cached same-chain Message, the current anchor or the root preserves the window, continuation, live evidence and pending sends without a read. An uncached descendant opens one page from `max(0, anchor.seq - 25)`, including on a fresh open; an omitted prefix remains available through older history. Explicit latest navigation drains forward pages. These projection reads never advance the sync cursor. Eviction fences superseded reads, preserving C6/C8-C10.

When evidence is checkpointed, summaries/counts with insufficient W or read-position coverage are unresolved until an existing baseline endpoint refreshes them; stale responses and duplicate replay cannot restore lost authority. Forgotten cursor ranges keep a scalar recovery target and require unfiltered refetch. Unread eviction keeps one proven first-Unread identity for the visit and requires retained projection/body coverage before marking an evicted prefix; successful marks refetch counts when subtraction evidence is missing. No position is advanced merely to reclaim metadata.

Each timeline mounts viewport rows plus overscan, measuring attached rows only. Paging preserves the visible anchor; an unpinned full window holds its bodies while arrivals remain available through latest navigation. Keyboard navigation uses retained Message IDs, mounting a destination before focus. A removed focus target falls back to the Composer. First-Unread entry can page beyond the body cap; a visit's marker is restored whenever its retained row is mounted again.

### Server guarantees (implemented and tested)
Tests are in `server/src/messages/tests.rs` (M), `server/src/realtime/tests.rs` (R) and `web/src/protocol.test.ts` (W).
- For all sends, including non-Replies, Account Session authentication precedes input validation (400/413/415), which precedes organization_unavailable (404) and Channel authorization, then the send limit (429), then admission (503). Topic, timeline and history GET projection routes keep organization_unavailable (404) before query validation (400); the Reply chain GET validates first.
- S1. seq is the Channel log position: per Channel, starts at 1 and is consecutive with no gaps (a rollback or an idempotent retry consumes no number). Today every seq is a confirmed Message, but the contract does not promise that every seq is a Message creation (later changes may take a position, #160). No order is promised across Channels. Tests: M `concurrent_sends_allocate_unique_consecutive_channel_sequences`, M `failed_send_after_sequence_allocation_leaves_no_gap`, M `concurrent_duplicate_sends_create_one_message_and_consume_one_sequence`, M `concurrent_cross_channel_duplicate_conflicts_without_sequence_gap`.
- S2. For an **accepted** subscription while the Member stays authorized: after `subscribe(channel, after_seq=N)` every confirmed Message with seq > N' is delivered in ascending order with no omissions, where N' = min(N, the Channel's committed high-water seq) (a future cursor is clamped, intended for database restore). Duplicates are possible: at-least-once, not exactly-once. S2 is a correctness guarantee that depends on no single notification: nothing is omitted while the database is reachable and the client stays connected or reconnects. Recovery latency is a measured target (#159), not a contractual bound (database waits, scheduling, replay limits and slow subscribers would break one). Tests: R `replay_pages_handoff_and_reconnect_keep_independent_channel_sequences_without_gaps`, R `concurrent_message_delivery_is_in_channel_sequence_order`, R `out_of_order_publication_fills_committed_gaps_without_duplicate_delivery`, R `malformed_controls_and_future_cursor_do_not_break_subscription_state` (clamp).
- S3. `subscribed(caught_up_seq=K)` is a replay/queued-prefix **handoff watermark**: replay is finished and live delivery follows. It is not "the newest seq now"; Messages committed after the handoff snapshot may still be on their way. Tests: R `replay_pages_handoff_and_reconnect_keep_independent_channel_sequences_without_gaps`, R `malformed_controls_and_future_cursor_do_not_break_subscription_state`.
- S4. Overflow and session end are never silent: 4008 (queue overflow, authorization-query failure, send timeout), 4001 (Account Session ended: Sign in) and 4003 (Organization Membership lost: Organization unavailable) close the socket; the server closes with 1001 (going away) sockets during server shutdown, when they stop answering Pings, or when their write fails because the peer is already gone (timings are in `docs/decisions/realtime.md`, #57 item 5); other internal failures may close with 1011. The server does **not** close the socket when a subscription is refused (`channel_not_found`, `subscription_limit` errors) or when a private-Channel Member loses membership after subscribing (channel_access_lost notifies them and delivery stops). Tests: R `overflow_closes_socket_and_reconnect_replays_every_committed_message`, R `sign_out_closes_idle_and_replaying_sockets_but_leaves_other_sessions_usable`, R `session_expiry_closes_idle_and_replaying_sockets`, R `session_check_database_timeout_at_connect_closes_with_internal_error`, R `live_delivery_rechecks_private_membership_after_subscription` (event, socket stays open), R `missing_pong_disconnects_idle_websocket` (1001), W `reconnects with backoff after a 1001 idle-timeout close`. No dedicated test: 4008 on authorization-query failure and on send timeout. 4003 closes only that Organization's sockets and is terminal: no reconnect, resubscribe or send retry. Session end and Membership loss have independent scoped signals and one fallback pass every 30 seconds with a 5-second absolute deadline; failed checks close with 1011. No new protected frame starts after the monitor observes loss; a frame already handed to the socket, or whose check raced the commit, may still arrive. Reconnect timing is client policy. Channel access loss (private grant, Guest public grant, or Role-to-Guest without a grant) sends `channel_access_lost` with only `channel_id`, discards queued/fetched frames and retires that subscription while the socket stays open. The single fallback also compares durable grant lifetimes, including remove/re-grant; it observes lost signals within 30 s + 5 s and fails closed on an overdue/failed pass. An observed loss and first frame handoff serialize; only a frame already in flight may finish. Failed outbound writes use normal socket failure/reconnect; the new subscribe then decides access. Socket limits (#196 A, values in `docs/decisions/realtime.md`): an upgrade over the per-Account cap (all its Organizations and Account Sessions) or the global socket cap, or from an Account whose control-frame budget is empty, is refused with 503 `socket_limit` and a 1-5 s Retry-After before the socket opens. Every client text or binary frame (subscribe, unsubscribe, malformed) is charged to the connection's and the Account's control-frame budget before any database access; over budget closes with 4029, and reconnecting does not reset the Account's budget. A subscribe for a Channel already subscribed on the connection is a charged no-op whatever its after_seq: no authorization query, watermark, replay or reply; to replay again, unsubscribe first. Tests: R `the_account_cap_counts_every_organization_and_session_and_refuses_with_503`, R `over_budget_frames_close_4029_before_any_database_access`, R `a_duplicate_subscribe_is_a_charged_no_op_whatever_its_after_seq`.
- S5. The same `(organization_id, sender, client_message_id)` returns the same confirmed Message (409 if body or Channel differ), subject to current authorization; an identical retry always succeeds canonically. Topic and reply target join the comparison with P7. `client_message_id` is unique per sender only. Tests: M `committed_send_retry_returns_canonical_message_without_sequence_allocation`, M `reused_client_id_conflicts_on_different_body_or_channel`, M `equal_ids_in_two_organizations_do_not_collide`.
- S6. Send limit (#306): one token bucket per (Organization, Member), shared across that Member's Channels and Account Sessions: burst 10, refill 1 per second, initial balance 10. A new send that passes the limiter costs one token, normally not refunded. Over the limit the response is 429 `send_rate_limited` with `Retry-After` = whole seconds until the next token, at least 1; nothing is queued, sequenced or published. No charge: a 429; a rejection before the limiter (401, 400/413/415, `organization_unavailable`, Channel authorization 404); a retry of a committed `client_message_id` (answered canonically before the limiter and admission, after an access recheck); a request identical to one in flight (it waits and settles with it: the canonical Message if that execution committed, otherwise the same failure, including a 503 admission refusal after the leader paid; it never executes or pays itself; a request reusing the key with a different Channel, body, Topic name or reply target waits too, but never inherits that failure: it then runs and pays like a new send); one retry of the same request after a charged COMMIT whose outcome is unknown, within 120 s (database failures other than a definite rollback count as unknown; a retry that ends before persistence keeps it, a free retry earns none). The operator may change burst and refill (`docs/spec/deployment.md`); nothing else changes. A retry after a confirmed failure is charged. Order: `reply_to` is checked inside the send transaction, so an empty bucket gives 429 and, with tokens, a missing parent gives 404 `reply_parent_not_found` and spends the token. Tracking is bounded: at most 16 waiters per key and 10,000 tracked keys, and at most 100,000 buckets; only a refilled (full) bucket is reclaimed. At any cap the request gets 503 with `Retry-After: 1`, uncharged, taking no admission slot. Tests: M `one_member_is_throttled_while_another_sends_and_the_bucket_refills`, M `exhausted_bucket_keeps_denials_as_denials`, M `concurrent_identical_requests_consume_one_token_and_share_one_message`, M `a_charged_leader_refused_by_admission_charges_its_identical_waiters_nothing`.
- History pages: `latest` (no cursor) returns the newest Messages visible to its query snapshot (not a response-time watermark), ascending; default 50, max 200; `after_seq`/`before_seq` are exclusive; `has_more` means older Messages for latest/before pages and newer ones for after pages. Test: M `message_pages_are_bounded_exclusive_ascending_and_directional`.

Guarantee scope: for an accepted subscription while the Member stays authorized (single process), at-least-once, ascending within the Channel, no omissions. Convergence after reconnect is an end-to-end property of the server together with a client that satisfies C1-C10, not a server-only guarantee. Not guaranteed: order across Channels, exactly-once, immediacy while disconnected (filled after reconnect), delivery after the Member loses access (Channel access loss stops delivery and sends channel_access_lost; Organization Membership loss closes with 4003), and convergence after a database restore whose history has already grown past the client's old cursor (see C8).

### Client rules
Implemented by the TypeScript client (`web/src/protocol.ts` pure protocol, `web/src/sync.ts` controller, Svelte adapters on top) and checked by the shared `contract/realtime` client fixtures, which run against the protocol and through the controller transports and timers, plus the tests listed in `docs/invariants.md`. Any other client (for example Kotlin later) must satisfy the same fixtures. Client-side scope: replacing the session clears and fences the previous session's client state, so its Messages and pending sends never appear in the new session.
- C1. Deduplicate Messages by (channel, seq).
- C2. Resume cursor = the highest seq confirmed gap-free from a trusted base.
  - Bootstrap while a Channel is uninitialized: fetch the `latest` page, take its highest seq as base B (0 only if that page is empty), then subscribe with `after_seq = B`; Messages committed in between are replayed. B is never a maximum chosen from concurrent ack/echo records (those are buffered and merged). Once initialized, a refreshed or stale `latest` page never moves the cursor over a gap or backwards; an intentional reset is C8.
  - The cursor advances only through unfiltered streams (live, replay, unfiltered pages); a projection page (P1) never moves it. Afterwards the cursor advances only through seq contiguous with it: a live event with seq = cursor + 1, a replay continuing from the cursor, or a history page requested with `after_seq = cursor` (if live traffic advanced the cursor meanwhile, merge the response's still-contiguous suffix).
  - A page that is internally consecutive but not adjacent to the cursor, and every `before_seq` page, extends the window only. Example: cursor 100, receive 102 then 101: the cursor stays 100 until 101 arrives, then becomes 102.
  - An HTTP ack alone never advances the cursor. A server-confirmed record buffered from an ack may count toward contiguity when a live event, replay or `after_seq = cursor` page advances the cursor (example: cursor 100, buffered ack 102, live 101: the cursor becomes 102). The cursor never passes a missing seq. The order of ack and live arrival may differ: an ack arriving after the live event it follows need not advance the cursor at once, which is safe, and reconnect replay (C4) converges to the same state.
- C3. Gap detection and gap filling are separate decisions. A held seq above cursor + 1 is a gap. Wait briefly for reordering (the grace period is a controller parameter, not part of the contract); fill (`after_seq = cursor`) only if the gap persists. A gap at or below `caught_up_seq` K of a completed `subscribed` is not explained by replay and is filled at once; a gap above K may still be in flight and follows the grace period. Never issue overlapping fills for the same range; coverage by a request in flight is cleared on success and on failure, and failed fills back off. A fill continues page by page until the gap is closed. The cursor never passes a gap.
- C4. On reconnect every watched Channel is resubscribed from its C2 cursor; races between history and live converge by C1 and C3. 4001 means Sign in for the Account; 4003 means Organization unavailable (C10). Neither reconnects. 1001 (Ping timeout, write failure or server shutdown), 4029 (control-frame budget), 1011 and abnormal closes reconnect with backoff; only a confirmed `subscribed` resets it. A 503 `socket_limit` refusal is a handshake failure (C10 REST check, then backoff). After 4008, reconnect with backoff before any history fill, with bounded retries on repeated overflow. A pre-connect handshake failure never implies 4003: use the REST check in C10. No other close code may reuse these meanings.
- C5. A pending send is resolved when an ack, echo or **any fetched history page (including older pages)** holds a Message with the same Channel, sender (the signed-in Member) and `client_message_id`. A Message missing from one page is not evidence that the send failed; a pending Message outside the loaded window is resolved by the same-key resend (C6). The confirmed Message always comes from the server record; local optimistic content never replaces it, and later ack/echo/history copies merge by (channel, seq) with the server record winning.
- C6. While a send outcome is unknown (network error, timeout, lost ack) resend with the same `client_message_id`. A 429 is throttled: automatically retry the entire original request with the same client_message_id after Retry-After (whole seconds >= 1; missing/invalid means 1 s), never earlier; each repeated 429 re-arms with its new delay. Settlement (C5), discard, access loss (C9/C10), Organization switch and session replacement cancel the wait. Definite refusals (400/403/404/409/413/415) are not resent; 401 means Sign in. A late 401 from a request that a history-generation change (C8) invalidated (clamp C8, unwatch or unavailable C9) still means Sign in when it comes from the same session; a 401 from a replaced Account Session is ignored. This includes an Organization switch or C10 terminal state: a late 401 from the same Account Session still means Sign in for the whole Account. A late failure or timeout never resurrects a pending entry already settled by echo, ack or history.
- C7. Another sender's identical `client_message_id` is a different Message.
- C8. Cursor clamp recovery: compare `caught_up_seq` with the `after_seq` **sent for that subscription**. If K < sent after_seq, the server's history is older than the client's (database restore): invalidate that Channel's confirmed window and cursor, fence stale async results by generation, and re-bootstrap (C2). Release the old server subscription at once, including when the Channel is unwatched before re-bootstrap finishes. Send state survives: definite failures stay failed, unknown outcomes stay resendable with the same `client_message_id`, a sending or throttled send invalidated with the old generation becomes unknown (cancel any retry wait) and its late result (other than 401, see C6) changes nothing, and a send started in the new bootstrap generation stays active and follows C5/C6. Clamp never resends automatically. Lowering the cursor alone is not enough. **Scope limit:** only a restored Channel that is behind the cursor is detected. A restored history that has already grown past the old cursor cannot be detected with today's API; a history-generation identifier in history/subscription responses is deferred until needed, and the end-to-end "convergent after reconnect" property excludes that case.
- C9. A refused subscription (`channel_not_found`, `subscription_limit`) or an ordinary 403/404 on history (other than organization_unavailable, C10) is terminal for that Channel until the user acts (select again, Sign in again): it is not a sequence gap, is never retried in a loop, and the UI shows the Channel as unavailable. A `channel_access_lost {channel_id}` event has the same C9 effect for its current subscription: pending text stays as failed with only discard available, retries and automatic reads stop, and late completions cannot revive it. A same-session late 401 still ends the Account Session. While the Channel is watched, if a pending/retired subscription makes attribution ambiguous, reconnect with backoff (#120); explicit re-selection tries again. Loss events for unwatched Channels are consumed and ignored; list and badge removal for any Channel follows `channel_access_revoked` (A9, #307).

- C10. Organization Membership loss is terminal for that Organization until explicit user re-selection. Re-selection (including after Invite acceptance) calls GET /api/v1/orgs/{org}/me with the current Account Session before opening any socket or loading Channels. Success starts fresh Organization sync state; organization_unavailable remains terminal, and network/5xx shows a retry action without automatic re-check. Re-selection never revives old pending sends or stale work. An open socket closing with 4003, or a REST 404 with `organization_unavailable`, marks it unavailable, fails its pending sends, and stops automatic reconnect, resubscribe and send retry. Other Organizations' sockets, subscriptions, Messages and pending sends remain unaffected; the user can switch Organizations. A browser cannot inspect a refused WebSocket handshake: after a handshake failure call GET /api/v1/orgs/{org}/me. Only `organization_unavailable` establishes Membership loss; 401 ends the Account Session everywhere, and network errors/5xx reconnect with backoff. Origin rejection has a different code and is never Membership loss. Switching Organizations closes the old socket and fences its Messages, ACKs, send completions, REST responses and timers. A late 401 from the same Account Session still means Sign in everywhere; a 401 from a replaced Account Session is ignored. An old Organization's unavailable response affects only that Organization.

Draft lifetime exception to C10's data fence: a late definite refusal after an Organization switch restores submitted text to that Organization's draft only if it remains unedited and unsettled. ACKs and unknown outcomes never restore it. Ending or replacing the Account Session clears all drafts and fences every old controller's draft writes.

### Topic, Reply and Unread projections (owners #137 Topics server, #138 Topics web, #139 Replies server, #140 Replies web, #142 Unread)
Topic server projections (#137) and opt-in web projection controllers/selectors (#138) are implemented and tested; Topic UI integration remains pending. The four client Topic projection fixtures run at the controller layer. Reply server behavior (#139) runs in delivery fixtures and Rust tests. Opt-in Reply chain controllers/adapters (#140 logic) and nine client controller fixtures are implemented; Reply panel UI remains pending after #222. Unread server behavior (#142) is implemented and tested; Unread controllers/adapters (#143 logic) are implemented, and the event/replay fixture runs against the production controller. The reconnect and equal-baseline fixtures remain `proposed`, reference-only for production by maintainer decision (#266): the shared fixtures keep concurrent requests with reverse responses, while the web controller serializes them; production serialization and stale rejection are tested separately. The independent test-only reference merge runs all three fixtures; UI integration remains pending. S1-S5 and C1-C10 keep holding; Topic and Reply Messages are ordinary Channel log positions.
- P1. Topic and Reply Messages travel in the same Channel stream with `topic_id` and reply target. Topic-filtered, main-timeline and Reply-chain pages are projection pages: they extend a projection window only, never move the cursor and never count toward contiguity (C2). Gap fill is always unfiltered, so Messages a view hides are never a gap (C3).
- P2. Main-timeline page. A Message without Topic is at its `seq`; a Topic line is at `position_W(T)` = max `seq` of T's Messages with `seq` <= W. The first page returns `as_of_seq` = W read under the #135 barrier, taken before the query snapshot is fixed so the read sees every `seq` <= W. Later pages pass W and return the state as of W; order and the exclusive continuation boundary apply after `position_W`, never to a position moved by later activity. Messages are immutable, so the state is derived from Messages with `seq` <= W: no server snapshot, no retention period for W.
- P3. W is a page anchor. It bootstraps the cursor (C2) only when the Channel has no sync state yet, and only from an initial response of the current history generation (C8); an established cursor is never moved to W. Page/stream overlap is removed by C1 and one line per Topic at its newest position. A C8 clamp discards W and all projection state; a stale page never revives an unavailable Channel (C9); C6's same-session late 401 is unchanged.
- P4. Summary merge. A page's summary fields (position, latest Message, `message_count`) are as of W. Per Topic the client keeps the as-of-W baseline and its live Messages with `seq` > W (deduped by C1): count = `count_W` + those Messages, position = max(baseline position, newest live `seq`). A Message with `seq` <= W never changes a baseline. A Topic seen only live has no count until a summary fetch gives it a baseline. Of two baselines the larger W wins and the rule is re-applied.
- P5. Whatever is posted while paging, no Topic with a Message <= W is missing from the pages and none is shown twice; activity after W arrives through the stream and moves its line. Cost is not claimed here: #137 measures a page with many Topics moved after W against a latency target and, on a miss, asks the maintainer (e.g. `snapshot_expired` with refetch); no limit is added silently. `snapshot_expired` is required anyway once Messages can change (#160).
- P6. Reply chain = the root and all its descendants, in the root's Channel; a Reply takes its parent's Topic (the client cannot choose it). Fetch is paged and bounded (exclusive continuation, `has_more`); Reply-chain pages are projection pages (P1). A bounded response is no claim of bounded traversal cost (#139).
- P7. A send names its Topic by `topic_name`, never `topic_id`. Retry (S5) also compares the normalized Topic `name_key` (#137) and the reply target: the same send intent returns the canonical Message; a different Topic or reply target returns 409. Responses and events carry `topic_id`.
- P8. Unread. The Channel read position covers Messages without Topic; each Topic has its own read position for its Messages. Main-timeline Unread = other senders' Messages without Topic with `seq` > the Channel position; Topic Unread = other senders' Messages of that Topic with `seq` > its position; the Channel badge = main-timeline Unread + the sum of its Topic Unread. Viewing the main timeline moves only the Channel position, viewing a Topic only that Topic's position. Positions are monotonic (`max`) and clamped to the Channel's latest committed `seq`. Own Messages never count; sending moves no position. Initial position: the latest committed `seq` when the Member gains access to the Channel (existing Members: the latest `seq` when Unread is introduced; a re-grant restarts at the new grant's latest `seq`). A current-revision Channel read position exists if and only if the active Member can see that Channel in the same Organization, for every Role. Role, grant, visibility and activation changes delete positions only when access is lost; continuous access preserves Channel and Topic positions. Guest public access requires a current explicit grant. Other devices converge by refetch on reconnect and, once #307 ships, on `read_position_changed` (A9). Examples: hidden Topic Messages stay unread after viewing the main timeline; a Member's own sends never become Unread; a stale update from another device cannot move a position back; after reconnect the refetched positions replace local ones only by `max`. The client keeps each scope's REST count baseline and adds only other senders' Message events with `seq` > `as_of_seq` and > that scope's position, deduplicated by (channel, seq) (C1), regardless of arrival before or after the REST response. Events at or below `as_of_seq` are already covered. Within the same access generation, Channel and Topic positions only advance, so counts at equal `as_of_seq` are non-increasing with read progress. Of two Channel baselines the larger `as_of_seq` wins; at equal `as_of_seq`, the larger Channel `read_seq` wins; at equal `as_of_seq` and `read_seq`, the smaller `unread_count` and `main_unread_count` win. A stale response never raises these counts. Losing access drops the entry; a regrant starts a new access generation with a baseline at the latest committed `seq`. This follows from existing server behavior and requires no server change. Reapply the live suffix to the winning baseline. The single-scope count formula applies per scope; the Channel aggregate converges by a Channel-list refetch after a confirmed Topic mark-read (no API change).

Unread REST (#142): `PUT /api/v1/orgs/{org}/channels/{id}/read` and `.../topics/{topic_id}/read` accept `{read_seq}` (nonnegative) and return the persisted `{read_seq}`. Fetching history alone changes no position; clients explicitly mark the viewed scope. Channel lists return per-Channel `as_of_seq`, `read_seq`, `main_unread_count` and `unread_count` (the badge). `as_of_seq` is the latest committed Channel `seq` visible in the same read-only REPEATABLE READ snapshot as the positions and counts (0 if no Message); both counts include exactly the eligible Messages with `seq` <= `as_of_seq`. It is independent of `read_seq` and includes own and already-read Messages. Topic summaries, including timeline Topic lines, return the current Member's `read_seq` and `unread_count` bounded by their enclosing `as_of_seq`; summary positions/counts remain W-relative (P2/P4). All responses are `no-store`; refetch Channel/Topic lists after reconnect. A Topic created after a grant inherits that grant's initial position, so its first Message can be unread.

If a visible Channel's position is missing through data corruption or an administrative write, list reads suppress only that Channel's Unread: return the snapshot's committed Channel `seq` (0 if empty) and zero counts. Topic projections use their enclosing `as_of_seq` and zero Unread. This read-only fallback never marks history unread or creates a position; Channel lists log the inconsistency for repair. Mark-read returns 404 until the position is repaired.

Reply API (#139, implemented): POST `/api/v1/orgs/{org}/channels/{id}/messages` accepts optional UUID `reply_to` (omitted/null = non-Reply). The parent must already be committed in that Organization/Channel; #140 waits for a confirmed Message id. Replies inherit the parent's Topic and root. Every canonical Message (ACK, history, Topic/timeline projections, live, replay) carries nullable `reply_to` and `reply_root_id`; non-Replies have both null. A Reply with non-null `topic_name` gives 400 `reply_topic_not_allowed`. Account Session authentication precedes validation; validation precedes Organization/Channel authorization, then canonical retry comparison (409 for changed body/Channel/Topic intent/parent), then parent lookup (uniform 404 `reply_parent_not_found` for unknown, foreign or not-yet-committed parents). Refusals consume no seq or Topic count and publish nothing.

GET `/api/v1/orgs/{org}/channels/{id}/messages/{message_id}/chain?after_seq&limit` accepts the root or any descendant and returns `{ root_id, messages, has_more }`: root plus all descendants including siblings, ascending seq, no depth cap. `after_seq` defaults to 0 and is exclusive; limit defaults to 50, range 1..=200. Malformed/negative after_seq or invalid limits give 400 ErrorBody before Channel authorization. Unknown/foreign-Channel/foreign-Organization anchors give identical 404 `reply_chain_not_found`; authorization retains `channel not found` / `organization_unavailable`. `has_more` means further matching chain Messages after the page; continue from its last seq. Each page waits out unresolved COMMIT via watermark admission/barrier, releases both, then snapshots authorization and data together. It includes only that committed prefix, without a persistent W across pages; later appends appear on subsequent requests. Admission refusal gives 503 with Retry-After. Chain pages never move the sync cursor.

Reply web logic (#140): `createReplySync` owns one open chain per watched Channel, optionally composed over `createTopicSync` so a confirmed Message from a Topic uses the same stream. Open with a confirmed Message; the adapter exposes anchor, root, inherited Topic, sorted canonical Messages, pending sends, loading/error/hasMore and unavailable state. Continue exclusively after the last page record, independently of live appends. Merge pages and Channel ACK/echo/replay records by Message id; `reply_root_id` identifies membership even without the parent. Pages only settle matching own sends (C5), never cursor/gap evidence. Sends target a confirmed chain Message through sync with a new client id and no Topic intent; retry preserves the id/body/parent (C6). Session replacement and close are ordered before sync teardown; clamp/unwatch/C9/C10 discard the chain and fence stale reads. Only a current read's ordinary 403/404 causes C9; reply_chain_not_found fails only the chain; same-session late 401 and organization_unavailable retain C6/C10 meaning after timeout. Components, composer UI and panel integration follow separately.

### Organization activity notices (#307, implemented)
Goal: a Member sees, without reloading, that something changed in any Channel they can see, and sees Channels they gain access to; Message bodies still arrive only for subscribed Channels (S2). Model (maintainer, 2026-11-14): **invalidate and refetch**. REST stays the source of truth for Unread counts, Channel lists and Member lists; a notice carries no Message body and no count, only identifiers and log positions, and tells the client which REST baseline to refetch. Tests: `server/src/realtime/tests/activity.rs`, `server/src/channels/activity.rs`, `web/src/activity.test.ts`, shared activity fixtures and `web/e2e-compose/activity.spec.ts`; invariants link executed checks. #151 reuses these notices for DM activity/read positions and adds an own-Member DM-list invalidation for its separate REST target ([DM E1-E7](dms.md#dm-discovery-and-activity-notices-b4)); #152 adds Mention counts to REST without a new Mention event.

- A1. Registration. Every socket receives its Organization's notices automatically; there is no subscribe frame. After the session check and before reading any client frame, the server registers the socket for `(organization_id, member_id, membership_revision)` and sends `activity_ready`, the first ServerEvent on every socket. The registration is one per socket, bounded by the #196 A socket caps, independent of the 256-subscription cap, and costs no control-frame budget. It ends with the socket.
- A2. Events (all Organization-scoped, JSON tag `type`, snake_case, no other fields than listed):

```json
{"type":"activity_ready"}
{"type":"activity_reset"}
{"type":"channel_activity","channel_id":"<uuid>","seq":1}
{"type":"read_position_changed","channel_id":"<uuid>","topic_id":null,"read_seq":0}
{"type":"channel_access_gained","channel_id":"<uuid>"}
{"type":"channel_access_revoked","channel_id":"<uuid>"}
{"type":"channel_list_changed"}
{"type":"dm_list_changed"}
{"type":"channel_members_changed","channel_id":"<uuid>"}
{"type":"members_changed"}
```

  `seq` is an integer >= 1 (the committed Channel `seq` of the newest Message the notice covers); `read_seq` is an integer >= 0 (the persisted position after the change); `topic_id` is a UUID or null (null = the Channel read position). The ordinary Channel/Member `ServerEvent` variants are implemented in `server/src/realtime.rs`; utoipa and `make api` generate their OpenAPI and TypeScript shapes. No `ClientMessage` variant is added. `channel_access_revoked` is distinct from the existing subscription-scoped `channel_access_lost` (S4, C9), which keeps its meaning unchanged.
  `dm_list_changed` is implemented: #151's own-Member invalidation; its mutation/recipient table is in DM E2. DM activity/read events reuse the Channel id and ordinary event shapes, but target the DM REST list; DM creation/renewal and peer-state changes follow that table instead of the ordinary Channel creation/manager rows below. A DM has no public/private visibility or member-management UI.
- A3. Emitting mutations and recipients. Every mutation-driven recipient is a registered socket in that Organization, with a live Account Session and the current `(member_id, membership_revision)` of an active Member. Evaluate the event-specific predicate after COMMIT: ordinary Channel notices require current Channel access using the fan-out predicate (`channels`); directory notices use A4. The sole Channel-access exception is `channel_access_revoked`: send it only to the still-active, current-revision target whose prior access this mutation removed, proved from the transaction's before/after access state. It carries only that previously accessible Channel's id. A never-authorized socket gets no revocation. This exception grants no ordinary activity or Channel member-list notices. No event crosses Organizations; deactivation/reactivation never delivers to an old Membership revision.

| Mutation (committed) | Event | Recipients |
|---|---|---|
| Message send, including Replies and Topic creation by first Message | `channel_activity {channel_id, seq}` | Members with access to the Channel, except the sender Member (P8: own Messages never count) |
| Channel or Topic mark-read that raises the position (PUT `.../read`) | `read_position_changed {channel_id, topic_id, read_seq}` | Only the same Member's sockets with current Channel access (every Account Session); a no-op `max` emits nothing |
| Channel creation | `channel_access_gained` | Public: every active non-Guest Member. Private: the creator. Never a Guest (no grant exists yet) |
| Grant added (POST `.../members`), target newly gains access | `channel_access_gained` to the target; `channel_members_changed` | Target; Members with access after COMMIT |
| Grant added, target already had access (public non-Guest) | `channel_list_changed` to the target; `channel_members_changed` | Target; Members with access after COMMIT |
| Grant removed or left, target loses access | `channel_access_revoked` to the target; `channel_members_changed` | Target; Members with access after COMMIT |
| Grant removed, access continues (public non-Guest) | `channel_list_changed` to the target; `channel_members_changed` | Target; Members with access after COMMIT |
| Channel manager right changed | `channel_list_changed` to the target; `channel_members_changed` | Target; Members with access to that Channel |
| Role change | target: `channel_access_revoked` per public Channel lost (to Guest without grant) or `channel_access_gained` per public Channel gained (from Guest), plus `channel_list_changed`; `members_changed` (A4); `channel_members_changed` per Channel where the target holds a usable grant | Target; A4 directory recipients; Members with access to each such Channel |
| Member deactivation | `members_changed` (A4); `channel_members_changed` per Channel where the target held a usable grant (captured inside the transaction) | A4 directory recipients; Members with access to each such Channel. The target's sockets close 4003 (S4), unchanged |
| Invite acceptance (activation or reactivation) | `members_changed` (A4) | A4 directory recipients. Reactivation restores no grant, so no Channel event |

  Idempotent no-ops (duplicate current grant, current manager value, current Role), refused requests and proven rollbacks emit no mutation notice. Unknown transaction outcomes follow A5-A6. Not included: Invite creation, password change, revoke-others (S4 4001 already covers it). Any later mutation of a Channel's name, visibility or Topics must add its row here before it ships.
- A4. Member directory notices follow what the recipient may list. `members_changed` goes to every active non-Guest Member, and to a Guest only when the changed Member is that Guest, or holds or held (before or after the COMMIT) a usable grant on a Channel the Guest can access after the COMMIT: the Guest directory rule. A non-member of a private Channel never receives `channel_members_changed` for it. A grant added or removed also sends `members_changed` to Guests with access to that Channel after COMMIT, since their directory may change.

  Independently of other directory recipients and of #294's implementation, a target Guest whose own Channel access changes MUST receive `members_changed`, including loss of its last shared Channel. This is an own-access change, not a notice about an invisible Member; it uses A3's live/current-revision target predicate without requiring continued Channel access. `channel_access_gained` and `channel_access_revoked` also invalidate that target's held Member lists (A9), so coalescing cannot omit the refresh. Member/Channel member-list responses issued before their latest invalidation lose authority immediately (A11); the next REST response may retain Members visible through another shared Channel. No notice names a Member.
- A5. Publication. Mutation notices are published only after confirmed COMMIT by detached work armed before COMMIT (as #57 PR B). Proven rollback/refusal completes the guard without publication; timeout, cancellation, lost COMMIT response or an unclassified COMMIT error is an uncertain outcome, never evidence of rollback. Retain recovery responsibility until a post-outcome snapshot can be obtained (A6/O5); a successful early recovery fetch cannot discharge it. SQLSTATE classification follows `server/src/messages/commit.rs:115`; absence in an outcome lookup proves nothing (#135). A recovery invalidation sent after outcome resolution must authorize recipients afresh; an early `activity_reset` alone is insufficient.

  Hooks take no row locks: recipient queries are non-locking reads after COMMIT, and before-state needed for revocation or directory visibility is captured inside the existing transaction under locks it already holds, preserving #149/#311 lock order. Emitters in `auth` reach Channel predicates through an injected hook (as `RoleChangeGuard`), never a reverse module edge.

  `channel_activity` recipient queries coalesce per Organization and Channel: at most one running query and one pending batch; one batched query per run, no per-recipient SQL. Freeze each batch's committed upper `seq` and sender eligibility before starting its authorization snapshot; later commits queue another batch, never raise the in-flight batch's `seq`. For each recipient, retain the maximum covered `seq` sent by another Member, not merely the newest Message's sender. Alice's Message followed by Bob's must still invalidate every Bob session for Alice's Message and every Alice session for Bob's. The two largest sender maxima from distinct Members suffice to compute this without retaining every Message. Coalescing must preserve each recipient's eligible activity and A8 epoch; if bounded bookkeeping cannot do so, use A6 recovery rather than silently discard it.
- A6. Recovery and confidentiality. A notice's occurrence and timing convey activity even when its payload is empty. On incomplete publication (capacity refusal, timeout, recipient-query failure, panic, cancellation, shutdown), a mutation-triggered `activity_reset` may reach only recipients established by that mutation's A3/A4 predicates and still valid under A8. A failed/unknown authorization check sends no mutation-triggered notice, reset or close to unproven recipients. Never broadcast a failure to all Organization sockets. Existing Message-stream failure closes remain limited to its subscribed sockets (#57 PR B/S4), not notice registrations.

  Recovery MUST converge after a lost notice or an uncertain transaction outcome with no subsequent mutation, including after an early successful fetch while COMMIT is still invisible. O5 selects unconditional client-side periodic REST reconciliation of held A9 targets: once the database is reachable and the outcome resolves, a later run obtains current authorized state, subject to A10's retry/terminal rules. Request completion, a one-shot reset, reconnect alone, or socket teardown does not prove that outcome resolved. Across shutdown, new registration's first refetch is not sufficient if an old database backend may still commit later; periodic reconciliation keeps repeating after it. This also covers publication-capacity refusal without an unbounded server retry queue. The web Activity controller implements this independent periodic recovery.
- A7. Per-socket buffer and ordering. Notices wait in a per-socket coalescing buffer separate from the 256-event Message queue, keyed by `(type, channel_id, topic_id)`: within one A8 epoch, `channel_activity` keeps the max eligible `seq`, `read_position_changed` the max `read_seq`, and access gained/revoked share one key per Channel where the newer transition replaces the older and moves to the tail. A late old-transition publisher cannot replace a newer transition. Enqueuing revocation removes that socket's buffered activity, read-position and Channel member-list notices for the removed epoch. A new key when 256 keys are buffered clears the buffer and latches one `activity_reset` only with valid A6/A8 provenance; if bounded provenance cannot be retained or revalidated, defer to O5 recovery instead. Overflow never broadens recipients. No order is promised between notices and Message-stream events, or across notices for different keys; `activity_ready` precedes every other event on the socket.
- A8. Revocation boundary. Every mutation-driven notice/reset carries internal authorization provenance: socket registration epoch, Membership revision, and the applicable Channel-access or Guest-directory epoch. Capture the epoch BEFORE the recipient query, validate it when that query completes, at enqueue and at first frame handoff. A failed comparison discards the old work; a current-access check alone cannot validate it. Under the handoff gate, observed loss irrevocably retires the old epoch and purges its buffered notices/reset contributions. Re-grant creates a distinct epoch and cannot revive a paused query, buffered notice, old revocation or failure reset. Refreshing authorization means starting new work with a new snapshot and A5 batch bound. A3's revocation and A4's own-access directory invalidation use a separate transition token recording the removed lifetime and still-current target; they do not authorize ordinary Channel events. A newer access transition invalidates that token, and its own notices/recovery supply current state.

  Loss observation and the first poll handing a frame to the socket serialize, as in `server/src/channels/access.rs:91`; a frame already handed off may finish. A check racing the loss COMMIT may authorize an old-epoch frame only until loss is observed, never after observation or into re-grant. Directory visibility loss similarly retires Guest-directory work, including buffered `members_changed` about formerly visible others. A coalesced reset retains valid provenance or is deferred to O5 recovery. 4001/4003 retain priority over notice writes (#136); no notice starts after observed session/Membership loss. Lost signals use the existing 35 s fallback, extended to notice authorization lifetimes without adding Message subscriptions or evading their cap. A stale Membership revision matches no mutation-driven recipient.

  A bounded implementation may use one conservative authorization epoch per socket: a relevant loss retires all its old mutation work, with unrelated discarded invalidations recovered by O5. Scope/grant provenance need only be retained for bounded in-flight/buffered work and checked by the fallback; do not allocate a subscription/watch for every visible Channel. Internal invalidation of unproven recipients must not itself emit a reset/close or alter mutation-independent reconciliation timing (A6).
- A9. Client: invalidate and refetch. A notice never changes a count, position, cursor or list entry by itself, except that `channel_access_revoked` removes the Channel's list entry and badge at once (fail closed). The client marks targets dirty and refetches them: `channel_activity` -> Channel list; `read_position_changed` -> Channel list, plus that Topic's summary or the main timeline's summaries when the Channel is watched; `channel_access_gained`, `channel_access_revoked`, `channel_list_changed` -> Channel list; access gained/revoked -> also held Member lists; `channel_members_changed` -> that Channel's member list if held; `members_changed` -> Member lists if held and GET `/api/v1/orgs/{org}/me` (Organization Capabilities); `activity_ready` and `activity_reset` -> every target above that the UI holds. Hidden but retained lists remain dirty until refreshed before reuse.

  #151 adds the held DM list with Unread/Mention unread as an independent target: `dm_list_changed` invalidates it; known-DM activity/read/access events target it instead of the ordinary Channel list. Unknown-kind notices invalidate both held lists. DM E4-E6 extends A9-A12's coverage, addition/identity fencing and access generations to each page/id batch. P-D1-P-D7 durable discovery coalesces one row per Member/revision/DM and reserves two independent attempts/run: rolling delta with a fresh snapshot and immutable-birth coverage with a frozen ceiling. Three remaining slots fairly serve retained-id refresh, browsing and recovery, including retries/continuations within five total DM attempts/run. Old/unheld DMs are discovered automatically; saved cursors progress independently. See [DM bounds](dms.md#protocol-and-amendment-of-e4-e6) for the ≤500-pending deadline and continuous-write progress proof. A5-A8 buffering/provenance and O5's single periodic reconciliation schedule are shared, with no separate DM timer.

  O5 periodic reconciliation refetches only A9 REST targets the client currently holds, including hidden but retained targets; it does not load unheld lists, summaries or Channels. Each run applies the access/directory invalidation and generation fencing used for ready/reset (A11-A12).

  Satisfaction is per target and current access generation. `channel_activity` may skip the Channel-list fetch when its accepted aggregate `as_of_seq` >= `seq`. For `read_position_changed`, a Topic/main summary with accepted scope `read_seq` >= the notice may skip only its own fetch. It cannot satisfy the Channel aggregate: the current REST aggregate exposes the main `read_seq`, not every Topic position. Always invalidate the aggregate for a Topic read notice unless independent aggregate coverage is proved by a successful request issued after that notice. A main read notice may use that aggregate's own `read_seq` coverage. A freshly fetched Topic summary plus an old Channel aggregate still requires the Channel-list fetch. Duplicate notices coalesce; they never borrow coverage from another target. Notice coverage never cancels an O5 periodic run.
- A10. Coalescing and failed refetches. Each target has at most one request in flight and one queued (as the existing web Channel-list rule). A first dirty mark waits a short trailing debounce (controller parameter, default 200 ms); later notices do not postpone it indefinitely. A notice arriving during a request queues one follow-up after that response. `activity_reset` refetches after a random delay (default 0-2 s). Every request has a finite deadline; timeout fences its late response. Bound: per target, at most one request per debounce plus round trip, whatever the notice rate.

  A periodic run uses the same per-target one-in-flight/one-queued rule: coalesce with an in-flight or already queued refetch, queuing at most one generation-current follow-up if the in-flight response cannot cover the run's invalidation. It never launches a duplicate parallel request or adds a second queued request. Periodic runs coalesce into a pending retry without bypassing backoff or Retry-After; the independent schedule continues regardless of request outcomes (O5/N2).

  For EVERY A9 target (Channel aggregate/list, Topic/main summaries, Organization/Channel Member lists and Capabilities), network errors, timeout, 429 and 5xx retain dirty state and retry automatically with capped exponential backoff and jitter, respecting Retry-After; there is no finite retry budget while the target is held and the session/Organization remains usable. Notices coalesce into the pending retry without bypassing backoff. Only a successful, generation-current, authoritative response covering that invalidation clears it. Ordinary non-retryable 4xx stops automatic retry for that invalidation and exposes an error; it cannot claim freshness or restore hidden data. A later valid invalidation or explicit retry may reattempt. 401/organization_unavailable and watched-Channel access errors retain C6/C9/C10 terminal semantics. Removal of an inaccessible Channel also discards its held member list. Session/Organization replacement, access-generation changes and directory invalidations fence responses AND retry timers; no stale retry can repopulate new state. A fresh generation keeps its own required recovery.
- A11. Snapshot races. A successful request issued after a confirmed mutation notice sees that COMMIT; an early recovery reset or periodic fetch for an uncertain outcome does not imply this (A5-A6). A response is **access-authoritative** only if its request was issued after the latest applicable invalidation: received `activity_ready`, `activity_reset`, `channel_access_gained`, `channel_access_revoked`, `channel_list_changed`, or an O5 periodic run. Only such a response adds Channel entries. A non-authoritative response may update baselines of entries present in both in the same generation and remove entries it lacks, never adds or re-adds one, and its follow-up is already queued (A10). Counts follow P8 baseline selection (larger `as_of_seq`, then larger `read_seq`, then smaller counts) within one access generation.

  Each held Member list, Channel member list and Capabilities target also has an invalidation generation. `members_changed`, `channel_members_changed` for its Channel, own access gain/revocation, ready/reset, O5 periodic runs and Organization/Session replacement advance the affected generations. A response issued before the latest applicable invalidation is discarded entirely, including additions and retained entries; issue ordering alone is insufficient. A Guest's invalidated directory is withheld from use until a current successful response replaces it, so neither a failed fetch nor a pre-revocation response leaves formerly visible Members listed. The queued refetch/retry retains that obligation (A10).
- A12. Access generation. The client keeps a local access generation per Channel. `channel_access_gained` for a Channel it holds, and any access-authoritative response that shows a removed Channel again, start a new generation: discard that Channel's baselines, records, held positions and pending mark-read intents, fence their in-flight requests, and accept only a baseline requested in the new generation (P8: a re-grant restarts at the new grant's latest `seq`). `activity_reset`, O5 periodic runs, reconnect and Organization or Account Session replacement (C10) start a new generation for every unwatched Channel: the next access-authoritative baseline replaces, not merges. No REST change is needed: the server already resets positions per grant lifetime (#149 `grant_id`), and the Channel list stays unchanged.
- A13. Interaction with the sync contract. Notices are not Messages: they never move the C2 cursor, never count toward contiguity, never signal or fill a gap (C3), never settle a pending send (C5) and never move a P8 position or baseline. For a watched Channel with a confirmed subscription, the stream (P4/P8 live suffix) stays authoritative and `channel_activity` is ignored; `read_position_changed` still triggers its A9 refetch (other devices). A watched Channel made unavailable by C9 is not revived by a notice or Channel list; its list entry follows A9/A11, and explicit re-selection subscribes again. C4: every new socket's `activity_ready` triggers the full refetch; 4001/4003 keep their terminal meanings, and 4008, 4029, 1001 and 1011 reconnect as today. C10: notices of a closed or replaced socket, Organization or Account Session are fenced like its Messages. A database restore whose Channel history is behind an accepted `as_of_seq` stays out of scope, as in C8.
- A14. Scale. Unsubscribed Channels need no subscription, so the 256 cap no longer limits badges; a client may subscribe only to the Channels it shows. More than 256 visible Channels with simultaneous activity collapse into authorized reset/recovery and one coalesced Channel-list refetch (A6-A7). Server cost per Message is one coalesced recipient query plus an in-memory buffer update per eligible socket. Publication epochs/provenance and retry work must remain bounded; no per-socket-per-visible-Channel subscription registry or per-recipient SQL. #307 item 5 measures this, O5 periodic REST load at 10,000 concurrent connections and multi-sender batching in the implementation PR before release; adjust the provisional period if those measurements require it.

### Observable vocabulary (used by `contract/realtime` fixtures)
Fixtures assert only what a client shows or emits to the outside; they do not name internal state, functions or timers. Any implementation (Rust, TypeScript, a future Kotlin client) with different internals satisfies the contract if these observations hold.
- **Channel state** (the contract's synchronisation state of a watched Channel, asserted by fixtures as `observe.channels[*].state`; it is not a UI display state): `loading` = initial sync not finished: this covers having no base yet and also having a base (from the initial history page) while the subscription is not yet confirmed; `ready` = initial sync finished, i.e. a base is established and the server has confirmed the subscription (`subscribed`), so the cursor is trusted. Establishing a base alone does not make a Channel `ready`. How a Channel is shown during a reconnect is not fixed by this contract unless a fixture asserts it; `unavailable` = terminal for that Channel until the user acts (C9). Not to be confused with the web client's `TimelineState.status`, a UI-facing, implementation-specific state: `TimelineState.status === 'ready'` means only that a base (cursor) is established and Messages can be shown; it does not require the `subscribed` confirmation. So a Channel can be `TimelineState.status === 'ready'` while its Channel state is still `loading` (for example after a reconnect, before the new subscription is confirmed), and the two need not agree at any moment. Fixtures verify the Channel state only and never equate it with `TimelineState.status`.
- **Send state**: `sending` = request in flight; `throttled` = 429, waiting for automatic same-request retry (C6); `unknown` = outcome unknown, same-key resend available; `failed` = definite refusal or unavailable target. Settled/discarded sends are absent.
- **Organization state**: available, or terminal `unavailable` after 4003 or REST-confirmed `organization_unavailable` (C10).
- **Session state**: `signed_in`, or `sign_in_required` after a 401 or a 4001 close (C6, S4).
- **Effect categories** (what a client emits outward, as classified by contract tests): HTTP requests, WebSocket connect/subscribe/unsubscribe, and `wait` effects classified as `reorder_grace` (C3 grace before filling a gap), `fill_backoff` (pause after a failed fill, C3) `reconnect_backoff` (pause before reconnecting, C4) and `send_retry` (429 Retry-After wait, C6). These are categories of observable behaviour only: scheduling and timer internals are not part of the contract; send_retry must respect C6’s minimum delay (controller timer tests). A `membership_check` effect is the C10 REST check after a handshake failure; a fixture marked `layer: controller` observes it and runs only against a whole client (TypeScript: the controller), not a pure protocol layer.
- **Unread vocabulary** (P8, controller-layer fixtures): `load_unread` requests a Channel baseline (`fetch_unread`); `unread_result` delivers its `as_of_seq`, position and counts; `observe.channels[*].unread` asserts the selected baseline and merged counts. All three shared scenarios run against the independent reference merge with broken-rule checks. The event/replay scenario also runs against production; its additive Channel B watch establishes a subscription so the real controller receives B events. The reconnect and equal-baseline scenarios retain concurrent requests and reverse responses, remain `proposed`, and are reported as not executed by production. Web Channel-list fetches use one in flight and one queued, avoiding ordinary overlapping-response races. Separate production tests check this serialization and reject stale snapshots by larger `as_of_seq`, then larger `read_seq`, then smaller counts at equal values, retaining the live suffix in both serial freshness orders. A timeout/retry test delivers the older request last after the retry succeeds and verifies it has no authority. A stale request issued after a newer response tests baseline selection; it is not equivalent to an older request completing last. Server delivery `unread` steps assert the REST baseline and counts and run today.
- **Reply projection vocabulary** (P1, P6-P7, controller-layer fixtures): open a chain from a confirmed Message, fetch forward chain pages with root id and exclusive after_seq, observe root/Topic/visible Messages/has_more, and send with reply_to.
- **Topic projection vocabulary** (P1-P5, implemented in controller-layer fixtures): a Message's Topic label, Topic-filtered and main-timeline pages (`as_of_seq` = W), the main-timeline lines a client shows (one per Message without Topic, one per Topic with its merged position and count) and a Topic view's Messages.

Capabilities (per-operation `{allowed, reason?}` on resources) are not part of this contract; they are added only when the UI must show whether an operation is possible in advance (see `docs/decisions/web.md`).

### Personal section notices (#204, specified, not implemented)

Extends A1-A14 with one personal layout refetch target, not another subscription or delivery protocol. Section behaviour, the decided REST shapes/limits (2026-11-14) and planned acceptance tests are in [Sections](sections.md). E1-E6 apply when sections ship; recovery follows the decided #307 O5 mechanism.

- E1. Event. Add exactly one `ServerEvent` variant, with JSON tag `type` and only the field shown:

  ```json
  {"type":"sections_changed","generation":"1"}
  ```

  `generation` is the committed Member/Organization layout generation (Q10; decimal-string encoding in the decided REST contract). It contains no section name, section content, Channel id/name, count, placement or order. Organization and Member are implicit in the registered socket; no `ClientMessage` variant is added. Every committed create, rename, reorder, move or section delete that advances Q10's observable layout generation emits it. Channel-deletion cleanup emits only for affected Members with effective access in the locked pre-deletion state; hidden-only cleanup removes storage atomically without advancing their exposed generation or publishing to them. No-op, refusal and rollback emit nothing. Access changes use #307 notices, not this generation.
- E2. Recipients. Exactly the changed Member's own registered sockets in the mutation's Organization, including the initiating socket and all other Account Sessions, even with zero Channel subscriptions. Recheck the active Member's current `membership_revision` and valid Account Session after COMMIT, using A3/A8's registration and revocation boundary. No other Member (Owner/Admin included), same Account in another Organization, stale-revision socket, inactive Member or ended Session receives `sections_changed`. There is no Channel-access requirement for this personal event; even a Guest with no accessible Channels owns their empty layout. Personal data is never broadcast to the Organization.
- E3. Reuse A5-A8. Arm publication before COMMIT, publish only afterwards, and use the **same** per-socket coalescing notice buffer and 256-key capacity. Its key is `(sections_changed, null, null)`; retain the numerically largest generation, so out-of-order publication cannot replace it with an older one. No Message queue entry or per-section buffer is added. `activity_ready` remains first. Overflow clears this key along with the other notice keys and latches the existing `activity_reset` only with valid A6/A8 authorization provenance. Incomplete personal publication may trigger a reset only to E2's proven, still-authorized personal recipients in that Organization, never Organization-wide or to another Member. Carry the owner/Organization identity, socket registration epoch, Membership revision and Session authority through publication: capture provenance before the recipient query and validate at query completion, enqueue and first frame handoff under A8's gate. Observed loss retires old work and its reset contributions; reactivation or a new registration cannot revive them. Failed/unknown authorization or unavailable provenance sends no mutation-triggered notice, reset or close to unproven recipients; use O5's mutation-independent periodic REST recovery without waiting for another mutation. Session/Membership loss and in-flight-frame boundaries retain A8/S4's priority; notice writes take no row locks. These notices never alter Message cursors, gap evidence, sends, Unread or subscription state (A13).
- E4. Refetch and missed notices. Add GET `/api/v1/orgs/{org}/me/sections` as one more held A9-style target in A9-A10's dirty/refetch scheduler, including when hidden but retained. Dirty it on `sections_changed` newer than the accepted generation, successful/unknown-outcome personal mutations, `channel_access_gained`, `channel_access_revoked`, `channel_list_changed`, and every `activity_ready`/`activity_reset`. Ready/reset refresh both it and the Channel list even with no subscriptions and no later mutation; reconnect waits for the new socket's ready handoff and uses the same full refresh. A generation gap needs one complete snapshot, never replay of intermediate layouts; duplicates/older generations already covered by an accepted snapshot are satisfied. Publication failure and overflow may use an authorized reset under E3; a broken transport uses reconnect/ready. All held targets, including the layout, participate in the single mutation-independent O5 periodic REST reconciliation schedule, with its decided cadence, spread first runs and jitter; sections add no separate timer or foreground-only recovery policy. Each run uses ready/reset access-generation fencing for layout and Channel-list targets that are held. Notices, mutations and successful requests never restart, postpone or complete that schedule. An early successful refetch while COMMIT is invisible cannot finish recovery: later periodic runs cover a delayed COMMIT, including after reconnect/re-registration or process restart with a surviving database backend. A10/N2 retry/backoff and terminal semantics apply to this target too. All triggers share A10's one-in-flight/one-queued, trailing debounce and reset jitter, including a queued follow-up for a notice during a fetch; timeouts fence late responses. No independent request queue, notice buffer or replay cursor is introduced.
- E5. Stale responses. Apply A11-A12/C10's existing socket, Organization, Account Session and local access-generation fences to the layout target as well as the Channel list. A layout requested before the latest ready/reset/access-gain/access-revoke/list-change/O5-periodic boundary cannot replace the layout; queue its A10 follow-up. Fence layout reads across local mutation start and completion/unknown outcome too, so they cannot restore the pre-intent order. A current-scope response also cannot replace a layout if its generation is below either the latest observed personal notice or the last accepted layout generation. Accept the entire ordered snapshot atomically, never merge old group arrays or restore entries from mutation acknowledgements. Displaying a newly added/reappearing Channel requires its presence in both a current access-authoritative layout and a current access-authoritative Channel list; intersect by id and render only once. Thus a stale layout cannot bypass Channel-list denial, and a stale Channel list cannot bypass layout omission. Existing entries may remain while refresh is pending, except immediate observed loss (E6). Generation equality does not prove access freshness: access loss does not increment Q10's generation. Ready/reset/reconnect starts a local reconciliation epoch and fences previous requests; version floors are rebuilt from its fresh snapshot and notices. Accepting a lower baseline after a database restore requires a fresh socket; unnoticed rollback under a live connection is outside scope. No notice of a closed/replaced socket raises the new epoch's floor. A12 still resets Channel baselines on regain/reset as specified, and C9 still requires explicit re-selection to revive a watched unavailable Channel. Same-session late 401 and Organization-unavailable results retain C6/C10 meanings; replaced-session results have no authority.
- E6. Access-driven display. On `channel_access_revoked`, immediately remove that Channel and its badge from **every** displayed group, discard any client-held placement entry for display and fence pre-loss layout/list reads. Keep its stored placement only on the server (Q5); refetch both targets via E4. A fresh layout omission likewise hides the entry and cannot be undone by an older response. A current direct-placement `404 channel not found` hides it, fences pre-denial layout/list reads and dirties both targets through the same queue. On `channel_access_gained`, refresh both targets under the new A12 access generation; only their fresh authorized intersection may show the retained placement again. `channel_list_changed` refreshes both even when a redundant public grant was removed; continuous access retains order and Unread baselines. Subscription-scoped `channel_access_lost` retains C9's effect, including ignored unwatched events; it does not replace the Organization-scoped revoke/list refresh path. Section display never grants access or revives that subscription. Membership loss closes 4003 and stops this target's automatic work; Account Session end closes 4001/401 with the existing global scope.
