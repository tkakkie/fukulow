## Accounts and Memberships
- Emails, setup Organization/Member names and Channel names reject NUL with 400 ErrorBody before operation-specific database/password work. Authentication and setup-token gates retain 401 precedence; web/native sign-in validates email before throttle reservation. Passwords and Invite tokens keep their existing rules (#299).
- An Account owns globally unique lower-case email, password and Account Sessions. A Member owns the display name and Role in one Organization. One Account may have different Members and Roles in several Organizations; there is at most one Member per Account per Organization.
- Sign in uses email and password only. Web POST /api/v1/session returns only identity and expires_in, setting an HttpOnly Account Session cookie; native POST /api/v1/native/session returns identity, token and expires_in without cookies. Both share verification, issuance, throttling and DELETE /api/v1/session revocation.
- DELETE /api/v1/session with invalid, expired, revoked or missing credentials returns 401 and expires the configured and legacy cookies without revoking any Session; a valid Session still returns 204 and revokes only itself (#300).
- GET /api/v1/me returns the Account and its active Organizations; GET /api/v1/orgs/{org}/me returns its active Member. Every Channel, Message and WebSocket route is under /api/v1/orgs/{org}; only the authenticated Account and that Organization URL establish authority.
- A non-Member, unknown Organization and deactivated Member all return identical 404 ErrorBody with error `organization_unavailable`. Other denials have distinct error values (for example `origin_not_allowed`). Cookie WebSocket Origin validation precedes authentication and Organization resolution: a missing or disallowed Origin returns 403 `origin_not_allowed` even with invalid credentials or an unavailable Organization. Member rows and historical attribution are retained. Reactivation never automatically restores private Channel permissions.

## Password and Account Session security (#304)
- PUT `/api/v1/me/password` takes JSON `{current_password, new_password}`; POST `/api/v1/me/sessions/revoke-others` takes JSON `{current_password}`. Both return empty 204 with `Cache-Control: no-store` and preserve the current Account Session and its sockets.
- Password change uses the same Argon2 algorithm and length rules as setup: at least 12 characters and at most 1024 UTF-8 bytes. Invalid new passwords return 400 ErrorBody `invalid_new_password`; malformed input or an empty/oversized current password returns 400 `invalid input`.
- A wrong current password returns 403 ErrorBody `current_password_incorrect`, never 401. On these endpoints 401 means only a missing, invalid, expired or revoked Account Session, including a Session lost while waiting for the Account lock. Refusals preserve password hashes, every Session and other Accounts; only incorrect-password verification consumes a failure budget.
- Both endpoints share web/native sign-in's IP and normalized-email budgets, reserve before Argon2, and count only incorrect passwords. Refusal returns 429 ErrorBody `too many sign-in attempts` with `Retry-After`. Argon2 admission refusal is 503 `password admission unavailable` and spends no failure budget.
- Password change and revoke-others serialize with web/native sign-in: lock the Account row `FOR UPDATE` before verifying the password or writing, then recheck and lock the current Account Session, then update/delete Sessions, retaining locks through COMMIT. Sign-in locks the Account before password verification and Session insertion. An already-authenticating sign-in must commit its Session before revocation proceeds, so that Session is deleted too.
- The password update and deletion of every other cookie/bearer Account Session across all Organizations commit in one transaction. Re-read both the password and current Session inside it; an error rolls back both password and Sessions. Every other Account stays unchanged.
- After COMMIT, signal each revoked token hash even if the HTTP caller disconnects: idle and replaying sockets in every Organization close with 4001. Current Session sockets remain open. The established observed-loss/in-flight-frame boundary applies: no new protected frame after observed revocation, but a frame already in flight may arrive; lost signals use the 35 s fallback.
- 設定 offers both actions with confirmation of the other-session logout and asks for the current password. Wrong-password 403 leaves the screen and current Session usable. Owner-initiated lost-password recovery is separate and out of scope.

## Members, Roles and Invites
- The server uses one deny-by-default `authorize(actor, action, resource)`. Owners invite any Role and change Roles; Admins invite Admin/Member/Guest. Member and Guest cannot invite or change Roles. All active Members may list active Members (id/name/Role only). Planned (#294, #315, not implemented yet): a Guest will list only themself and active Members with a usable grant on a Channel the Guest can access, and sender names of readable Messages will come from the author lookup (#301), never by widening the list. Owner/Admin/Member may create Channels; Guest cannot.
- Channel access permits a current explicit grant, or a public Channel for Owner/Admin/Member. Guest always needs a current explicit grant, including public Channels. Role, active Membership, revision and grants are read afresh for history, writes, subscribe, replay and fan-out; Owner/Admin never bypass private grants.
- Organization Capabilities are `can_invite`, `can_manage_roles`, `can_deactivate_members`, `can_create_channels`; Channel Capabilities are `can_add_members` and `can_remove_members` (Owner/Admin with access, plus usable private Channel manager rights), `can_manage_managers` (usable managers on private Channels), and `can_leave` (every Role with access). Each is `{allowed, reason?}`, computed by `authorize`; they are UI hints, never authority.
- An Invite binds one normalized email and Role, expires after seven days and is single use. A 256-bit random token is returned once; only its SHA-256 hash is stored. The web sends tokens in POST bodies, shares fragment-only links and removes incoming fragments from browser history immediately; no credentials in web storage.
- Existing Accounts must sign in and match the Invite email by their authenticated Account id. Anonymous acceptance creates an Account only when the email is unused; a uniqueness race refuses rather than attaching that Account. New Accounts sign in afterward. Used/expired/unknown/foreign Invite or wrong supplied email returns identical 404 `invite_unavailable`; mismatched signed-in Account returns 403 `invite_account_mismatch`.
- Invite emails are not verified: an Account accepting an Invite is bound by authentication, not proof of email ownership; email verification is out of scope.
- Invalid Invite credentials never become anonymous. A session 401 offers explicit sign-out; only 204/401 returns to the form with the Invite retained, never auto-submitting. Network/5xx keeps the Invite and shows an error. Existing Accounts still need matching sign-in. Web sign-in, sign-out and Invite acceptance share one operation guard; their submit and recovery buttons stay disabled until it releases, and Account generation fences stale completions (#300).
- Acceptance, Member activation and token consumption commit atomically; expiry is checked at consumption. An active Member cannot accept an Invite to change Role. A deactivated Member reuses its id and revision, gets the invited Role/name and restores no old Channel grants. Under the same Organization lock, acceptance re-reads the issuer's active Membership and current Role, applying the same permission rule as Invite creation for the invited Role; otherwise it returns 403 `invite_issuer_unauthorized`. No email sending or Invite revocation endpoint in this Issue.
- The last active Owner cannot be demoted or deactivated, including concurrent/direct SQL changes. Role changes serialize per Organization and re-check the actor under a Member lock through COMMIT. Organization removal remains out of scope.
- PATCH `/api/v1/orgs/{org}/members/{id}/role` applies the last-manager rule below atomically across private Channels (#231/#311). `last_owner` takes precedence over `last_channel_manager`. Neither refusal changes Roles, grants, Unread, sessions or subscriptions, and the ErrorBody contains only the error value (no Channel details). Owner -> Admin and already unmanaged Channels remain allowed.

### Member deactivation (#305, #237)
- POST `/api/v1/orgs/{org}/members/{id}/deactivate` takes a **Member id**, never an Account id. Success is 204 No Content with no body and `Cache-Control: no-store`. Unknown, foreign-Organization and already-inactive targets return 404 `member_not_found`; a repeat request after success returns that same 404.
- Deactivation uses `authorize` for both the base permission and the target. No Role may deactivate itself. The matrix for other active targets is:

| Caller / target | Owner | Admin | Member | Guest |
|---|---|---|---|---|
| Owner | Allowed | Allowed | Allowed | Allowed |
| Admin | Forbidden | Allowed | Allowed | Allowed |
| Member | Forbidden | Forbidden | Forbidden | Forbidden |
| Guest | Forbidden | Forbidden | Forbidden | Forbidden |

- Error precedence: (1) authentication, 401; (2) caller Membership, 404 `organization_unavailable`; (3) base authorization, 403 `forbidden`; (4) active same-Organization target lookup, 404 `member_not_found`; (5) self-deactivation or Admin on Owner, 403 `forbidden`; (6) 409 `last_owner`; (7) 409 `last_channel_manager`. Every denial leaves Memberships, revisions, grants, rights, Unread, Account Sessions and sockets unchanged. With this matrix a valid caller cannot reach `last_owner`: the sole Owner's self-request is forbidden first; the defensive check and DB constraint remain.
- Organization -> sorted affected private Channels -> Members locks retain the actor's freshly checked Role, activity and revision through COMMIT. The shared #311 check rejects loss of any private Channel's last usable manager, including a right-holding Member, with only the error value. Public and already-unmanaged Channels are exceptions; all affected Channels change atomically.
- Deactivation retains the Member and historical authorship, increments `membership_revision`, and makes old grants and rights unusable. Invite reactivation restores neither; explicit renewal clears the old right. Account Sessions remain valid in other Organizations. Commit plus revocation signaling survives HTTP cancellation; every affected Account Session socket closes with 4003. REST history/replay snapshots established after commit deny; live checks start no new protected frame after observing loss, while in-flight frames may arrive. The 35 s fallback covers a lost signal.
- The Member panel offers permitted other targets a Japanese confirmation Dialog; Capabilities are hints, and every request reauthorizes on the server.

## Channel membership and Channel managers (#149, #231, #311)
- GET/POST `/api/v1/orgs/{org}/channels/{id}/members` lists usable grants (Member `id/name/role/manager`, no email) or adds `{member_id}`. DELETE `.../members/{member_id}` removes a grant or leaves. Unknown, foreign and inactive targets return uniform 404 `member_not_found`. Duplicate current grants and absent removals on visible Channels succeed (204); an inaccessible absent self-removal matches a nonexistent Channel's 404, while a retained stale self grant may be removed.
- A usable grant belongs to an active Membership and captures its current `membership_revision`. A usable manager has such a grant and either Owner/Admin Role or the Channel manager right. Creating a private Channel gives the creator's grant `manager=true` in the creation transaction. Public Channels never carry the right. A usable manager can add/remove grants and grant/revoke the right on usable private grants. Owner/Admin without a private grant have no management, Message/history, subscription or Unread access.
- The right belongs to one `grant_id` lifetime and is independent of Role: Owner/Admin -> Member and Member -> Admin keep it. Removal/leave ends it; stale renewal and re-grant start without it and replace `grant_id`. Adding an already-current grant is a no-op preserving the right, `grant_id`, Unread and subscriptions. Invite acceptance only reactivates the Member; old grants/rights stay stale and unusable until explicit renewal, which clears the right. Reactivation never grants Channel access.
- Guests cannot hold a usable right. A Role change to Guest clears rights in the Role transaction; later promotion never restores them. Guest demotion/promotion retains current private grants, `grant_id`, Channel/Topic Unread and continuous subscriptions. Changing only the right changes no access, delivery or Unread and emits no access-loss event.
- PATCH `/api/v1/orgs/{org}/channels/{id}/members/{member_id}` with `{manager: bool}` grants/revokes the right on an existing usable private grant, returning 204 with `Cache-Control: no-store`. Setting the current value is a no-op success after the same actor, Channel and target checks. The actor's Role, active Membership, revision, access and right are re-read inside the transaction under locks; Capabilities are only hints.

| Manager PATCH refusal | Status + ErrorBody error |
|---|---|
| Unauthorized actor (including no-ops and Guest actors) | 403 `forbidden` |
| Inaccessible, unknown or foreign Channel | 404 `channel not found` |
| Unknown, foreign or inactive target Member | 404 `member_not_found` |
| Active same-Organization target without a current grant (absent or stale revision) | 404 `channel_grant_not_found` |
| Public Channel (after ordinary management authorization) | 400 `channel_manager_private_only` |
| Guest target (including no-op revoke) | 400 `channel_manager_guest` |
| Revocation would remove the last usable manager | 409 `last_channel_manager` |

- Revocation, removal/leave, Role changes and Member deactivation refuse 409 `last_channel_manager` whenever a private Channel with at least one usable manager would lose its last. Rights held by Members count alongside Owner/Admin grants; inactive/stale grants do not. Private last-usable-grant protection remains 409 `last_channel_grant` and takes precedence for removal/leave. Unmanaged Channels need no new manager. ErrorBody carries only the error value.
- `authorize` is the single deny-by-default policy for management and Capabilities. SQL manager Role sets are projected from that policy for both right values; removal/revocation and the injected RoleChangeGuard use the same before/after count. Transactions lock Organization -> private Channels (ascending id for Role changes) -> Members (target NO KEY UPDATE before grant changes) -> grants -> #142 Unread/shared #135. Creation locks Organization NO KEY UPDATE -> creator Member -> new rows, so its grant and right commit atomically and the Role guard's Channel set stays stable. Sends retain Member/grant locks through COMMIT: send-first may commit while removal waits; removal-first denies new sends and canonical retries.
- No backfill: existing private Channels recorded no creator, guessing could grant an unchosen right, and nothing is deployed yet. Existing grants default to `manager=false`; Owner/Admin grantees still manage them, and unmanaged Channels retain #149's rule. Migration `202611130311_channel_managers.sql` rejects rights on public Channels and skips Unread triggers for right-only changes.
- #237 is delivered by #305: deactivation reuses the shared usable-manager count and Organization -> sorted Channels -> Members lock order, with atomic no-details refusal and `last_owner` precedence.
- #298 enables the web private option only after #311's PR merges. The メンバー tab displays the Channel manager right and uses `can_manage_managers` for grant/revoke controls with a confirm Dialog; Japanese refusals follow docs/ui.md §10. This server/API change does not enable that option.

## Setup
- `FUKULOW_SETUP_TOKEN` is required in every mode (Compose, docker run, standalone binary). Unset, whitespace-only or the former published example (`setup-token-local-test-only`, also with surrounding whitespace) fails startup with a Result error, regardless of `FUKULOW_COOKIE_SECURE`. `.env.example` leaves it empty; generate a secret with `openssl rand -base64 32`. Development and tests explicitly supply their own test-only values. The server never generates or logs the token; accepted values retain their exact bytes.
- Setup extracts the JSON body before checking `setup_token`. Malformed JSON, missing required fields or invalid field types return 400, oversized bodies return 413, and unsupported content types return 415 even if the token is missing or invalid.
- After successful extraction, the token must match before semantic input validation, password hashing or database access; missing or incorrect tokens return the same generic 401 before and after setup.
- `GET /api/v1/setup` remains public and read-only: only `setup_required`, with `Cache-Control: no-store`, independent of the token.
