# Spec: Accounts

Index and Terms: [docs/spec.md](../spec.md).
Related: [Membership/access loss, C9](realtime.md#client-rules); [setup token](deployment.md#proxy-and-sign-in-limits).

## Accounts and Memberships
- An Account owns globally unique lower-case email, password and Account Sessions. A Member owns the display name and Role in one Organization. One Account may have different Members and Roles in several Organizations; there is at most one Member per Account per Organization.
- Sign in uses email and password only. Web POST /api/v1/session returns only identity and expires_in, setting an HttpOnly Account Session cookie; native POST /api/v1/native/session returns identity, token and expires_in without cookies. Both share verification, issuance, throttling and DELETE /api/v1/session revocation.
- GET /api/v1/me returns the Account and its active Organizations; GET /api/v1/orgs/{org}/me returns its active Member. Every Channel, Message and WebSocket route is under /api/v1/orgs/{org}; only the authenticated Account and that Organization URL establish authority.
- A non-Member, unknown Organization and deactivated Member all return identical 404 ErrorBody with error `organization_unavailable`. Other denials have distinct error values (for example `origin_not_allowed`). Cookie WebSocket Origin validation precedes authentication and Organization resolution: a missing or disallowed Origin returns 403 `origin_not_allowed` even with invalid credentials or an unavailable Organization. Member rows and historical attribution are retained. Reactivation never automatically restores private Channel permissions.

## Members, Roles and Invites
- The server uses one deny-by-default `authorize(actor, action, resource)`. Owners invite any Role and change Roles; Admins invite Admin/Member/Guest. Member and Guest cannot invite or change Roles. All active Members may list active Members (id/name/Role only). Owner/Admin/Member may create Channels; Guest cannot.
- Channel access permits a current explicit grant, or a public Channel for Owner/Admin/Member. Guest always needs a current explicit grant, including public Channels. Role, active Membership, revision and grants are read afresh for history, writes, subscribe, replay and fan-out; Owner/Admin never bypass private grants.
- Organization Capabilities are `can_invite`, `can_manage_roles`, `can_create_channels`; Channel Capabilities are `can_add_members` and `can_remove_members` (Owner/Admin with Channel access; #311 will add private Channel managers, #292), and `can_leave` (every Role with access). Each is `{allowed, reason?}`, computed by `authorize`; they are UI hints, never authority.
- An Invite binds one normalized email and Role, expires after seven days and is single use. A 256-bit random token is returned once; only its SHA-256 hash is stored. The web sends tokens in POST bodies, shares fragment-only links and removes incoming fragments from browser history immediately; no credentials in web storage.
- Existing Accounts must sign in and match the Invite email by their authenticated Account id. Anonymous acceptance creates an Account only when the email is unused; a uniqueness race refuses rather than attaching that Account. New Accounts sign in afterward. Used/expired/unknown/foreign Invite or wrong supplied email returns identical 404 `invite_unavailable`; mismatched signed-in Account returns 403 `invite_account_mismatch`.
- Invite emails are not verified: an Account accepting an Invite is bound by authentication, not proof of email ownership; email verification is out of scope.
- Acceptance, Member activation and token consumption commit atomically; expiry is checked at consumption. An active Member cannot accept an Invite to change Role. A deactivated Member reuses its id and revision, gets the invited Role/name and restores no old Channel grants. Under the same Organization lock, acceptance re-reads the issuer's active Membership and current Role, applying the same permission rule as Invite creation for the invited Role; otherwise it returns 403 `invite_issuer_unauthorized`. No email sending or Invite revocation endpoint in this Issue.
- The last active Owner cannot be demoted or deactivated, including concurrent/direct SQL changes. Role changes serialize per Organization and re-check the actor under a Member lock through COMMIT. Organization removal remains out of scope.
- PATCH `/api/v1/orgs/{org}/members/{id}/role` rejects Owner/Admin -> Member/Guest with 409 `last_channel_manager` if any private Channel would lose its last usable manager (#231); `last_owner` takes precedence over `last_channel_manager`. Usable means active Membership, current grant revision and current Owner/Admin Role. The rejection changes no Role, grants, Unread positions, sessions or subscriptions; its `ErrorBody` contains only the error value, without Channel names, ids or counts. Another usable manager on every affected Channel permits demotion; Owner -> Admin, public Channels and already unmanaged Channels remain allowed. The transaction locks Organization -> affected private Channels (ascending id) -> Members through COMMIT, sharing #149's manager check and serializing against private Channel creation, demotions, removals and leaves. Membership deactivation/removal protection is tracked separately in #237.

Channel membership (#149): GET/POST `/api/v1/orgs/{org}/channels/{id}/members` lists usable grants (Member id/name/Role only) or adds `{member_id}`. DELETE `.../members/{member_id}` removes or leaves. Unknown, foreign and inactive targets return uniform 404 `member_not_found`. Duplicate current grants and absent removals on visible Channels succeed (204); inaccessible absent self-removal returns the same 404 as a nonexistent Channel, while a retained stale self grant may be removed. stale grants renew explicitly at the target's current revision. Mutation transactions recheck the actor's Role/Membership/access. Private removal/leave rejects the last usable grant (409 `last_channel_grant`) and removing the last usable Owner/Admin grant (409 `last_channel_manager`), even with Member/Guest grants left. An unmanaged Channel needs no new manager; Role demotion follows the same last-manager rule (#231). Sends retain Member/grant locks through COMMIT: send-first may commit, removal waits; removal-first denies new sends and canonical retries.

Private Channel managers (#292; planned in #311, not implemented yet; until then the rules above apply):
- Creating a private Channel gives the creator's grant the Channel manager right, independent of Organization Role. Public Channels never carry it.
- A usable manager is a usable grant (active Membership, current revision) whose Member is Owner/Admin or holds the right. Usable managers add and remove grants and grant or revoke the right on another usable grant. Owner/Admin without a grant cannot manage a private Channel and get no implicit Message access.
- The right belongs to one grant lifetime: removal, leave and a Role change to Guest end it. Stale renewal, re-grant and reactivation create or renew grants without it. Guests cannot hold it. Owner/Admin -> Member keeps it.
- 409 `last_channel_manager` applies when revoking the right, removal, leave, a Role change or Membership deactivation (#237) would take a private Channel from at least one usable manager to none. Channels without one are not required to gain one; `last_channel_grant` is unchanged.
- Existing private Channels are not backfilled: no creator was recorded, and nothing is deployed yet.
- The member list shows the right. The endpoint, Capability name and error values are fixed by #311's PR, which updates this section. Until then the web never creates private Channels (#298).

## Setup
- `FUKULOW_SETUP_TOKEN` is required in every mode (Compose, docker run, standalone binary). Unset, whitespace-only or the former published example (`setup-token-local-test-only`, also with surrounding whitespace) fails startup with a Result error, regardless of `FUKULOW_COOKIE_SECURE`. `.env.example` leaves it empty; generate a secret with `openssl rand -base64 32`. Development and tests explicitly supply their own test-only values. The server never generates or logs the token; accepted values retain their exact bytes.
- Setup extracts the JSON body before checking `setup_token`. Malformed JSON, missing required fields or invalid field types return 400, oversized bodies return 413, and unsupported content types return 415 even if the token is missing or invalid.
- After successful extraction, the token must match before semantic input validation, password hashing or database access; missing or incorrect tokens return the same generic 401 before and after setup.
- `GET /api/v1/setup` remains public and read-only: only `setup_required`, with `Cache-Control: no-store`, independent of the token.
