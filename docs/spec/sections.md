## Personal sections (#204, specified, not implemented)

Maintainer decisions of 2026-11-14 are fixed. The remaining behavioural defaults, REST design and numerical limits below are proposals for approval under **Open decisions**, not an implemented API. This feature adds a product-feature spec part to keep the REST, ordering and acceptance contract together. Rust schemas and `openapi.json` follow in an implementation Issue after approval; this Issue changes neither.

- Q1. A **section** is a Member's named, ordered collection of Channels in one Organization's left column. Every active Role, including Guest, can manage its own sections. A section belongs to a Member, not an Account across Organizations. There are no shared, Organization-default or admin-managed sections, and no other Member (Owner/Admin included) can read or change them.
- Q2. Each Member has zero or more custom sections and one implicit **Other Channels** group, shown as `その他のチャンネル`. A Channel has at most one stored placement for that `(Organization, Member)`. A placement identifies its group (one custom section or the implicit group) and its place in that group's order. No placement means Other Channels in automatic name order. The implicit group has no section id or mutable name, cannot be created/deleted/reordered among sections, and follows all custom sections. Empty custom sections remain visible; hide an empty Other Channels heading. Names need not be unique, including a custom name matching the localized default label; identity is always the id.
- Q3. Custom sections follow the Member's complete section order. Within each group, explicit placements follow the Member's order, then unplaced Channels (possible only in Other Channels) follow the existing Channel-list order: `lower(name COLLATE "C"), id` (ASCII-only folding, UUID tie break). Create appends a section. A move to another group appends after that group's explicit placements and before its automatic tail; moving to the current group is a no-op and preserves order. Reordering uses complete lists, never partial position patches. Integer positions, fractional keys and other internal representations are implementation choices; no such keys appear in the API.
- Q4. Effective access is exactly the existing `authorize` policy, read afresh: active current-revision Owner/Admin/Member can access public Channels or Channels with a usable grant; Guest needs a usable grant even for public Channels; every Role needs a usable grant for private Channels. Section reads return only accessible Channel ids, with no hidden ids, names, counts, placeholders, gaps or stored order keys. Section metadata remains visible to its owner even when all its Channels are hidden. Channel names and badges come only from the authorized Channel list; section responses confer no access.
- Q5. Access loss retains the stored placement and order but immediately hides the Channel from every group when loss is observed. A regain reveals the same stored group and place, provided neither that section nor the Channel has been deleted. Hidden placements are never submitted by the client or silently removed by a reorder. Removing a redundant public grant for Owner/Admin/Member changes neither effective access nor placement. Deactivation retains personal data on the preserved Member identity; reactivation does not restore grants, and only newly effective access reveals retained placements. This persistence is independent of Unread positions, which follow P8 and may reset on re-grant.
- Q6. Deleting a section atomically removes the section and all its placements, including hidden ones. Its accessible Channels become unplaced in Other Channels (automatic name order); inaccessible ones appear there only if access returns. Deleting a Channel removes every Member's placement for it in that same transaction. Neither section deletion nor any other personal operation changes a Channel, grant, Membership, Role, Message, Unread position or subscription. A later Channel-deletion feature must integrate this cleanup before shipping; this spec adds no Channel-deletion endpoint.
- Q7. Every section-related row (including generation and create-retry metadata) has `organization_id NOT NULL` and a same-Organization Member reference `(organization_id, member_id)`. Channel references use `(organization_id, channel_id)`. Sections have unique `(organization_id, member_id, id)`; a custom placement references exactly that owner-consistent key. A unique `(organization_id, member_id, channel_id)` prevents multiple placements, including default/custom duplicates. Section and Channel deletion cannot leave dangling references. The `channels` module owns this data and its SQL; auth remains the owner of Member authorization. An append-only migration adds constraints and supporting indexes, including composite-reference targets and cleanup lookups; Organization RLS/context rules also apply. Direct SQL cross-Organization and cross-owner references must fail, independently of API checks.
- Q8. Mutations are atomic and serialized per `(Organization, Member)` through COMMIT; reads see one complete committed state, never partial reorder/delete work. Concurrent moves have one winner's complete placement. Move versus section delete either leaves a placement in a surviving group or removes it to Other Channels; a move whose destination was deleted first fails without writing, never recreates it. Concurrent complete reorders of the same current resource set use last-committing-writer-wins, with no duplicate/missing entries. A concurrent create, delete, move or access-set change that changes a reorder's required id set rejects the whole reorder: `409 section_layout_changed` unless an earlier 404 ownership/access check denies (refusal precedence below). There is no partial application or automatic merge. No order-version precondition rejects an order-only concurrent update.
- Q9. Use #149/#311's lock order: Organization -> affected Channels ascending id -> Members (ascending id if more than one) -> grants -> personal layout rows. Retain fresh actor Role, active Membership/revision and any required grant authorization through COMMIT, including no-ops and retries. Discover affected sets before taking later locks; revalidate after locking and restart or return the set-conflict above if they changed, never acquire an earlier-order lock afterwards. Section-only changes need no Channel/grant locks when they neither authorize nor modify a Channel placement; skip unused stages, never reverse them. Channel deletion locks all affected Members before layout cleanup in the same order. Publication uses non-locking post-COMMIT recipient reads (A5).
- Q10. Each Member/Organization has a durable `generation`, initially zero, advanced once per transaction that changes personal section data, including Channel-deletion cleanup. No-ops, denied requests and rollbacks do not advance it or publish. Access changes alone do not advance it: A9-A12's access generation is separate. A GET returns the generation, order and effective-access projection from one read-only REPEATABLE READ snapshot with current Membership/revision authorization, without Member row locks. Loss committed before that snapshot denies or filters; an earlier authorized snapshot may finish, subject to the client fences below.

## Proposed REST contract

All paths start `/api/v1/orgs/{org}`. `org`, section ids and Channel ids are UUIDs. The owner is always the authenticated active Member resolved from that Organization URL; there is no owner/Member field or administrative override. Cookie and bearer authentication follow the existing API. Request objects reject unknown fields. Every response, including errors and empty successes, is `Cache-Control: no-store`.

`generation` in both REST and the notice is a canonical unsigned decimal **string** (`0` or a nonzero digit followed by digits, maximum `9223372036854775807`), compared numerically, not lexically. It never wraps or gets reused during normal database lifetime. It is a snapshot version, not a Channel `seq`, grant lifetime or authorization token. A database restore requires a fresh socket and reconciliation epoch before accepting a lower baseline; unnoticed rollback under an existing connection is outside this contract, as with C8's undetected restores.

Shapes (all fields required unless stated; arrays are ordered, ids unique):

```text
Section = { id: UUID, name: string, channel_ids: UUID[] }
SectionLayout = { generation: decimal-string, sections: Section[], other_channel_ids: UUID[] }
SectionSnapshot = { generation: decimal-string, section: Section }
ChannelPlacement = { generation: decimal-string, section_id: UUID | null }
CreateSection = { id: UUID, name: string }
RenameSection = { name: string }
SectionOrder = { section_ids: UUID[] }
ChannelOrder = { section_id: UUID | null, channel_ids: UUID[] }
MoveChannel = { section_id: UUID | null }
CreatedSection = { id: UUID, generation: decimal-string }
ErrorBody = existing { error: string }
```

`null` means Other Channels, not a custom section. `sections` includes all the owner's custom sections, even empty; both Channel-id arrays contain accessible Channels only. Across the layout, every effectively accessible Channel occurs exactly once. No pagination, hidden-placement metadata or Channel contract copy is added. The Channel list supplies the existing Channel representation separately; clients render the intersection under E5-E6.

| Method and suffix | Request | Success |
|---|---|---|
| GET `/me/sections` | none | 200 `SectionLayout` |
| GET `/me/sections/{id}` | none | 200 `SectionSnapshot`; only that owner's section |
| POST `/me/sections` | `CreateSection` | 201 `CreatedSection`; 200 for a canonical retry while it still exists |
| PATCH `/me/sections/{id}` | `RenameSection` | empty 204; identical current name is a reauthorized no-op |
| DELETE `/me/sections/{id}` | none | empty 204, also if absent, deleted or owned elsewhere; no disclosure |
| PUT `/me/sections/order` | `SectionOrder` | empty 204 |
| GET `/me/channel-sections/{channel_id}` | none | 200 `ChannelPlacement`; `null` for explicit/default or unplaced/default |
| PUT `/me/channel-sections/{channel_id}` | `MoveChannel` | empty 204; Q3 appends only when changing groups |
| PUT `/me/section-channel-order` | `ChannelOrder` | empty 204 |

The static `/me/sections/order` route is reserved, not parsed as a section UUID. There are no query parameters on these routes.

- R1. Names contain 1..=60 Unicode scalar values, no NUL, are not whitespace-only and have no leading/trailing Rust `str::trim()` whitespace. Reject rather than trim or normalize; keep internal whitespace and case. Maximum 50 live custom sections per Member/Organization, including empty sections and those containing only hidden placements. The implicit group and retired create ids do not count. The count check and insertion are atomic; a canonical retry does not consume another slot.
- R2. Default body limit is the existing 16 KiB. `PUT /me/section-channel-order` proposes a 1 MiB exception and at most 20,000 Channel ids, so a complete order for thousands of Channels fits. `SectionOrder` has at most 50 ids; an empty array is valid when there are no custom sections. `ChannelOrder` may be empty when its group has no accessible Channels. Limits count decoded Unicode scalars / array elements, while the byte limit counts the actual JSON body. Supporting a group larger than 20,000 requires the unresolved O2 capacity choice; it must not be silently truncated or partially reordered.
- R3. Section reorder lists **every current custom section id exactly once**; omitted current own ids return `section_layout_changed`, duplicates give `invalid_section_order`, and unknown/deleted/foreign ids keep `section_not_found`. Channel reorder lists **every currently accessible Channel in the selected group exactly once**, including its automatic tail, and cannot move Channels between groups. Hidden placements are omitted and preserved: take the stored explicit sequence, append the current accessible unplaced tail, keep each hidden slot fixed, and fill the remaining slots in submitted order. Submitted visible Channels become explicit placements; hidden ones keep their group and place. Example stored `[A, hidden H, B]`, submitted `[B,A]` becomes `[B,H,A]`, displayed `[B,A]`; regain shows `[B,H,A]`. A missing or extra accessible id (including one now in another group) gives `section_layout_changed`; supplied inaccessible ids deny first with `channel not found`. Q8 defines concurrent results. Fetch a fresh layout after a set conflict before resubmitting an intentional full order.
- R4. POST uses a client-generated id stable across retries, scoped to the owner/Organization. Persist its original create intent atomically: same id and exactly the original name returns 200 with the id and current generation, preserving any later rename/order; another original name gives `409 section_id_conflict`. After deletion, retain a retired-id record sufficient to reject every reuse with `409 section_deleted`, so a late create retry cannot resurrect it. Concurrent identical creates make one section. No section data is returned for another owner's id. Ids may coincide between owners without conferring authority.
- R5. Rename, move and reorder express desired state, not relative increments; repeating an already satisfied request is a no-op after current authorization and set validation. Reissuing an older desired state after an intervening write is a new last writer, not a canonical replay. Clients serialize their own mutation intents and do not blindly retry them after an unknown outcome: refetch and ask the user to reapply if the desired state is no longer current. DELETE is safely repeatable. POST alone retries the same original id/name (R4). After every success or unknown outcome, dirty the layout target through E4; mutation acknowledgements alone never add displayed Channels.

### Refusals and precedence

Authenticate the Account Session first (401), then parse the Organization UUID (malformed: 400 `invalid input`), then resolve Organization Membership/revision (404 `organization_unavailable`), then validate the remaining path/body (400/413/415). Writes recheck authentication authority inside the transaction before any effect; a deactivation/reactivation race never borrows the new revision. Resolve an owned custom section before exposing its contents; for a Channel placement read/move, authorize the Channel before resolving the destination. For Channel reorder: resolve the selected owned group, authorize every supplied Channel, then validate the complete current set. Section reorder checks ownership of supplied ids before set equality. Denials and conflicts change nothing and publish nothing.

| Refusal | Status and `ErrorBody.error` |
|---|---|
| Missing/invalid/expired/revoked Account Session | 401 `invalid credentials` (existing Session error) |
| Unknown Organization, non-Member, inactive or stale-revision Membership | 404 `organization_unavailable` |
| Malformed JSON/UUID, missing/unknown fields, wrong types/nullability | 400 `invalid input` |
| Invalid section name | 400 `invalid_section_name` |
| Duplicate order ids or an array over its element limit | 400 `invalid_section_order` |
| Actual body exceeds byte limit | 413 `request body too large` (existing extraction error) |
| Unsupported content type on a body route | 415 `expected application/json` (existing extraction error) |
| Unknown, foreign-Organization or another Member's section id (GET/PATCH, move destination, reorder) | 404 `section_not_found`; DELETE keeps uniform 204 |
| Unknown, foreign-Organization or inaccessible supplied Channel, including a guessed retained placement | 404 `channel not found` (existing access error) |
| New creation would exceed the live-section limit | 409 `section_limit` |
| Create id reused with a different original name / after deletion | 409 `section_id_conflict` / `section_deleted` |
| Complete reorder's current id set differs | 409 `section_layout_changed` |
| Database/internal failure, including generation exhaustion | 500 `internal error` (existing generic error) |

No error contains a name, owner id, hidden Channel id/count or conflicting layout. An inaccessible Channel is never distinguished from an unknown one. A read of an owned section/layout succeeds with inaccessible Channels omitted; direct placement reads deny instead. This is not a management permission, so no new 403 bypass or Owner/Admin special case is introduced.

## Left-column behaviour

Follow [UI rules](../ui.md) for layout, responsive navigation, copy, focus and accessibility. Custom sections and Other Channels are collapsible headings with keyboard-operable buttons and `aria-expanded`; initially expanded. Each visible Channel keeps its existing Topic accordion. Offer `セクションを作成`, `名前を変更`, `上へ移動`, `下へ移動`, `セクションを削除` and `チャンネルを移動`; destination choices include `その他のチャンネル`. Reorder and move have visible keyboard-reachable controls, not drag-only interaction. Retain focus on the moved item; after deletion focus the next section heading, else the previous, else the Channel-list heading. Collapse does not alter placement, access, subscription or Unread; collapse state stays local in memory and is not synchronized or stored in web storage. Empty custom sections remain editable/deletable.

## Open decisions

- O1. Approve the proposed REST routes/shapes, 60-scalar names / 50 live sections and behavioural defaults: default group last, duplicate labels allowed, append on move, unplaced name order after delete, local in-memory collapse state. Recommendation: as specified; UUID identity and complete orders keep the first implementation small.
- O2. Approve a full visible-group reorder of at most 20,000 ids with a 1 MiB body exception (existing default 16 KiB). Recommendation: as specified for the first implementation; explicitly decide larger-group support before approval if required, rather than truncate or add hidden partial-order semantics.
- O3. Recovery from a silently missed final notice while the socket stays open needs reconciliation beyond failure/reset signals. Recommendation: E4's 60 s foreground reconciliation plus immediate foreground resume, through the existing A10 target queue; approve the interval or another bounded recovery policy.
- O4. Approve decimal-string generation and durable original-create/retired-id metadata. Recommendation: as specified; exact version comparison across clients and canonical retries must survive rename/delete without resurrecting a section. This metadata is private, Organization-scoped and not a new access generation.
