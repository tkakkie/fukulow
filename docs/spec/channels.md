## Channel rename and archive (#410, implemented)

- K1. Only ordinary Channels (kind `channel`) are renamed, archived or restored. Public: active Owner/Admin. Private: a usable Channel manager (#311), i.e. a current grantee with Owner/Admin Role or the manager right. No Role bypasses private access. Other Members, Guests and non-manager grantees get 403 `forbidden`. Accessible DMs refuse all three with 400 `dm_channel_fixed` after DM access authorization (DMs have no name or archive state).
- K2. Archive is a Channel state, not access loss. Grants, manager rights, read positions, Unread baselines, subscriptions and #204 placements are kept, and restore brings all of them back. Archive and restore are neither loss nor reappearance for [A12](realtime.md#organization-activity-notices-307-implemented): clients start no access generation and discard no Unread baseline, record, position or pending mark. Rename/archive/restore allocate no `channel_log` position and change no Message version, `mutation_seq` floor, `history_generation`, fixed-W page or cursor (#160).
- K3. While archived, a new send (including Replies and first Topic Messages) or Move gets 409 `channel_archived`. It comes after Channel authorization, `history_generation_changed` and canonical receipt resolution (S5 for sends, the `operation_id` receipt for Move), so committed retries return their original outcome and changed intent keeps its existing 409. For Move it comes after the chain lookup and Move rights (404 `reply_chain_not_found`, 403 `move_not_allowed`) and before `chain_too_large`/`version_conflict`. For sends it precedes limiting/admission (S6). #204 placement operations on an archived Channel also get 409 `channel_archived` after Channel access authorization ([Q4](sections.md#personal-sections-204-specified-not-implemented)). History, events/replay/subscribe, Topic/Reply reads, mark-read, Search and grant/manager/leave stay available under existing access, including #311 guards. #287 decides Edit/Delete on archived Channels.
- K4. Rename/archive/restore lock the Channel row `FOR NO KEY UPDATE` in the #149/#311 order (Organization → Channel → Members → grants). Sends and Moves hold their `FOR SHARE` Channel lock through COMMIT and recheck archive state under it. Send-first commits the Message and its position before archive commits. Archive-first refuses the send with 409, with no position or publication. A token paid inside persistence is kept, as for a missing parent (S6). Tests cover both commit orders for send and for Move.
- K5. Rename follows creation name rules (400 before a write transaction) and the #51 uniqueness, which includes archived Channels: their names stay taken (409 `channel name already exists`). On an archived Channel any authorized rename gets 409 `channel_archived` first, so it discloses no name collision. Otherwise an exact-byte same name, or a same-state archive/restore, is a no-op after authorization: 204, no write, no notice. A case-only rename is a change.
- K6. The ordinary Channel list excludes archived Channels. A separate archived list returns currently accessible archived Channels with the same access rules, order, Capabilities and stored counts. The web shows no Unread or Mention badge or total for them. Positions stay and count again after restore. Absence from the ordinary list is not access loss: only `channel_access_revoked`, `channel_access_lost` or a denial is (C9). When an open or linked ordinary Channel is absent from the ordinary list, the client reads it by id to learn its archive state and Capabilities. DMs are never in that list and never use the by-id read: they refresh through the [DM held-id lookup](dms.md#protocol-and-amendment-of-e4-e6). An archived Channel opens read-only with its history.
- K7. API:
  - `PATCH /api/v1/orgs/{org}/channels/{id}` takes exactly one of `name` or `archived` (boolean), rejects unknown fields and returns an empty 204.
  - `GET /api/v1/orgs/{org}/channels/{id}` returns one accessible ordinary `Channel`. An accessible DM gives 400 `dm_channel_fixed`. An inaccessible, unknown or foreign id, including an inaccessible DM, gives 404 `channel not found`.
  - `GET /api/v1/orgs/{org}/channels?archived=true` returns the archived list in the existing `ChannelList`. `archived=false` equals omission. Invalid values give 400 `invalid input` after Organization resolution. `history_generation` applies as on the ordinary list.
  - `Channel` gains `archived`. Capabilities gain `can_rename` and `can_archive` (archive or restore). On an archived Channel, `can_rename` denies `channel_archived` for managers. DMs deny both with `dm_channel_fixed`.
  - Error order: 401 → 400/413/415 path, body and name → 404 `organization_unavailable` → 404 `channel not found` (inaccessible, unknown, foreign) → 400 `dm_channel_fixed` → 403 `forbidden` → 409 `channel_archived` → 409 `channel name already exists`. Denials write and publish nothing.
- K8. An append-only migration adds nullable `channels.archived_at` with a CHECK that DMs are never archived. No backfill: existing Channels stay active. `channels` owns the SQL. Any other schema change or backfill needs maintainer approval.
- K9. The web replaces the overview placeholder with 名前を変更, アーカイブ and 復元 controls gated by Capabilities. It confirms archive and restore, adds the アーカイブ済みチャンネル list, and in archived Channels shows a read-only notice with sending disabled. Refusals are in Japanese. [Copy rules](../ui.md)
