## Proxy and sign-in limits
- Sign-in failure budgets are process-local: 20 per IPv4 or IPv6 /64 and 5 per normalized Account email in a 60-second window. IPv4-mapped IPv6 shares the IPv4 budget. Web and native sign-in share budgets; in-flight attempts reserve capacity, and successful attempts release it.
- Standalone proxy configuration requires both `FUKULOW_TRUSTED_PROXIES` (comma-separated exact IPs or CIDRs, IPv4/IPv6) and `FUKULOW_CLIENT_IP_HEADER`. Invalid/partial configuration fails startup. CIDR prefix lengths use decimal digits without a sign or leading zeros (except `/0`). CIDRs may contain host bits; membership uses the prefix. IPv4-mapped IPv6 peers are canonicalized to IPv4. IPv4 peers match IPv4 ranges or IPv4-mapped IPv6 ranges wholly inside `::ffff:0:0/96` (mapped address and prefix >= 96); other IPv6 ranges never trust IPv4 peers.
- Only a trusted socket peer can supply the client IP. One header field uses its rightmost comma-separated IP, which the immediate proxy must append or overwrite. Missing headers, repeated header fields, a non-text value or an invalid rightmost IP fall back to the socket peer. Earlier comma-separated values are ignored, even if invalid. An untrusted peer's entire header is ignored.
- Compose runs exactly one of `--profile caddy` (default) or `--profile nginx`, both HTTPS. Only proxy + app join `edge`; only app, the one-shot `migrate` service and DB join `backend`. The app has no published port by default. `FUKULOW_EDGE_PREFIX` (default `172.30.94`) derives the edge subnet `<prefix>.0/29`, gateway `<prefix>.1`, fixed proxy IP `<prefix>.2`, app IP `<prefix>.3` and dynamic allocation range `<prefix>.4/30`; change this one value to move them together. Dynamic containers cannot take the proxy or app IP. Compose trusts exactly `<prefix>.2`, never the gateway or subnet, and sets `x-forwarded-for` itself.
- For opt-in local debugging, add a temporary Compose override with `services: {app: {ports: ["127.0.0.1:8080:8080"]}}` and pass it with `-f compose.yml -f /path/to/debug.yml`. The published-port peer is untrusted; forwarded headers cannot select a budget. Remove the override afterward. Health checks normally use the selected proxy.
- Upgrade existing deployments: set a random `FUKULOW_SETUP_TOKEN` before `docker compose up`; missing/empty fails interpolation before container recreation and leaves the running stack and volume intact. Existing Accounts and sign-in are unaffected; the token only gates setup, but remains required after setup. The default `127.0.0.1:8080` publication is gone; move host health probes to the proxy or use the debug override above. Existing `.env` values for `FUKULOW_TRUSTED_PROXIES` and `FUKULOW_CLIENT_IP_HEADER` are ignored by Compose. If Docker reports a subnet overlap, set `FUKULOW_EDGE_PREFIX` to three octets of a free private IPv4 subnet (for example `172.29.193` for `172.29.193.0/29`) and recreate the stack; never widen trusted proxies to resolve it.
- `node --test scripts/compose-security.test.ts` checks both configurations, including removal/weakening of container restrictions and proxy headers; `node scripts/check-compose-security.ts` builds an isolated stack for each profile, testing read-only migration/probe/send/restart, success and app/proxy error headers, token setup, sign-in, spoofing over proxy, untrusted backend and published debug-port paths, and retained setup. It ignores deployment `.env`, uses disposable values/ports/volumes, and cleans up its own resources. Both it and `check-compose-restart.ts` choose random per-run private edge prefixes in separate ranges; `CHECK_EDGE_PREFIX` can select a known free test subnet. `CHECK_COMPOSE_IMAGE` can reuse a locally built image for the security check.

## Database deployment and upgrade (#194 B)
- Keep `fukulow` as the migration owner. The one-shot Compose `migrate` service uses the same image with `fukulow-server migrate`; only it and DB receive owner credentials. App depends on `service_completed_successfully` and receives only the `fukulow_app` URL. Standalone/dev must run the matching migration command separately with an owner URL; migration commands do not serve HTTP or require setup/proxy settings.
- App startup only reads `public._sqlx_migrations`. Missing history, missing/extra/different versions, checksum differences or any failed row stop startup before listening; it never repairs or migrates. Migration lock waits remain bounded to 5 seconds, including SQLx's advisory lock; failure requires an operator retry of the one-shot service.
- The app pool sends `statement_timeout = 10s` and `jit = off` as connection startup parameters (no per-connection query); they override URL options and role/database defaults. App startup reads both on an app connection and stops before listening unless they match. The one-shot owner/migration connection does not get them; migrations disable statement/transaction timeouts themselves.
- Before applying migrations, the migration command requires `fukulow_app` to exist; otherwise it exits with instructions to run `migrate roles`, leaving the schema untouched.
- `fukulow_app` is LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, NOREPLICATION, NOBYPASSRLS, with no ownership or role memberships in either direction (no role may be a member of `fukulow_app` either). It gets CONNECT, public-schema USAGE, table SELECT/INSERT/UPDATE/DELETE, sequence USAGE and only SELECT on migration history. In the application database it has no CREATE, TEMP, TRUNCATE or trigger-change rights; other databases retain their own PUBLIC privileges. Default privileges apply the same DML/sequence grants to future objects created by the migration owner; the migration command reapplies the history exception afterward. Row-Level Security (#314) restricts it to the transaction-local Organization (or, read-only, the verified Account's own Members); the owner bypasses RLS, so migrations, backups and restore drills run unrestricted. The grants step also limits EXECUTE on `fukulow_setup_required()` to `fukulow_app`, including after a `--no-acl` restore.
- `POSTGRES_APP_PASSWORD` is required by Compose; unset/empty fails closed, never selecting the owner URL. Use a separate URL-safe random value (for example `openssl rand -hex 32`). The role step requires a superuser, as does initdb's Compose owner: before sending the password it transaction-locally suppresses statement/parameter/error-context logging and nested pg_stat_statements tracking, failing closed if settings cannot be changed. It binds/quotes the value as data; PostgreSQL literal-quotes the password utility statement, and role-update diagnostics are suppressed. No password lives in SQL files.
- New volumes run `deploy/init-db-roles.sh` and the shared roles/grants SQL via initdb. Existing volumes do not rerun initdb. Upgrade: take and drill a #198 backup first; set the required setup token (PR A) and new app password in the private deployment environment; build the matching image; stop app/writers; run `docker compose run --rm migrate roles`, then `docker compose --profile caddy up -d` (or nginx). The roles step is idempotent, preserves rows, updates an existing role's password/grants, and rejects ownership/membership instead of reassigning or deleting anything. Keep the same app password on subsequent runs; rotation also requires app recreation. Never remove the volume to resolve an upgrade failure.
- `node scripts/check-db-upgrade.ts` builds the current origin/main image in an isolated temporary directory, populates a disposable volume with Owner, Message and Session, then upgrades it and compares Organizations/Accounts/Members/Messages/Sessions exactly. It tests old-Session access, sign-in, history, restart, privilege denials, #198 backup/drill and restored grants. It never loads deployment `.env`; `CHECK_COMPOSE_IMAGE` may reuse a locally built candidate image; `CHECK_UPGRADE_CACHE_FROM` (buildx `--cache-from`) lets CI reuse main's image layers. CI runs it after the candidate build.
- #198 restores use `--no-owner --no-acl`, so role GRANTs do not require role creation in the isolated drill. For recovery, run the roles step against the restored database after the deliberate database-name switch, before starting app; this restores ACLs/default privileges without changing data. Follow [Operations: backup and restore](#operations-backup-and-restore-198-c), including ending restored Sessions and reconciling permissions.

## Deployment (#194 C)
- The runtime image runs as UID/GID 10001, with a root-owned executable and no writable application data. Dockerfile base images and external deployment/load Compose images use a tag plus a registry-verified multi-platform sha256 digest. Dependabot checks Dockerfile and both Compose directories weekly; image updates still require review and deployment checks.
- Deployment and load `app`/`migrate` use a read-only root, drop ALL capabilities and enable no-new-privileges. Neither has writable mounts or tmpfs; DB and proxy state retain their existing storage. `check-compose-security.ts` checks fresh stacks; `check-db-upgrade.ts` checks a populated main volume, role/migration runs, probe, retained data/Session, send and restart under these restrictions.
- App and both proxies send `Cross-Origin-Opener-Policy: same-origin` and identical empty `Permissions-Policy` feature allowlists on success/errors, including proxy 404s and upstream failures. Listed sensor, media, Clipboard, fullscreen, device and other unused APIs are denied; unlisted features keep browser defaults (no wildcard default directive exists). Ordinary editing/paste is retained. App headers cover optional direct access; proxies replace upstream copies and cover their own errors. Caddy shares one policy across normal/error routes; nginx uses http-scope `add_header ... always`, without child overrides.
- #401's production-equivalent browser acceptance remains a maintainer/orchestrator gate for each deployed TLS profile: setup, Sign in/out, WebSocket send/reconnect, Channel/Topic/Reply, DM, Mention, Search and any external-window/file flow. Automated HTTP/container checks do not satisfy that gate; regressions require a decision before weakening headers.
- Every deployment and load service uses `json-file` logging with `max-size: 10m` and `max-file: 3`. These bounds apply to Docker's local logs per container; arrange separate retention if longer incident history is needed. Recreate existing containers to apply log options.
- Caddy is the default production profile: use a public DNS name pointing at the VPS, reachable TCP ports 80/443 (or the restricted-access procedure below), persistent `caddy_data` and valid HTTPS before setup or Sign in. The localhost certificate is for local checks; clients must trust it explicitly.
- nginx terminates TLS with the official image's bundled official ACME package and a full main-context config. Both profiles share `FUKULOW_DOMAIN`, edge network and trusted proxy IP; keep `FUKULOW_COOKIE_SECURE=true`. Public DNS and reachable 80/443 are required. HTTP-01 is nginx's default; challenge paths never redirect, other HTTP requests for the configured domain redirect to that HTTPS domain. Both profiles reject foreign Hosts, unknown/missing SNI and Host/SNI mismatches before app access. For absolute-form targets, nginx additionally validates the raw Host; Caddy forwards the canonical URL authority. HSTS applies only on TLS; WSS upgrades retain Host and client IP. All API responses, including proxy-generated readiness 404s and upstream errors, use no-store without compression.
- nginx's dedicated `nginx_acme` volume holds account/certificate keys. The master and workers run as nginx; state is nginx-owned, directories 0700/files 0600. Restart/recreation reuse it. Binding 80/443 as nginx relies on Docker's per-network-namespace `net.ipv4.ip_unprivileged_port_start` (normally 0); startup fails with a clear message if it exceeds 80. Never inspect/export state contents or include them in logs/artifacts. nginx has no DNS-01; unattended renewal with both ingress ports closed is unsupported. TLS-ALPN-01 is an optional module alternative, not required or tested here.
- Keep the nginx tag+digest and exact `NGINX_ACME_PACKAGE_VERSION` together: Dependabot proposes image updates; manually inspect the image's `dpkg-query` package version and update both in one reviewed PR. `check-versions.ts` rejects ABI-version drift; startup verifies the package and `nginx -t` loads it against the binary. No module compilation/custom image. Pebble updates are manual tag+digest changes in `scripts/compose-acme.ts`, followed by the same checks.
- `CHECK_COMPOSE_ACCEPTANCE=1 node scripts/check-compose-security.ts` adds the browser suite and restart/recreation/renewal checks for both profiles (`CHECK_COMPOSE_PROFILE` selects one). A pinned local Pebble CA issues ten-minute certificates with real HTTP-01 and no authorization reuse. A test-only directory omits optional ARI to select lifetime-based renewal; Caddy scans every 5s with half-life renewal. After each restart/recreation, directory health and the first served persisted certificate anchor a 15s observation of unchanged serial/order/account counts. Observation continues to reject new orders or replacements before nginx's earliest half-life renewal window (48% of certificate validity, truncated to seconds; nginx 0.4.1 varies half-life by 2%). Only a subsequent new order and serial before the original expiry count as automatic renewal, without another restart. Polls have a 250ms cadence; HTTP challenge/redirect/header checks continue throughout. Only main pushes/manual dispatch run this full gate; PRs retain the existing shorter security check. `CHECK_COMPOSE_WORK_DIR` selects temporary fixture storage.
- **Switching the proxy.** Run `deploy/switch-proxy.sh nginx` (or `caddy`) from the checkout, appending the `docker compose` options used for every other command (for example `-f compose.yml -f '<override>'`). The script needs bash, Docker and host `curl`. Steps:
  1. It records whether the other proxy is running and creates (never starts) the target. If the target's published ports differ from the running proxy's, it refuses and changes nothing (exit 2), so a switch cannot drop a loopback-only override; `SWITCH_PROXY_ALLOW_PORT_CHANGE=1` permits an intended change.
  2. It stops the other proxy, then starts the target with `up --wait`. A proxy is healthy once container port 80 answers HTTP for `FUKULOW_DOMAIN` (a redirect).
  3. It requires verified HTTPS within `SWITCH_PROXY_HTTPS_TIMEOUT` (default 180 s): `https://$FUKULOW_DOMAIN/api/v1/health` through the published 443 must return `ok` with a trusted chain and matching hostname (host trust store, or `SWITCH_PROXY_CACERT`). A failed issuance or an untrusted certificate fails this step.
  4. On failure it stops the target and restarts the previous proxy only if it was running before (with the same health and HTTPS checks), then exits 1; a proxy that was not running stays stopped.
  - Both proxies take the fixed edge IP `<prefix>.2` (and in production 80/443), so Docker refuses to run both; never enable both profiles in one `up`. Each keeps its own state volume (`caddy_data`, `nginx_acme`); a switch removes neither, and returning to a proxy reuses its certificate and account without a new order. A proxy's first start issues a new certificate, which counts toward the public CA's rate limits. The stopped proxy stays stopped across Docker restarts (`unless-stopped`).
  - `node scripts/check-compose-switch.ts` verifies against Pebble, on main pushes and manual e2e-compose dispatch: Caddy -> nginx -> Caddy, refused overlap and port change, restore after issuance failure, untrusted certificate and failed start, a stopped previous proxy left stopped, and reuse on return.
- The binary remains PID 1 with Docker's default SIGTERM stop signal and the existing 75-second stop grace period; #195 handles shutdown. No init wrapper is needed because the server starts no child processes.

### Restricted access through SSH (#392; preparation for #285)

SSH tunnelling is the first candidate, pending maintainer deployment. Firewall public ingress to allow only SSH; close 80/443 on every public IPv4/IPv6 address, including Docker-published paths (host firewall rules alone may be bypassed by Docker). Keep app/DB unpublished. Caddy still terminates TLS for `FUKULOW_DOMAIN=<app-domain>` with a valid domain certificate and persistent `caddy_data`; the tunnel carries TLS unchanged to Caddy, never directly to app HTTP.

**Loopback-only proxy ports.** Docker publishes `80:80`/`443:443` on every host address and its rules can bypass the host firewall, so bind the proxy to loopback with a private Compose override kept outside the checkout. Cover both proxies, so a switch to either keeps the restriction (`deploy/switch-proxy.sh` refuses a target whose ports differ from the running proxy's):

```yaml
services:
  caddy:
    ports: !override
      - "127.0.0.1:443:443"
  nginx:
    ports: !override
      - "127.0.0.1:443:443"
```

Use `!override` (Compose 2.24.4 or later): a plain `ports:` list in an override is appended to the base list and leaves `80`/`443` public (verified with `docker compose config`). Pass it on every command (`docker compose -f compose.yml -f '<override>' --profile caddy ...`, and to `deploy/switch-proxy.sh`); a command that recreates a proxy without it republishes the public ports. nginx has no DNS-01, so while 80/443 stay closed its renewal also needs an approved window. Port 80 stays unpublished; the SSH tunnel needs only loopback 443. Verify on the VPS before and after each change:

```sh
# Before switching: both proxies must render loopback-only ports.
docker compose -f compose.yml -f '<override>' --profile caddy --profile nginx config caddy nginx | grep -A3 'ports:'   # expect host_ip: 127.0.0.1 for both
docker compose -f compose.yml -f '<override>' --profile caddy port caddy 443   # running proxy (or nginx): expect 127.0.0.1:443
ss -ltnH '( sport = :80 or sport = :443 )'                                    # expect only 127.0.0.1:443
```

The maintainer chooses certificate issuance/renewal:

- DNS-01 keeps 80/443 closed, but needs a custom Caddy build with the DNS provider module (absent from the stock image), reviewed/pinned updates and a least-privilege DNS API token kept privately outside the checkout. DNS propagation and token custody add operational work; outbound DNS/ACME access is still needed.
- HTTP-01 (80) or TLS-ALPN-01 (443) can use a short, deliberate public opening with correct public DNS. Run the window without the loopback override, then restore it immediately after issuance and rerun the restriction checks. This temporarily weakens isolation; renewal needs another approved window before expiry or a switch to DNS-01. A one-time opening does not provide unattended renewal while closed.

After approval, on the operator machine (replace placeholders privately):

```sh
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:8443:127.0.0.1:443 '<ssh-user>@<vps-host>'
```

Map `<app-domain>` to `127.0.0.1` in the operator's hosts file, then browse `https://<app-domain>:8443`; keep `<vps-host>` resolving to the VPS for SSH. Local 8443 avoids privileged binding. Preserve domain TLS SNI and HTTP Host (including `:8443`) through Caddy: browsing by loopback name/IP or changing only Host breaks certificate/SNI checks. Do not disable certificate verification. Keep `FUKULOW_COOKIE_SECURE=true` for `Secure`/`__Host-fukulow_session` cookies. Cookie WebSockets require the HTTPS same-Host Origin, including port, or an exact `FUKULOW_WS_ALLOWED_ORIGINS` match; forwarded headers do not decide it ([auth decisions](../decisions/auth.md)). If configured, allow `https://<app-domain>:8443` explicitly. The browser uses `wss://<app-domain>:8443` automatically.

Restriction check, in one run with the tunnel and app healthy: from a non-allowlisted source outside the VPS, test each public address, bypassing local name overrides. Both ports must refuse or time out; DNS failure is not evidence. Any successful TCP connection fails the restriction check.

```sh
nc -4 -vz -w 5 '<vps-public-ipv4>' 80
nc -4 -vz -w 5 '<vps-public-ipv4>' 443
nc -6 -vz -w 5 '<vps-public-ipv6>' 80
nc -6 -vz -w 5 '<vps-public-ipv6>' 443
```

Run the IPv6 pair from a source with IPv6 connectivity against every global VPS IPv6 address; skip it only when `ip -6 addr show scope global` on the VPS is empty, and record that. A source without IPv6 cannot prove refusal.

In that same run, on the operator machine, require HTTPS 200 (`ok`) and a TLS WebSocket upgrade (`101 Switching Protocols`) through the tunnel:

```sh
curl --noproxy '*' --resolve '<app-domain>:8443:127.0.0.1' --connect-timeout 5 --max-time 10 -sS -D - 'https://<app-domain>:8443/api/v1/health'
curl --noproxy '*' --resolve '<app-domain>:8443:127.0.0.1' --connect-timeout 5 --max-time 10 --http1.1 -sS -D - -o /dev/null \
  --cookie '<private-cookie-jar>' -H 'Origin: https://<app-domain>:8443' \
  -H 'Connection: Upgrade' -H 'Upgrade: websocket' \
  -H 'Sec-WebSocket-Version: 13' -H 'Sec-WebSocket-Key: <base64-16-byte-nonce>' \
  'https://<app-domain>:8443/api/v1/orgs/<organization-id>/ws'
```

Use a valid signed-in Member's cookie jar (0600, outside checkout) and a base64-encoded 16-byte handshake nonce; never paste credentials into commands/logs. HTTPS with Upgrade headers performs the `wss` handshake. The curl stream may time out after 101; require the observed 101, not curl exit success. No credential with an allowed Origin returns 401 before upgrade; missing/disallowed cookie Origin returns 403 (`origin_not_allowed`), not 101 (`server/src/realtime.rs`, `server/src/realtime/origin.rs`).

**Client IP through the tunnel (operational note).** All tunnelled traffic reaches Caddy from the VPS itself through Docker's loopback port proxy, so the app sees one shared client IP (typically the Docker bridge gateway) for every operator. The per-IP sign-in failure budget (20 per IPv4 or IPv6 /64, 60 s) is therefore shared: one user's failed sign-ins can throttle every tunnel user, and logs/metrics cannot tell users apart by IP; identify them by Account instead. Do not add forwarded headers or widen `FUKULOW_TRUSTED_PROXIES` to recover the original IP. Lifting the restriction restores per-client IPs only for clients connecting directly to public Caddy; clients still using the SSH tunnel keep sharing one IP.

R2 backup/alert/restore gates remain [#316](#operator-runbook-and-production-hold-316), without credentials, endpoints or account values here. Provisioning, contracts, DNS, certificates, credentials, deployment and lifting the restriction remain maintainer work ([workflow §12](../workflow.md#12-needs-the-maintainer)); #285 remains blocked.

## Send limit (#306)
- `FUKULOW_SEND_BURST` (tokens, default 10) and `FUKULOW_SEND_REFILL_PER_SECOND` (tokens per second, default 1) size the per-(Organization, Member) send bucket (S6 in `docs/spec/realtime.md`). Each must be an integer from 1 to 1,000,000; unset uses the default; empty, zero or invalid values fail startup.
- Compose passes `${FUKULOW_SEND_BURST:-10}` and `${FUKULOW_SEND_REFILL_PER_SECOND:-1}`, so production keeps 10 and 1/s unless `.env` sets them. Do not raise them in production; CI raises them only for the light k6 run and browser tests, which send from one Member.
- The settings change only bucket size and refill: authorization order, idempotency, the waiter/key/bucket caps and 503 fail-closed behaviour stay the same. Restart the app to apply a change; buckets are in-process and start full.

## HTTP availability
- `/api/v1/health` remains liveness: plain-text `ok`, no DB/worker check. Internal `GET /api/v1/ready` returns plain-text `ok` (200) when DB `SELECT 1` succeeds, bounded connection cleanup completes and the fallback supervisor has not observed an abnormal exit; not-yet-started is normal. Worker availability is a supervisor latch, not a progress watchdog: a hung worker or an exit the supervisor has not yet observed can still appear available.
- Readiness failure returns 503 `ErrorBody` (`error: "not_ready"`), `Retry-After: 1`, no internal details. Both endpoints use `Cache-Control: no-store`. Worker failure recovers through #163 process replacement; DB recovery can restore readiness in-process.
- Readiness coalesces overlapping callers onto one check and shares its result; the next caller after completion starts a fresh check. Acquire, query and explicit connection return each time out after 200 ms (600 ms total). Errors or query cancellation detach/drop the socket; cancellation or timeout during return drops the return future's socket and pool permit. Admission lasts through return/discard, including when an HTTP caller disconnects. It shares the FIFO app pool, holds at most one slot, and takes no #156/#158 send/watermark permits.
- Compose app/load checks run `fukulow-server probe` every 10 s (1 s internal deadline, 2 s Compose timeout, 3 failures, 10 s startup allowance). The runtime binary probes `/ready` directly on the configured app address/port, trying resolved addresses within one overall deadline and mapping wildcard IPs to loopback; no ports are added. Its separate current-thread runtime shuts down without waiting for stalled blocking hostname resolution; the server runtime and shutdown are unchanged.
- Both proxies respond 404 for the exact `/api/v1/ready` path; `/api/v1/health` routing is unchanged. Compose probes go directly to the app and bypass the proxies. Proxy `depends_on: app` remains `service_started`. Unhealthy alone does not restart Compose; #163 abnormal-exit recovery and `restart: unless-stopped` are unchanged.
- During graceful shutdown, new HTTP API requests return 503 with JSON `ErrorBody` (`error: "shutting_down"`), a jittered `Retry-After` of 1–5 seconds and `Cache-Control: no-store`. This instance is stopping; the outer middleware rejects requests before authentication, extraction or operation admission, including health checks and WebSocket handshakes.
- Clients retry after `Retry-After`, preserving the same `client_message_id` for sends to retain idempotency (C6). Send-admission 503 (`send admission unavailable`) instead rejects one operation because its queue is full or its 30-second admission wait expired; persistence has not started. Projection-admission 503 (`projection admission unavailable`) is also an operation capacity rejection. Both admission responses use the same retry range and no-store policy.

## Logs and aggregates (#198 B)

Read application JSON lines from stderr with `docker compose -f compose.yml logs --no-log-prefix --since 10m app`. Existing Docker rotation bounds retained history; keep incident extracts private. No metrics endpoint, monitoring service or persistent metric storage is added.

- `fields.event=http_completed` carries an `http_request` span with `request_id` (fresh UUID per request), `method`, matched `route` template, numeric `status` and `duration_ms` through response creation (not body streaming or WebSocket lifetime). Unknown routes use `<unmatched>` and extension methods use `OTHER`. Inbound `X-Request-Id` is ignored and no response header is added. Headers, raw paths/queries and bodies are never recorded.
- WebSocket `websocket_opened`, `websocket_closed` and `websocket_disconnected` events retain the upgrade request span. `websocket_closed.code` is a fixed bucket. Counts represent server Close attempts, including failed/timed-out writes, not confirmed receipt. A peer Close or transport EOF/error is counted separately as `peer_or_transport_end`; peer reason/text and arbitrary peer codes are never logged. Disconnect includes task cancellation; an aborted task may have no Close attempt.
- One `fields.event=metrics` line every 60 s (first after 60 s; missed ticks skipped) reports `active_websockets`, `close_1001`, `close_1011`, `close_4001`, `close_4003`, `close_4008`, `close_4029`, `close_other`, `peer_or_transport_end` and `admission_rejections`. Active counts established callbacks, excluding pending/failed handshakes, until callback exit/cancellation. Other counters are cumulative since process start. Each atomic read is safe; concurrent updates mean the whole line is an approximate snapshot. Restart resets all counters; a process dying before a tick can lose unreported counts.
- Admission sites increment counters without per-rejection diagnostics. Each nonzero category emits at most one `fields.event=admission_rejected` line per tick with `kind` and cumulative `count`. Categories: `send_channel_queue`, `send_global_queue`, `send_channel`, `send_global`, `watermark_channel`, `watermark_global`, `notification_channel`, `notification_global`, `notification_organization`, `notification_execution`, `socket`, `password`. Compare successive counts to see growth. Categories and Close buckets are fixed; no Organization, Channel or Account labels. Ordinary HTTP completion and socket lifecycle logs still track individual requests/connections.
- `database_failure.kind` is allowlisted: `pool_timeout`, `pool_closed`, `deadline`, `io`, `database`, `other`. Synthetic WouldBlock admission errors are counted at their admission site, not logged again. Existing SQLx error overloading (#290) still limits classification. Worker stop, cleanup/work deadlines and missing Unread positions have named events without raw errors or entity IDs. Only reviewed `fukulow` tracing events are enabled; `RUST_LOG` cannot enable SQL/parameter/dependency diagnostics. Never log cookies, bearer credentials, passwords, setup/Invite tokens or Message bodies.
- Cleanup database failures include `span.operation=session_cleanup`. A payload-safe panic hook is installed before tracing setup and Tokio runtime construction; startup, task and thread panics emit only the fixed JSON `fields.event=panic` to stderr, without payloads or backtraces. Panics retain Rust/Tokio's normal unwind/termination behavior.

### Application pool statistics (#426)

- The serving process emits one JSON line with `fields.event=pool_stats`, `version=1` every 1 s, first after 1 s. Missed ticks are skipped. `sample_sequence` starts at 1; `sample_elapsed_ms` is actual monotonic time since the previous sample (since reporter start for the first). `interval_ms=1000` is the target cadence. Detect gaps before interpreting samples as per-second occupancy; do not fabricate missing samples.
- Every application acquisition after SQLx connects routes through `database::acquire` (transactions through `database::begin`). This includes readiness, detached workers, sends, setup status and its pre-transaction check, detached sign-out revocation, Account Session/Invite/security lookups and startup migration-history and session-settings validation. The locked setup recheck uses its existing transaction connection. Former `&PgPool` executor calls explicitly acquire first; new application code must use the same path, including for one-statement queries. Direct SQLx pool acquisition/executors are reserved for owner commands and test fixtures. Pool settings and deadlines are unchanged.
- Each line declares `coverage="application_after_connect"` and `uncovered_paths="startup_connect,migration_commands"`: SQLx's initial connection acquisition and the separate one-shot owner commands are outside these counters. Maintenance opens/returns connections without an application checkout and is also unmeasured. Serving startup connection failure has no pool-stat line. These exclusions are not request-time gaps.
- Wait fields are cumulative inclusive histogram buckets, in microseconds: `wait_le_100_us`, `wait_le_500_us`, `wait_le_1000_us`, `wait_le_5000_us`, `wait_le_10000_us`, `wait_le_25000_us`, `wait_le_50000_us`, `wait_le_100000_us`, `wait_le_500000_us`, `wait_le_1000000_us`, `wait_le_5000000_us`; `wait_count` is the +infinity bucket. Elapsed time rounds up to microseconds, so a wait just beyond 10/50 ms cannot enter its budget bucket. Successful, failed and cancelled waits enter the distribution once when they finish; an in-flight wait enters a later window.
- Cumulative outcomes: `acquire_success`, `acquire_timeout` (SQLx PoolTimedOut), `acquire_closed`, `acquire_io`, `acquire_database`, `acquire_other`, `acquire_cancelled` (future dropped, including external deadlines). `waiting` is the in-flight gauge. SQLx can retry connection errors and eventually return PoolTimedOut; causes describe the final result, not suppressed retries. Cancellation cannot distinguish caller disconnect from an external deadline.
- `in_use` and `idle` sample SQLx size minus idle and idle, respectively. Reads can race maintenance/returns; idle is clamped to size. Cumulative occupancy histogram fields are `occupancy_le_N` for N = 0, 1, 2, 4, 8, 16, 24, 32, 48, 64, 100; `occupancy_count` is +infinity. One observation per emitted line; derive occupancy p95 from bucket deltas (or raw samples), and peak from the maximum `in_use` in the window. This is sampled occupancy, not a high-water mark between samples.
- For a window, subtract cumulative values at its boundaries. The first bucket reaching ceil(q × delta count) bounds percentile q. Exact edges 10,000/50,000 us and 24/32 allow the DM pool budgets to be checked without interpolation. No acquisition timeout requires delta `acquire_timeout=0`; review cancellation and other error deltas separately. Missing baseline, missing samples, process replacement or absent lines must remain visible to the runner. Counters reset with the process; concurrent atomic reads make snapshots approximate. No SQL, raw errors, tenant identifiers, credentials or request context enter the line.

## Operations: backup and restore (#198 C)

### Backup and custody

Use deployment `.env` (0600), pinned Node, Docker Compose and deployment `COMPOSE_PROJECT_NAME`. Scripts resolve root via `import.meta.url`; manual commands require checkout root. Backup requires PostgreSQL 18 in `db`. The drill reads the literal pinned `services.db.image` directly from tracked `compose.yml` without invoking Compose or loading secrets; update that single definition. Scripts ignore `DATABASE_URL`/suppress diagnostics. Never use `set -x`, print environment/`docker compose config`, save raw errors or put credentials/URLs in cron/arguments/logs. Keep records private.

```sh
umask 077
mkdir -p /srv/fukulow-backups
chmod 700 /srv/fukulow-backups
node scripts/backup.ts /srv/fukulow-backups
```

Use an operator-owned 0700 non-symlink directory under a trusted parent outside checkout/web root. Archives are 0600; only `fukulow-*.dump` is final after flush, dump and `pg_restore --list`. Publication renames the archive then fsyncs the destination directory; failed fsync reports failure, retains the renamed archive and older archives, and requires manual durability/integrity confirmation before copying it. The CLI prints fixed success text, never an archive path. Backup and drill failures expose only allowlisted stage/error categories and exit status 1, never raw diagnostics. `--list` checks structure: also drill. Separately protect roles, server configuration, TLS keys and `.env`; record code revision/migration versions. Never migrate the only restored copy with newer code.

All local backup writers hold `.backup-run.lock` through dump, encryption, upload and cleanup. Under that lock, sweep only owned 0700 non-symlink directories matching the generated `.partial-` or `.partial-age-` plus six alphanumeric characters; preserve other entries and completed archives. Never copy partials. Locks left by a crash are refused regardless of age or PID; stop all writers before manually removing a stale lock, then let the next run sweep remnants. Trusted parents and cooperative use of the same lock are required.

Schedule daily (e.g. 02:15 UTC), provision capacity, check success/free space daily. Keep ≥14 successful daily archives on VPS, ≥30 off VPS, and latest drilled archive until replacement passes. VPS pruning is manual: only finals with verified off-VPS copies, never last good copy or merely because a job ran.

### Automated off-VPS backup (#316; mock implementation)

Off-VPS backup uses a dedicated R2 backup bucket, separate from the future images bucket. No lifecycle expiry. The VPS token is scoped to backup objects; image credentials never reach backups. The checker uses a backup read/delete binding and lists images only for capacity. Restore uses a separate read-only token held by the maintainer. Tokens/config files are user-owned 0600 outside the checkout, Compose environment and app container; diagnostics and notification events contain no private values.

The daily schedule is 02:15 UTC (systemd calendar, persistent catch-up); hourly independent checks use the injected checker. The tracked schedule contract in `scripts/backup-r2.ts` is inert: no timer, Worker, notification transport or production entry point is installed. Production wiring waits for approval. The daily flow takes a conservative capture timestamp after preflight immediately before the existing PostgreSQL 18 custom dump (a conservative snapshot-time bound), followed by its structural check, encrypts with age to an X25519 public recipient, and uploads only ciphertext. The private identity stays offline with the maintainer in at least two places. Local retention remains manual, at least 14 generations.

Each attempt writes `backups/<capture-UTC>-<attempt>/archive.dump.age`, then `manifest.json`, then `verified.json`. The strict version-1 manifest records capture time, PostgreSQL major, plaintext/ciphertext SHA-256 and positive byte sizes, and SHA-256 of the recipient. The marker contains manifest SHA-256 and verification time. PUT includes hex SigV4 payload SHA-256 and base64 checksum; HEAD requires checksum mode ENABLED and matching size/checksum. Full GET read-back of archive and manifest must match before the marker is written. The marker is also checked. curl uses three retries, all errors and bounded time; uncertain PUTs are reconciled by HEAD. A mismatch abandons the generation and retries a fresh suffix (three attempts maximum), never overwriting an uncertain object.

Only a parsed marker matching the manifest hash, strict manifest, capture matching the prefix and no more than five minutes ahead, and archive HEAD matching ciphertext size/checksum count as verified. All other prefixes are reported as malformed, excluded from freshness/counts and never selected for restore. The VPS daily flow re-reads the newest verified archive in full; the independent checker reads only small JSON objects and HEAD metadata, never archive bodies. Restore selection must use this same predicate and fully hash the download before decryption and the existing drill.

The backup prefix has a 35-day lock; restore-verified has a 40-day lock. No age-based expiry is configured. Each checker run prunes at most five generations, only after every object is past lock, outside the newest 30 verified backups, and never the source capture of the latest restore-verified copy. Fewer than 30 verified backups, newest capture at least 24 h old, or malformed inventory freezes all deletion and alerts. Locked/protected candidates are retained. The newest restore-verified copy is never deleted; older copies require expiry of their lock and a newer copy. After a successful monthly drill the maintainer copies the whole verified generation to `restore-verified/<capture-UTC>/`; the latest copy is selected by completion time (the latest upload time of its three objects), which also measures drill age. Alert at 35 days without a new copy.

The checker alerts on stale/missing backups, malformed inventory, insufficient generations, failed checks, overdue drills, and newest ciphertext below 50% or above 200% of the median of the previous seven verified archives. Daily alive messages include newest capture, backup bytes, image bytes, total bytes and percentage of the shared decimal 10 GB free tier, and account Class A/B operation usage. Alert at 70% and 90% capacity and 70% of 1M Class A/10M Class B operations. The injectable analytics client queries the provider's account-wide operations dataset, grouped by `actionType` (`groupBy: [actionType]`), without a bucket filter, for each UTC day from month start to now. Unknown actions, empty/incomplete/capped responses, invalid counts and request failures yield `operations-unknown`, null usage and frozen pruning, never zero/OK. The backup job never refuses a backup to save cost.

The S3 adapter follows opaque ListObjectsV2 continuation tokens to completion. Every page must match the unfiltered request: absent/empty Prefix, StartAfter and Delimiter, no CommonPrefixes or EncodingType. Scope mismatches (including changes after continuation), missing/repeated/inconsistent tokens, duplicate keys, invalid metadata/counts, malformed XML, failed pages or the 10,000-page cap fail the entire inventory; no partial inventory may prune. Only the exact internal `coordination/run.lock` object is excluded from inventory.

`runChecker` loads/saves versioned checker state in an external owned 0600 regular file under a trusted 0700 directory. Each successful notification persists alive UTC day or sent active alerts by file fsync, atomic rename and directory fsync. Unchanged alerts deduplicate until resolution; failed delivery is retried. Missing/corrupt state alerts and freezes pruning for that run; safe regular corrupt files are replaced after notification, unsafe files/symlinks are refused. State opens use nonblocking/no-follow flags before descriptor-based regular-file/owner/mode checks, so a FIFO cannot stall the runner while it holds the lock. Notification and persistence cannot be atomic together: a crash between them may duplicate a notification; delivery is at least once, never guaranteed.

Backup/daily backup and checker entry points require the same shared run lock. `bucketRunLock` acquires `coordination/run.lock` by conditional PUT (`If-None-Match: *`); only the successful owner runs. Conditional DELETE support is not assumed: release requires the acquisition ETag, a conditional GET (`If-Match`) of that version and an exact owner-token match immediately before DELETE. A missing ETag, failed check or owner mismatch refuses deletion. The GET/DELETE pair has a residual race if manual recovery replaces the lock between those requests; it cannot fence a suspended owner, so recovery must quiesce every writer/checker. Verified provider support for conditional DELETE would permit using `If-Match` on DELETE to close that race. The key must be outside retention-lock rules and every writer (including manual restore-copy/cleanup) must participate or pause schedules. The full entry-point lifecycle, including busy/uncertain acquisition, release and local cleanup, attempts a fixed `backup-failed` or `checker-failed` notification; notification errors remain suppressed. Acquisition/deletion are never retried; an uncertain response or crash may leave a lock and must fail closed. No automatic expiry/takeover is safe for a suspended pruner. Recovery requires stopping every writer/checker, confirming none can resume, inspecting the lock privately, then removing only the abandoned lock. Local filesystem state requires one durable checker runner; a Workers deployment needs equivalent persistent storage/coordinator wiring before activation.
