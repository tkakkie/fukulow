# Issue #689 search SQL PoC

Run from the repository root with Node from `.node-version` and Docker. The build uses the B1 Dockerfile with PostgreSQL 18.6 and PGroonga 4.1.0. The output parent must exist outside the worktree and the output directory must be new. The runner owns the container it creates, `fk689-poc-pg`, and removes it on exit. If the runner is killed while a synchronous `psql` or `docker` call blocks, remove it manually with `docker rm -f fk689-poc-pg`.

```sh
docker build -t fk689-poc-pg:local -f load/search-engines/Dockerfile load/search-engines
node --test load/sql-probes/689-d3/model.test.ts
node load/sql-probes/689-d3/run.ts --smoke --repetitions 4 --out /absolute/smoke/run
node load/sql-probes/689-d3/run.ts --repetitions 200 --out /absolute/recorded/run
```

Use an idle host for a recorded run. `--repetitions` is the number of transactions per class, arm and pgbench client. The default is 20. Smoke uses one client and a recorded run uses five. The write probe uses one writer with the same number of repetitions per operation. Every run uses the same 24,007 synthetic Messages across three Organizations. Each Organization has public Channels, private Channels, DMs modelled with the B1 grant path, Members and a Guest. Both reads and d3 writes use restricted, non-owning login roles with forced tenant RLS. The superuser sets up fixtures, applies authorization changes in the fixture, and runs the brute-force oracle with explicit visibility and substring checks.

## Query shapes

- **d3** stores one row per distinct one-, two- or three-scalar gram of a Message's normalized body. The exact key is `<channel UUID>:<gram>`; a DM uses its Channel UUID. A trigram is more selective than a unigram or bigram for longer queries and keeps the seed lookup to one key per visible scope. A one- or two-scalar query uses its full normalized text as an exact unigram or bigram key. Longer queries use their first trigram as a necessary condition and apply an escaped LIKE to the full normalized body for candidate Messages in that Channel. A common first trigram can still produce many candidates. The term opclass uses exact equality with tokenization and normalization disabled. [PGroonga index options](https://pgroonga.github.io/reference/create-index-using-pgroonga.html)
- **d4** reads each visible Channel's recency B-tree range in descending Message time and ID, applying escaped LIKE until 20 hits or the range ends. Its outer sort merges at most 20 hits per scope. The timed d4 transaction disables bitmap scans locally to measure the ordered walk. A separate frequent-query plan keeps the default planner settings to show the choice it makes. The shared table also has the B1 text index. d3 and d4 use an expression for the LIKE recheck that keeps the B1 index out of their plans.
- **B1** reuses the existing role, restrictive LIKE policy, index and query on the same database. Both new shapes reuse the B1 visibility CTE and the 180-day date window. A Channel's grant, a Member's active state and Role are read at query time. Send, Edit, Delete and Move update individual d3 term rows in the Message transaction. Grant removal, Guest Role changes, deactivation and Channel visibility changes use the existing term keys. A consistency check inserts a stale key for a visible public Channel that points at a private Channel's Message and shows that d3 still hides it.

## Evidence

- `metadata.json` records the commit and worktree state, harness source hashes, pinned base image digest and built image ID, DB settings, verified roles and RLS, plan mode, cache condition, client count and repetitions. Read sampling uses pgbench's prepared protocol in Auto mode. The plan summaries record `pg_prepared_statements` state from the SQL PREPARE used for each EXPLAIN.
- `correctness.json` contains oracle IDs for full matches and the ordered top page for each class. The runner checks all three variants against both, including composed and decomposed input, short queries, wildcard decoys and both time-window boundaries. `consistency.json` includes before/after search observations, term changes and unchanged term snapshots for authorization changes.
- `plans.json` summarizes raw `*-plan.json` files. Check d3's exact `scope_term` index condition and scan loops against the visible scopes in metadata. EXPLAIN reports executor activity, without instrumenting Groonga file I/O by key. Compare sort input with its LIMIT output. A top-N heapsort still consumes its entire input. Check for a d4 ordered recency Index Scan beneath the per-Channel Limit and no B1 index scan.
- `latency.json` reports small-DB-only p50/p95 in ms for each variant and class. `timing.json` reports the same percentiles and many/few ratios for each d3/d4 pair. A matching fingerprint checks row IDs, scope, timestamp and byte length, and checks body content outside the one deliberately changed foreign block. The arms have the same visible page and 1 versus 1,000 foreign matches. Both arms are fresh databases built and warmed the same way. The few arm's 999 other foreign rows hold a ROT13 decoy of the key, with the same length, bytes and distinct-gram count, so both term tables have the same row count. `termIndex` records, per arm, the superuser count of the foreign scope key read through `search_terms_exact` (asserted 1 and 1,000), the term row count (asserted equal), term heap and index relation bytes, and Groonga file bytes at index build. PGroonga keeps its data in Groonga files, so the index relation size is 0, and those files grow in fixed chunks; `foreignKeyRows` is the evidence that the arms differ. The sampler warms each arm, alternates block order, and retains pgbench samples, scripts, logs and raw plans. Results are descriptive measurements of the three fixtures. Cache state, index metadata and physical placement can still affect timing.
- `writes.json` reports d3 logical tuple bytes and rows written or retired per transaction, PostgreSQL WAL insert-LSN deltas and elapsed commit-inclusive timings. The write sample uses fixed synthetic bodies and drops the read comparison indexes first. Logical bytes come from `pg_column_size`. PostgreSQL WAL bytes include full-page images where applicable. The pinned image defaults leave PGroonga WAL and crash-safe mode off, so the filesystem size and PostgreSQL WAL metrics describe different costs. Size reports include the d3 heap and maintenance B-tree, PostgreSQL relation size and incremental Groonga side-file bytes at index build, plus the d4 recency B-tree. The per-10k and 1M figures scale the observed small-DB bytes linearly. They do not measure growth, churn, bloat or performance at 1M.

The corpus uses repetitive short bodies, seven Channels per Organization, and a physical Delete in the synthetic schema. Authorization changes are serialized. The scope is limited to SQL and descriptive small-DB measurements. Smoke artifacts are local working files. Follow [focused SQL measurement retention](../../../docs/workflow.md#14-focused-sql-measurements) for a recorded run.

## Constraint for a production d3

`search_terms` has only tenant RLS; its key prefix is the only scope inside an Organization. A production design must read the term table only through the query-time visible-scope join followed by the `messages` recheck (`m.channel_id = v.id`, tenant RLS, escaped LIKE). Counts, estimates, autocomplete or prefix scans over the term table would expose grams from private Channels and DMs. Only the trigger or owner code may write the table; unlike this PoC's writer role, the application role should get no direct write grant on it. A missing key silently drops hits. A stale or extra key can drop or add candidates, but the recheck keeps it from exposing a Message.
